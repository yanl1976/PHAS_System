# 工时组合：发布控制 + 产品部件层级 + 工艺卡

> 2026-11-04 提案。目标是把「889 个工时组合」从一张**观察用的聚合视图**，
> 变成一套**有状态、有归属、有层级、可被引用的工艺内容**。

---

## 一、现状：先用数据把问题说清楚

### 1.1 889 从哪来（没有实体，只是并集）

`app/services/combos.py:list_combos()` 里，组合是两处的并集：

```
standard_hour 的 (product, part, process…)   ← 历史工时账（1279 行）
      ∪
process_route 的 (product, part)             ← 已建的基线工艺（85 条）
```

没有 `combo` 表，所以**组合没有自己的身份**：不能挂状态、不能挂层级、不能挂确认人。
所谓"状态"是从路线状态**投影**出来的（`_route_state()`：已发布 > 草稿 > 归档 > 待建）。

实测（2026-11-04）：

| 项 | 数量 | 说明 |
|---|---|---|
| 组合总数 | **889** | 其中 89 条产品名为空（全是钳工序，归属不明） |
| 已发布（released） | 81 | 对应 81 条已发布基线路线 |
| 草稿（draft） | 1 | |
| 待建（none） | 807 | **没有任何工艺内容**，只是历史工时的一堆数字 |

### 1.2 那 81 条"已发布"，其实没有工艺员签过字

```
published_by = 'migration'   81 条（另 2 条为 fork，published_by 空）
published_at = 2026-11-03 23:31:09 ~ 23:32:44   （同一秒批量写入）
source       = 'history'
```

也就是说：**81 条"正式可引用"的工艺，是迁移脚本一次性标出来的**，不是任何人确认的结果。
这正是“需要经过工艺员确认后发布”要解决的第一个问题——现在的"已发布"不具备业务效力。

### 1.3 已发布 → 可引用，这条链已经通了（但要补组合这一层门）

- `routes.released_index()`：只把 `kind='route' AND status='released'` 的路线喂给识别校验。
- 在制任务 6 条，**全部**引用 released 路线（`task_route.origin`：baseline 4 / copy 2）。

问题在于：这条门只设在**路线**上。组合这一层没有门，所以"889 个组合默认草稿"无处落地——
它们连"草稿"这个身份都没有。

### 1.4 层级只存在于人脑里

- 树（`routes.build_tree()`）现在是两级：**产品 → 件名（平铺）**，件名之间没有父子。
- 但件名数据本身已经带着层级痕迹：`YUJ-18BZ` 下同时有
  **整机装配**、料仓组件、包板总包、机架、主轴、刀具……
  "整机装配"是总装，"料仓组件"是部件，"主轴"是零件——系统把它们当兄弟平铺。
- 工艺卡（`docs/工艺及工时编排_方案设计.md` 的 P1「F7 工艺过程卡导出」）一直没做，
  所以"层级怎么落在卡上"没有历史包袱，可以从头设计对。

### 1.5 三个结构性缺口（决定方案形态）

| 缺口 | 后果 |
|---|---|
| **组合没有实体** | 无法"默认草稿"、无法批量确认、无法按产品分类挂层级 |
| **发布没有人工确认** | 81 条假发布；发布后谁批的、凭什么批，答不出来 |
| **层级不在数据里** | 工艺卡只能一张一张按件名出，显示不出"这台机器由哪些部件总装" |

## 二、目标与边界

### 目标

1. 组合成为**受控对象**：默认草稿，工艺员确认后发布，发布后才可被前端引用。
2. 组合**按产品归类**，树上按**总装 → 部件 → 子件**多层展开。
3. 工艺卡**按层级成册**：总装卡带出子件卡，工时能层层汇总。

### 明确不做（这一版）

- **不做完整 BOM**：用量、替代料、共用件、BOM 版本、领料——都不是现在能拿到数据的。
  这一版只做"谁挂在谁下面 + 单台用量"。
- **不改报工口径**：`work_item` 仍按件名记实报，月度汇总不变。
  层级只在"编制/工艺卡/报价/产能"侧使用，否则历史数据会全乱。
- **不做跨产品通用件**：同一件名在不同产品下工艺不同，这是现有模型（组合键含产品）的前提。

## 三、数据模型

### 3.1 新表 `work_combo`（工时组合主档）

```python
class WorkCombo(Base):
    __tablename__ = "work_combo"
    __table_args__ = (
        UniqueConstraint("product", "part", name="uq_combo_key"),
        Index("ix_combo_state", "state"),
        Index("ix_combo_parent", "parent_id"),
    )

    id: int
    # —— 身份：产品 × 件名（与 standard_hour / process_route 同键）——
    product_id: int | None       # product_dict.id，发布前必须有
    product: str                 # 保留历史写法，显示用
    part: str
    part_id: int | None          # part_dict.id（可选，用于查归类/别名）

    # —— 层级：总装 → 部件 → 子件 ——
    level: int = 1               # 0=总装  1=部件/零件  2+=子件
    parent_id: int | None        # 上级 work_combo.id；NULL=挂在产品根
    qty_per_unit: float = 1.0    # 单台用量
    seq: int = 10                # 同层排序

    # —— 状态 ——
    state: str = "draft"         # draft / confirmed / released / archived
    state_note: str = ""         # 降级/归档原因
    confirmed_by: str = ""
    confirmed_at: datetime | None
    published_by: str = ""
    published_at: datetime | None
    revoked_by: str = ""
    revoked_at: datetime | None

    # —— 当前生效的工艺内容 ——
    current_route_id: int | None # → process_route.id；released 时必填
    version: int = 0             # 已发布次数（只增）

    active: bool = True
    note: str = ""
    created_at / updated_at
```

### 3.2 三张表的分工（这次要讲死，否则以后会互相污染）

```
WorkCombo      工艺内容的「身份 + 状态 + 层级」      ← 新增，唯一权威
   │  current_route_id
   ├──> ProcessRoute  工艺内容的「版本」（已有：draft/released/archived）
   │        └── ProcessRouteStep  工序行（工时定额）
   └──> StandardHour  历史实测样本（只读参考，不参与发布）

WorkItem       现场实报（按件名，不进这张树）
```

一句话：**组合回答"这是什么零件、归谁管、能不能用"，路线回答"怎么做、多少工时，第几版"。**
`standard_hour` 从此只做两件事：生成草稿的输入、校验偏差的参照。

### 3.3 不变量（服务层强制，迁移时校验）

1. `state='released'` ⇒ `current_route_id` 非空，且该路线 `status='released'`，且 `(product, part)` 一致。
2. 同一 `(product, part)` 同时只能有一条 released 路线 —— 已有唯一索引 `uq_route_released` 兜底。
3. `state='released'` ⇒ `product_id` 非空（挂不上产品树的组合不许发布，89 条缺产品名先认领）。
4. `parent_id` 必须同产品、不能指向自己、不能成环，链路深度 ≤ 5。
5. `archived` 是终态：复原要重新走 draft → 发布（保留历史版本）。

## 四、发布流

### 4.1 状态机

```
                 系统聚合 / 手工新建 / 从历史生成
                              │
                              ▼
                        ┌──────────┐
                        │  draft   │ 草稿：可编辑，前端一律不引用
                        └────┬─────┘
                   工艺员确认 │ (工序/工时/件名/层级)
                              ▼
                        ┌──────────┐
                        │confirmed │ 已确认：内容锁定，仍不可引用
                        └────┬─────┘
                 发布(工艺主管)│  ── 同事务内调用 routes.publish()
                              ▼
                        ┌──────────┐   新版本发布
                        │ released │ ──────────────> 旧版转 archived
                        └────┬─────┘
                    撤发布  │  （有在制任务引用时需二次确认）
                              ▼
                          draft（保留版本号，不删内容）
```

**默认一步走**：界面上的主按钮是「确认并发布」，此时 `confirmed_by = published_by`，
状态直接落 `released`。若要两级审批，在系统管理开 `require_confirm_step`，
工艺员点「确认」、主管点「发布」，两步都留痕。字段已经预留，不用改表。

### 4.2 发布前置校验（7 条，缺一不可）

| # | 校验 | 不通过时 |
|---|---|---|
| 1 | 能解析到产品（`product_id`） | 阻断："先在产品字典里认领这个写法" |
| 2 | 有当前草稿路线，且工序 ≥ 1 道 | 阻断："先点『从历史生成草稿』" |
| 3 | 每道工序 `unit_hours > 0` | 可放行：勾"暂无定额"并填原因（有些工序确实记时） |
| 4 | 同工序名不重复 | 阻断 |
| 5 | 层级合法（§3.3 第 4 条） | 阻断 |
| 6 | 与 `standard_hour` 单件合计偏差 > 50% | 需填「偏差说明」才能发布 |
| 7 | `MISSING_PROCESS`（工序为空）等 block 级告警 | 阻断（沿用 rules.py 现有 block 机制） |

发布动作本身要写的留痕（三处，一个都不能少）：

- `audit_log`：`entity='combo'`，`field='state'`，old=`draft`，new=`released`，操作人取自登录身份。
- `route_version_notice`：复用现有表（`action='publish'`），带 `from_version/to_version`。
- `work_combo` 自身的 `published_by/published_at/version`。

### 4.3 撤发布 / 归档

- **撤发布**（released → draft）：把路线 `status` 退回 draft（现有 `archive`/`reopen` 已能表达）。
  若被 `task_route.status='active'` 引用，先列出**任务单号 + 订单名**，二次确认并强制填原因。
  任务侧走已有的 `ref_released=false` 提醒通道（不是新机制），任务抽屉里显示"该工艺已撤发布，请复核"。
- **归档**：新版发布时旧版自动 archived；`work_combo.state` 保持 released（组合还活着，只是版本变了）。
- **组合停用**（`active=False`）：不参与树默认视图，已发布状态保留，用于淘汰件。

### 4.4 与现有接口的对接（不重复造）

| 现有能力 | 位置 | 新方案里怎么用 |
|---|---|---|
| 从历史生成草稿 | `POST /api/routes/batch-generate` → `R.batch_generate()` | 组合详情页「生成/重建草稿」按钮，生成后组合仍是 draft |
| 发布单条 | `POST /api/routes/{id}/publish` → `R.publish_route()` | 被 `combo.publish()` 内部调用，**唯一入口** |
| 批量发布 | `POST /api/routes/publish-drafts` → `R.publish_drafts()` | 改为"按组合批次走"，跳过条件加上"组合层级/产品归属不合法" |
| 覆盖率 / 待建清单 | `GET /api/routes/tree`、`/coverage` | 状态改读 `work_combo.state`，与路线状态做一致性断言 |

**红线**：发布动作只允许从「组合」这一侧发起（或在编排页发布路线后**同步**组合），
两处各自改状态一定会漂移 —— 服务层封装 `combo_publish(db, combo, ...)`，路线发布内部调用它。

## 五、产品部件层级与工艺卡

### 5.1 层级从哪来：先自动铺一层，再人工细调

889 条如果要求先手工梳理父子关系，这事就永远开不了工。所以**迁移时按规则自动初始化**：

| 规则 | 判定 | 结果 |
|---|---|---|
| R1 | 件名命中 `整机装配 / 总装 / 整机 / 装配`，且该产品下唯一 | `level=0`，`parent=NULL`（作为根） |
| R2 | 件名含 `组件 / 总成 / 总包 / 部件` | `level=1`，`parent=根` |
| R3 | 其余件名 | `level=1`，`parent=根`（有根时） |
| R4 | 该产品没有根（无整机装配件名） | 树接口合成**虚拟根节点**（显示"产品总装"，不落库） |

结果：每个产品开箱即得一棵「总装 → N 个件名」的两层树（YUJ-18BZ：整机装配 → 45 件）。
工艺员之后只处理真正有子件关系的（`料仓` → `料仓水套`/`料仓组件`），不用从头梳理 889 条。

迁移脚本要输出一份**"被识别为根的件名"清单**给人核对——这是唯一可能误判的地方
（万一某个产品下"装配"指的是零件名）。

### 5.2 层级维护入口

- 组合台账：新增「所属部件」列 + 行内「设置层级」（选父件、用量、序号）。
- 编排页树：节点悬停出「挂到…」，支持多选件名批量设父（工艺员一次把 5 个料仓子件挂上去）。
- 校验：设父时即时检查同产品、非自环、不成环、深度 ≤ 5，并提示"父件尚未发布，不影响子件发布"。

### 5.3 工时口径：三个数，必须分开叫

| 口径 | 公式 | 用在哪 |
|---|---|---|
| **本层工时** `own_hours` | `Σ step.unit_hours + setup_hours/batch_qty` | 单张工艺卡卡尾、现有"单件合计" |
| **含子件工时** `rollup_hours` | `own + Σ(child.rollup × child.qty_per_unit)` | 工艺卡册汇总、报价、产能 |
| **产品单台工时** | `Σ(顶层 rollup × qty_per_unit)` | 产品级工时看板 |

界面上三个数**并列且带标题**（本层 / 含子件 / 全产品），不要只给一个"合计"——
否则跟现有的"单件合计 2.58h"对不上，现场一定来问。

### 5.4 工艺卡：层级怎么落在纸上

**编号**（按树的深度）：

```
01            整机装配（总装）
01-01         机架
01-01-02      主轴
01-02         料仓组件
```

**卡片字段**（对齐制造业工艺过程卡的常见格式，不做花活）：

```
┌────────────────────────────────────────────────────────────┐
│ 产品名称/代号：YUJ-18BZ 制丸机          层级号：01-01        │
│ 零件名称：料仓      图号：（待补）        单台用量：1         │
│ 上级部件：整机装配   版本：v3  生效：2026-11-05              │
│ 编制：张三（工艺员）  审核：李四（主管）  批准：—             │
├────┬──────┬────┬────────┬──────┬──────┬──────────┬─────────┤
│序  │工序  │工种│设备/工位│单件h │准备h │检验要求  │备注     │
├────┼──────┼────┼────────┼──────┼──────┼──────────┼─────────┤
│10  │下料  │钣金│剪板机  │0.35  │0.20  │—         │        │
│20  │焊接  │焊工│氩弧焊  │1.20  │0.30  │焊缝探伤  │        │
├────┴──────┴────┴────────┴──────┴──────┴──────────┴─────────┤
│ 本层合计：1.55h   含子件累计：1.55h   子件：无              │
└────────────────────────────────────────────────────────────┘
```

层级在卡上的三个落点：

1. **卡头**印「层级号 + 上级部件」——单张卡拿出来也知道它装在哪。
2. **卡册顺序**按层级深度优先（总装 → 一级 → 二级），编号即装订顺序。
3. **卡尾**给「本层 / 含子件」，子件清单列名字与用量（点得进去看子件卡）。

### 5.5 工艺卡在页面上的形态

放在「工艺及工时编排」页，顶部加模式切换，不新开一级菜单：

```
┌ 工艺及工时编排 ─────────────────────────────────────────────┐
│  [编排] [工艺卡]       产品：YUJ-18BZ ▾     [打印] [导出]    │
├──────────────────────┬──────────────────────────────────────┤
│ ▾ YUJ-18BZ (46 件)   │  ① 层级汇总表（缩进树 + 小计 + 累计） │
│   ▾ 01 整机装配 ✓发布 │  ─────────────────────────────────   │
│     ▸ 01-01 机架 草稿 │  ② 卡片区：一页一卡（A4 宽）          │
│     ▸ 01-02 料仓 ✓发布│     选产品=整册，选件名=单卡           │
│     ▸ 01-03 刀具 草稿 │                                     │
```

- 树上的状态点：草稿灰 / 已确认蓝 / 已发布绿 —— 与组合台账同一套颜色。
- 打印用 `@media print`（隐藏侧栏与按钮，一页一卡），**不引入 PDF 依赖**。
- 导出 Excel 放 P2（复用现有 xlsx 能力），先把打印跑顺。

```
# 组合（新增，都写在 app/api/combos.py）
```

前端不再自己算层级与汇总（现在树是前端自己拼的，多级之后拼不动了）。

## 八、迁移与兼容

### 8.1 一次性迁移 `scripts/migrate_combo_state.py`

1. 建表 `work_combo`（走 `db.py` 的加列/建表逻辑）。

### 12.5 停用 = 归档（2026-11-04 修）

**现象**：台账里点「停用」后，状态列还是「草稿 / 已发布」，看不出这条组合已经下架。

**根因**：`set_active()` 只翻历史工时行 `standard_hour.active`，而台账「状态」列读的是
`work_combo.status` —— 两个字段，停用只改了其中一个。更麻烦的是它不止是显示问题：
组合仍停在 `released`，于是 `released_index()` 照样收它，识别能匹配、任务能挂线、
工艺卡照样印得出来，等于「停用」这件事只做了一半。

**改法**：停用落到组合状态上，启用按路线状态回到原档。

| 动作 | 组合状态 | 路线 | 说明 |
|---|---|---|---|
| 停用 | `draft`/`released` → `archived` | 不动（保持 released） | 停用是「下架」不是「撤回」。已挂在在制任务上的引用不该因为停用失去基准 |
| 启用 | `archived` → `released`（route_id 那版仍是 released）<br>`archived` → `draft`（路线已被撤/归档） | 不动 | 不另存 `prev_status`：路线状态才是权威，停用期间有人撤了工艺，启用不会把它悄悄抹回去 |

**顺带堵掉的四个口子**（每一个都是「停用了还能用」）：

1. `pick_baseline()`：归档组合不再返回已发布基线 —— 否则任务照样挂得上；
2. `tasks.add_routes()`：先查组合，归档直接拒绝。**必须先拦**，否则 `pick_baseline`
   返回 None 会掉进 `create_baseline` 兜底，给它现造一条已发布路线，比不做闸更糟；
3. `routes.publish()`：归档组合不能再产出新的已发布版本，否则库里多一条没人认领的
   已发布路线（索引不收、编排页却显示已发布）；
4. `routes.restore(to='released')`：同上；
5. `_sync_combo()`：归档组合不因路线动作复活 —— 在编排页随手发布一版，不能等于
   静默撤销别人做的下架。

**台账口径**：`active` 字段改为 `status != 'archived'`（原来从历史工时行反推，所以停用后
按钮和筛选都不跟着变），另留 `history_active` 表示历史工时行是否在用。
摘要条增加「已归档（停用）」；工艺卡页增加「已停用」并说明「要印先在台账启用」。

**数据对齐**：`scripts/align_disabled_combo.py`（默认预演）处理历史残留 ——
判据是「该组合有历史工时行、且每一行都被停用、组合却不是归档」。生产库命中 1 条
（`（空产品）× 出条板`），已对齐为归档。挂着已发布路线的默认跳过，要人工确认。

**回归**：`scripts/test_combo_archive.py` 37 项（状态变归档 / 停用不撤线 / 四个闸门 /
挂线被拒且不偷造基线 / 启用回原档 / 重复停用不刷审计）。
全量 `run_tests.py`：**22 个脚本 / 0 失败 / 190s / 生产库未被写入**。

**顺带的两个界面修正**：台账操作列 188px → 262px（四个按钮原来挤成两行，
「编排」快被裁掉）；筛选条件写进地址栏（`#/combos?state=archived&q=板钳`），
「已归档」这类视图可以直接发给同事。

### 12.6 工艺卡 = 加工路线单（2026-11-04 纠正）

**我一开始做错了**：给工艺卡自造了一套 HTML 表格（工序/工种/设备/准备工时/关键/SOP
一列列排得很漂亮），等于凭空多出一个「工艺卡」概念。但车间手上那张纸印的是
《加工路线单》，两套东西对不上：卡上写「准备工时」，纸上没这一栏；纸上要填
「加工结果」，卡上又没地方写。**工艺卡不是新东西，它就是加工路线单。**

**现在的关系**：

```
编排好、还没干活  →  印出来的是工艺卡：工序与定额预印，操作者/结果/检查员留白
干完活、录进系统  →  同一张纸变成加工路线单（sheet + work_item）
```

版式只有一份：`app/render/route_form.py`（毫米坐标的 A4 横向真源）。
`/api/sheets/{id}/print.pdf`（已识别的单）与 `/api/cards/print.pdf`（工艺卡）
调的是同一个渲染器，区别只在喂给它的数据：一个来自识别结果，一个来自工艺编排。

**版面格怎么填**（`app/services/card_print.py`）：

| 版面格 | 预印什么 | 为什么 |
|---|---|---|
| 计调员 / 材料员 | **留空** | 纸上签名的人得是真人。库里只有 admin/operator 这类系统账号，印上去等于替人签名 |
| 产品批号 | 任务批次 | 一张卡要能独立看出属于哪批活 |
| 件号 ×2 | `01 整机装配` / 件名 | 第一格带层级编号，装订顺序一眼可见 |
| 类别 ×2 | 总装·部件·子件 / `装在 01` | **上下级关系落到纸上就靠这两格** |
| 投产台数 | 任务数量 | 没挂任务时留空（印 0 会被当成零台） |
| 加工件数 | 本单件名数量，否则台数×用量 | 子件要印真实件数，否则定额合计对不上 |
| 工序等级 | 工序名（关键工序加 ★） | 65mm 是全表最宽的栏，工序写这里 |
| 数量 | 留空 | 原单现场这栏基本不填 |
| 定额工时 单件 | 编排单件定额 | `2ʰ / 30' / 1ʰ30'` 手写体 |
| 定额工时 合计 | 单件 × 加工件数 | 按本批件数算，不是按 1 台 |
| 操作者 / 加工结果 / 检查员 / 日期 | **留白** | 车间要填的，预印就是编数据 |
| 备注 | 外协 / 检验标记 | 只有 13mm，写不了作业要求全文 |
| 小计 | 定额合计（含准备工时） | |
| 计划调度 | 发布人 | 谁认的这版工艺 |

作业要求（sop）版面上没有位置，不进卡面，在纸外的卡片说明里看 ——
不为一句话去改车间现行表格。

**三条业务关联**（用户点名的）：

1. **生产任务**：新增「按生产任务」视角。表头印投产台数、产品批号，
   定额合计按本单件数算；任务上挂了件名却没有已发布工艺的，进 `missing`
   并写清「工艺未发布（状态：草稿）」，而不是让人数一数发现少一张。
2. **工艺编排**：卡的工序与定额来自组合当前生效的**已发布**路线；改工艺去编排页，
   卡跟着变，不存在「卡上写一套、库里另一套」。
3. **上下级**：编号 `01 → 01-01 → 01-01-01` 印在件号格，类别格写层级 + `装在 01`；
   有下级的卡在页面说明里提示「下级 N 件要先做完」。

**顺带接上的第四个关联**：同一个「产品×件名」如果已经有加工路线单录进来，
卡片上写「已录 N 张 / M 小时」并可点进那张单，左栏件名旁挂「已报 N」徽标。
工艺卡是「还没干」，单据是「干完了」，这个数让人一眼看出这张卡还需不需要下发。
材料也从最近一张单取。

- `GET /api/cards/print.png?combo_id=&page=` — 单页预览（前端 `<img>` 显示的就是它）
- `GET /api/cards/print.pdf?combo_id=` / `?product=` / `?task_id=` — 一卡一页

### 12.7 一屏一张 + 打印只出当前展示（2026-11-04）

原来的纸按容器宽度铺满（`width: 100%`）：容器一宽，A4 横向的纸就比视口还高，
打开页面只看到表头到第 8 行，表尾和「车间主任 / 计划调度 / 日期」得往下拖才看得见。
而且点左栏某个部件时默认带子件，右栏一次铺出好几张，打印就是一大叠。

**改法一：纸按「视口里还剩多高」反算宽度。**

```css
.pc-paper {
  width: var(--pc-paper-w, min(100%, calc(var(--pc-fit-h, 68vh) * 297 / 210)));
  aspect-ratio: 297 / 210;
}
```

`--pc-fit-h` 由脚本量：`innerHeight − 纸的顶边 − 16px`。三点讲究：

1. **量纸自己的顶边**，不是卡片容器的顶边 —— 纸上方还有一行说明（`.pc-meta`），
   按容器算会让纸底正好多出那一行、顶到屏幕外面去（实测多出 25px）。
2. **用文档坐标**（`rect.top + scrollY`）而不是当前滚动位置 —— 否则滚一下就重算，
   纸忽大忽小，像页面在抖。
3. **窗口变窄会让工具条换行**，纸的顶边随之下移，所以除了 `resize` 还用
   `ResizeObserver` 盯住工具条/摘要条的高度，并用两帧延迟避开「换行尚未生效」。

配套压掉几处会换行的占位：摘要条 `flex-wrap: nowrap`（窗口不够就横向滚动，
宁可数字横着找，也别把纸压小）、窄屏隐藏「打印于」与提示语、页头说明缩成一句。

另给「适应窗口 / 实际大小」开关：实际大小 = 297mm × 96dpi = 1123px，屏幕像素与
纸上毫米一一对应，要看细节时切过去（容器窄则横向滚动）。

**改法二：左栏点哪一件，右栏就只有那一张。**

`selectPart()` 现在把 `include_children` 置 false（勾「连子件一起」才打成套）。
打印/下载都跟着「当前展示」走：

- `打印` = `window.print()`，DOM 里只有当前这张纸 → 出纸也只有它
- `下载 PDF` = 只有一张时传 `combo_id`，后端 `_one_card()` 仍走整本重算（编号才连得上）

**踩到的坑**：打印时 `.pc-paper` 高度写 `210mm`，浏览器把纸底算成溢出 0.5px，
每张卡后面白送一张空白页（单卡打出 2 页）。改成 `209.5mm` 后恢复正常。

**验收**（Playwright 实测，生产库只读）：

| 场景 | 纸（宽×高） | 结论 |
|---|---|---|
| 1440×900 | 860×608，底 884 | 整张可见 |
| 1366×768 | 614×434，底 752 | 整张可见 |
| 点「刀具」 | 右栏 1 张 / 打印 1 页 | 只出当前这张 |
| 点「全部」 | 右栏 2 张 / 打印 2 页 | 打印=当前展示 |
| 实际大小 | 1123×794 | 1:1，滚动看细节 |

实拍：`data/shots/50_cards_fit.png`、`51_cards_one.png`、`52_cards_1366.png`、
`53_cards_zoom100.png`、`54_cards_1080.png`。

### 12.8 右侧改成「清单 + 明细」，打印走预览弹窗（2026-11-04 第二轮）

12.7 那版把纸直接铺在右栏。用下来不对：

- **一屏只看得见一张纸**，要判断「这套工艺有哪几件、哪件工时不对劲」得来回翻；
- 纸是给人签字的成品，不是给人读的界面 —— 在网页上把 210mm 的表压到 600px 看，
  字小到没法用；放大又只能看半张。
- 打印入口在页面顶部，点下去就出纸，**打错一叠没人拦得住**。

现在改成台账式：

```
左：部件层级（不变）        右：① 这批有哪几张单（表格，点一行选中）
                              ② 选中那张：基本信息 + 工序明细（网页表格，不是纸）
                              ③ 行上「预览打印」→ 弹窗里看整张纸 → 弹窗里点打印
```

**为什么这样更合理**：

| 场景 | 纸铺在页面上（旧） | 清单 + 明细（新） |
|---|---|---|
| 看这套工艺有几件、各自多少工时 | 一张张翻 | 一屏扫完，可排序 |
| 核对某道工序的定额 | 盯着缩小的纸看 | 表格里看，字是正常大小 |
| 打印 | 页头按钮直接出纸 | 先看整张纸，确认无误再出纸 |
| 丢了哪一张要补 | 找不到单张入口 | 行上「预览打印」/双击行 |

**明细区两块**（都从同一份 `build_cards()` 数据来，不另造）：

1. **基本信息**：件号/件名/类别/装在、产品、版本、工序数、本批件数、每台用量、
   件数口径、单件定额、准备工时、本批定额、含子件、产品单台（含占比）、下级、
   已录加工路线单（可点进去）、发布人时间、材料、备注。
2. **工序明细**：序 / 工序（关键工序 ★、疑似非工序 ?）/ 工作中心 / 准备 /
   单件定额 / 检验 / 作业要求，表尾一行**合计**。
   空列自动不显示（整张卡都没有工作中心时，这一列不占宽度）。

**打印只在预览弹窗里发起**：

- 弹窗里按 A4 横向比例缩放显示整张单（多页竖排），一屏能看完整张；
- 点「打印」时走一份打印专用副本（Teleport 到 body），`@media print` 只留它，
  页面上其它东西（含弹窗本身）都不出纸；
- 打印前等每张图 `onload` 解码完，否则纸上会是空白；
- 图片按 200dpi 渲染（150dpi 出纸小字发虚）。

**踩到的两个坑**：

1. **`row-key` + 数据里的 `children` → el-table 把清单变成树形表格**，
   「刀具」被折进「整机装配」底下藏起来，表面看是"少了一行"。
   去掉 `row-key`，选中高亮改用 `row-class-name` 自己上色。
2. **格式化函数取名 `h`** 与 Vue 的渲染函数 `h` 撞名，表格单元格渲染直接抛
   `Unhandled error during execution of render function`，整块内容白屏。
   改名 `hours()`。

**验收**（Playwright，生产库只读）：

| 项 | 结果 |
|---|---|
| 清单 | 2 行（整机装配 01 / 刀具 01-01），点行高亮切换 |
| 明细 | 3 道 / 8 道，序号 1..n，表尾合计 32h / 21.17h |
| 预览弹窗 | 纸 905×640，底 772（视口 900），整张可见；图 2338×1653（200dpi） |
| 打印 | 打印副本 1 张，`#app` 隐藏，PDF **1 页** |

### 12.9 工序明细补齐纸面列（2026-11-04 第三轮）

12.8 那版明细只有「序 / 工序 / 单件定额 / 检验」，纸面上有的**数量、准备工时、备注**
看不到，工序名那一栏还叫「工序」。工艺员在页面上核对完、印出来发现纸上多几格，就没法认。

现在列口径对着纸面走：

| 列 | 来源 | 说明 |
|---|---|---|
| 序 | 行号 | 1..n（库里 `seq` 是 10/20/30，纸上要连续） |
| 工序等级 | `process_name` | 与纸面同名列同文；★关键工序、?疑似非工序（字典外） |
| **数量** | `print_qty`（本批件数） | 纸面这一格车间不填，页面显示「这批做几件」，乘单件定额才是纸上合计 |
| 单件定额 | `unit_hours` | `2ʰ / 30' / 1h30'` 口径与纸面手写一致 |
| **准备工时** | `setup_hours` | 每批一次，原先列在有数据时才出现，现在常驻 |
| 工作中心 / 工种 | `work_center` | 有数据才出现（纸上没有这一栏） |
| 检验 | `inspect_required` | 「需检」浅底标签 / 「—」；纸上印在备注格 |
| **备注** | `op_type` + `remark` | 外协优先；「疑似非工序」是系统核对标记（工序名旁已有 ?），不当作备注显示 |
| 作业要求 | `sop` | 有数据才出现（纸面备注格只有 13mm，放不下） |

表尾：`合计（n 道 · 本批 N 件）` + 单件定额合计 + 准备工时合计，与纸面小计
（单件×件数＋准备）口径对得上。

**一个必须记住的坑**：CSS 注释我用 `-->` 收尾（应为 `*/`）。CSS 里 `/*` 没闭合会
一直吃到下一个 `*/`，结果 `.pc-steps{width:100%;table-layout:fixed}`、单元格边框、
`.pc-insp` 全部被吞掉 —— 页面看起来「表格有边框但铺不满」，实际是规则整块没生效。
排查时的判定方法：`getComputedStyle(table).tableLayout` 返回 `auto` 就说明这个规则
压根没进 CSSOM；再遍历 `document.styleSheets` 找缺失的规则即可定位注释断点。

### 12.10 工序备注印到纸上（2026-11-04 第四轮）

**现象**：页面上「备注」列有内容，点预览打印出来的纸上这一格是空的。

**根因**：`card_print.card_values()` 里 `remark` 只放了「外协 / 检验」标记，
`step.remark`（工艺员写的交代）一个字都没映射到版面。而且当时跑着的后端进程是
几天前起的（没有 `--reload`），连页面上的备注也还是旧的空值 —— 两头都不对。

**为什么不能直接塞进备注格**：纸面「备注」列只有 13.3mm（`form_spec.COLUMNS`），
4.0mm 字一行只放得下 2 个字。硬塞会压到「日期」列上，印出来两行字叠在一起。

**现在的规则**（`card_print._remark_plan`，三条路都不截断）：

| 情况 | 印在哪 |
|---|---|
| 只有标记（外协/检验） | 备注格单行，4.0mm 字（两个字刚好） |
| 备注 ≤ 4 字 | 备注格两行：上行标记、下行备注，缩到 2.6mm |
| 备注 > 4 字 | 备注格只留标记；整条备注挪到**工序等级格第二行**（3.2mm 小字，65.3mm 宽能写 19 个） |

第三种是这轮的关键取舍：整张纸只有「工序等级」这一格有 65mm 宽、下面还有一行余量。
备注挂在它自己那道工序下面，比截断成一格省略号更接近「交代」的用法。

另外「疑似非工序」这条系统核对标记不会被当作备注印出去（工序名旁已有 `?`）——
它是一段 30 字的机器提示，不是人手写的交代。

**踩到的坑**：改完代码、跑测试全绿，但页面上备注还是空的。原因是 8000 端口上那个
uvicorn 是三天前起的，模块早就缓存在内存里，`card_print`/`route_form` 的改动
只有重启才生效（启动命令没有 `--reload`）。**结论：改后端打印链路要重启服务，
否则「测试过了但页面不对」。**

实拍：`data/shots/82_print_api_60.png`（接口直接返回的整页）、
`83_page_remark.png`（页面备注列）、`84_preview_remark.png`（预览弹窗里的纸）。

### 12.11 部件层级怎么改：装在哪、点在哪儿（2026-11-04 第五轮）

**此前的状态**：层级只有迁移时按件名规则自动铺过一次，台账里连个入口都没有。
第 518 行写着「工艺员在台账里点『改层级』」，那个按钮从来没做出来 ——
`api.js` 里 `comboSetLevel` / `comboRelayout` 两个方法封装好了，但没有视图调用。
于是 43 个件全平铺在「整机装配」下，一个二级件都没有。

**现在的入口（三处，都指向同一个弹窗）**

| 在哪 | 怎么点 |
|---|---|
| 清单「层级 · 装在」列 | 整格可点：`部件 装在 整机装配`，鼠标移上去出现虚线下划线 |
| 清单操作列 | 「层级」按钮（在「改名」和「停用」之间） |
| 按产品树 | 每个件右侧「设上级」；工具条右侧另有「按件名重铺」 |

**弹窗为什么用树、不用下拉**

改层级本质是「从这台机器的装配结构里挑一个位置」。40 多个件名塞进下拉框，
选项全是孤零零的名字，「料仓水套」到底在「料仓组件」里还是和它平级，看不出来。
所以直接把整棵产品树摆出来：

```
○ 不挂任何部件（作为最上层）
▾ 整机装配            [已发布]
  ● 包板总包          [草稿]      ← 选中：蓝点 + 整行浅蓝
    主盖              [草稿]
    主轴              [草稿]
  ○ 刀具              [已发布] 当前这件   ← 灰色，点不动
```

- **选中的那一行**蓝点 + 浅蓝底 + 件名加粗；
- **自己和自己下面挂着的件**整行变灰、点不动（点它会弹「不能挂在自己的下级下面」）——
  禁选集来自后端 `blocked`，不是前端猜的；
- 每行带状态徽标，顺带能看出「要挂的上级还没发布」；
- 底部「改后位置」实时跟着变：`整机装配 › 包板总包 › 刀具`。改之前就看得见结果，
  不用保存完再回来看。
- 顺带可以改**每台用量**（用于含子件工时加权）和**排序号**（工艺卡件号按它排）。

**后端**

- 新增 `GET /api/combos/level-tree?product=&part=`：只认 `parent_id`，
  **不掺 `cluster_siblings()` 那层按件名前缀聚的虚拟分组** —— 虚拟节点库里没有，
  拿它当上级会挂到空气上。每个节点带 `blocked`；不带 `part` 时返回整棵树
  （新增组合时选上级要用）。
- `PATCH /api/combos/level` 收进服务层 `set_level()`，返回 `path` / `parent_part` /
  `affected`；补了 `AuditLog`（parent_id / level / qty_per_unit / seq 各一条）。
- **修掉一个会算歪编号的缺陷**：原来改层级只改自己那一行，下级层号不动。
  把「包板总包」从根沉到某部件下，它的子件还停在 level 2，工艺卡编号会算错。
  现在 `relevel_subtree()` 整支重算，返回 `affected` 告诉人「几个下级跟着调了」。
- 「提到最上层」原来写成 `level = 1`（部件），与库里「根 = 0」不一致，改成 0。
- 台账清单多带 `parent_part` / `qty_per_unit` / `seq`：前端跨页拿不到 id→件名，
  不能让它在浏览器里猜。

**一个必须先说清的坑**：弹窗里**不显示件号**（01-01 那种）。台账的层级是全量的，
工艺卡的编号只按「已发布且链上连续」编 —— 两个口径不一样。在弹窗里显示一个
01-05、印出来却是 01-01，比不显示更糟。件号以工艺卡为准。

**验收**

- `scripts/test_combo_level.py` 45 项全过（禁选集、改层级、整支下沉、成环/跨产品
  /不存在四种拒绝、重铺不冲人工、审计留痕）。
- Playwright：清单列显示「部件 装在 整机装配」；弹窗 43 个节点、1 个禁选（刀具自己）；
  点「包板总包」→ 改后位置变成 `整机装配 › 包板总包 › 刀具`；点灰掉的「刀具」→
  提示「不能挂在它自己下面」；保存请求体 `{parent_part:"包板总包",qty_per_unit:2}`，
  提示「已挂到「包板总包」下（整机装配 › 包板总包 › 刀具）」并关窗。保存链路用
  路由拦截验证，**没有往生产库写**。
- 实拍：`data/shots/90_level_list.png`、`91_level_dialog.png`、`92_level_picked.png`、

### 12.12 改层级换成方向键（2026-11-04 第六轮，**取代 12.11 的弹窗**）

**为什么换**：12.11 的弹窗是「打开 → 在树里找目标 → 点一行 → 保存」四步。
一件一回来，43 个件就是 43 次；人的注意力在「弹窗—树—保存」之间来回跳，
改到第 10 件就烦了。改层级真正的动作只有一句「往上/往下/往外挪一格」，
这正好是按键的形状。

**现在的操作**：`工时组合 → 按产品树`，点中一件，然后

| 键 | 动作 | 落点规则 |
|---|---|---|
| `←` | 退一级 | 挂到当前父的父下，序号取「原父 + 1」，紧跟原父之后 |
| `→` | 进一级 | 挂到**上面那个同级兄弟**下，序号排在它已有子件之后 |
| `↑` | 上移 | 和上一个兄弟交换序号，父子关系不动 |
| `↓` | 下移 | 和下一个兄弟交换序号 |

按下即入库，没有「保存」。行右侧另有一组 `← → ↑ ↓` 按钮，给习惯用鼠标的人；
选中态是浅蓝底 + 左侧「当前 整机装配 › 刀具 › 刀具Ф5.0 · 第 2 层 · 每台用量 1」。

**几条不能含糊的边界**（都返回 400 并说明原因，数据原样不动）：

- 同一层里第一个按 `↑` → 「已经在同一层的最前面了」；
- 已经在最上层（`parent_id` 为空）按 `←` → 「它已经在最上层了」；
- `→` 时上面没有同级兄弟 → 「上面没有同级的件，没有可以挂进去的对象」；
- 会成环、跨产品 → 沿用 `validate_level()` 的原文案。

**批量一次性归位**：工具条「按件名一键归位」。规则只有一条 —— 件名以另一个
件名开头（至少两个字）就认为装在那件里，取最长前缀：

```
刀具Ф5.0      → 刀具        ✓ 前缀
刀具去刺打花   → 刀具        ✓ 前缀
```

### 12.13 「怎么保存」的答复：不保存，但要看得见、退得回（2026-11-04 第七轮）

**问题**：用户问「用箭头调整顺序和层级后，如何保存呢？」

**答案：不用保存。** 方向键每次按下就 `POST /api/combos/move`，服务层算落点、
写 `work_combo`、写 `audit_log`、`commit`，一步一个事务。刷新页面、换台电脑看，
改完的位置都在。没有「暂存 → 保存」这个中间态，也就不存在「改了没存」的风险。

**真正的问题在界面上，不在数据上。** 原来只有一条 1.2 秒的 toast，飘过去就没了；
人看不到「这些都是在库里的」，自然会去找保存按钮。所以这轮补的是**回执**：

- 「当前」那一行右侧常驻一个绿色回执：`✓ 已保存 18:04:04 ·「刀具Ф5.0」已挂到「刀具」下`。
  存的过程中显示灰的「保存中…」，回来后变绿。这行跟着树一起滚不走。
- 回执旁边就是「撤销」（Ctrl+Z 等价）。栈里最多留 20 步，连按连撤，后进先出。
- 提示条改成直说：**「按下就已经存进库了，没有『保存』按钮」**，后面紧跟「按错了 Ctrl+Z 撤回」。

**为什么不是「改一堆再统一保存」**：那等于把方向键的价值还回去 —— 攒着改、忘了存、
关页面丢一片。既然每步都是独立的、合法的结构变动，就没有理由挂在内存里等确认。
代价是「改错了」，所以配了撤销；撤销只覆盖「刚才手滑」，不是历史回滚。

**撤销的实现**（`POST /api/combos/undo-move`）

- `move` 的返回里带 `undo`：改动**前**的 `{id, parent_id, level, seq}` 快照。
  - `↑↓`：双方各一行；两条 `seq` 撞车触发整组重编号时，整组一起进快照 —— 只退自己会剩下半截乱序。
  - `→ ←`：一行（自己）。
- 前端把快照原样送回，后端只写 `parent_id` / `seq`，**层号不照抄快照**，
  改完统一 `relevel_product()` 重算 —— 子树可能早就不是当时那一支了。
- 前端传的是普通 JSON，所以后端会按「改后全貌」再过一道路径检查：
  两行互指（A 挂 B、B 挂 A）单看每行都合法、合起来是环，整批 400 拒绝，一行不改。
- 撤销栈只在内存里，刷新即清空。要的是「刚才按错一格」，不是十天前的历史版本。

**验收**

- `scripts/test_combo_move.py` **72 项 0 失败**，新增第 10 组：`→` 后撤销回到原位且层号复原、
  `↑` 撤销退回双方序号、撞车整组重编号后整组退回原值、不存在/指向自己/互指成环一律 400 且数据不动。

  连做两步再连撤两件都回原位。

- `derived`（60 条）：**装配单元**（整机 + 部件桶）在历史账里没有工时记录，
  按它下级全部件的合计推算 —— 整机取 总装 10% / 试机 3% / 检验 2%，
  部件取 装配 6% / 检验 1.5%。每条工序的 `remark` 写明了「按下级合计 Nh 的 x% 推算」。

**结构是怎么来的**：件名是真实的，层级是按语义分桶 + 编号变体归本体（`轴套2 → 轴套1`）
+ 少量手工指定（`刀具Ф5.0 → 刀具`）。件名语义有 6 类：电气 / 工作件 / 灌装封口 /
气液管路 / 传动 / 机架钣金，剩下的是标准件。分桶**顺序即优先级**，排错的后果很具体：
「刀轮」会被「轮」带进传动、「料仓」会被「仓」带进钣金、「风机叶轮轴」会被「轴」
带出风机组建。

**踩到的三个坑**

1. **待建清单的口径来自 `standard_hour`，不是 `work_combo`**。`combo_index()` 遍历的是
   历史工时行，所以「有组合、没路线」的件不算待建，「有工时、没路线」才算。
   第一版夹具造了组合，白造。
2. **播种脚本第一版不幂等**：`preview()` 从 `product_node` 读件名，第二次跑时把上次
   造的部件桶（「传动部件」）也当成真实件，桶套桶直接撞唯一约束。
   改成一律以 `standard_hour` 为件名真源后可以反复跑。
3. **工艺全换一遍后，单据上的旧告警成了假数据**：告警是按「当时的路线」算出来的物化值，
   路线换了不重算，界面就会「看着有告警、其实早不该报」，而且谁点一次校验就集体跳变。
   播种末尾统一重算了一遍（6 张单的告警数变化）。

**顺带修出的测试缺陷（5 个脚本）**

这批测试原来都在**扫描生产数据里的「不完整」**来给自己找目标，数据一补全就集体失效 ——
测试不该依赖生产数据恰好残缺：

| 脚本 | 原来的取数 | 改法 |

| `test_routes_api.py` | 树里捞一个 `state='none'` 的件 | 自建一条「有工时、没路线」的 standard_hour 夹具 |
| `test_routes_e2e.py` | 同上 | 同上，并核对夹具已删除（否则一直挂在覆盖看板上） |
| `test_route_batch.py` | 假设「偏移 300 处还有 50 条待建」 | 自建 60 条高价值待建项，价值给到最高让它稳定排在清单头部，`offset=0` 即可 |

### 12.17 「按生产任务」左栏变成 100 个平铺件 —— 是进程没重启（2026-11-04 第十一轮）

**现象**：工艺卡页面点「按生产任务」，左栏不是层级树，而是 100 个件平铺、编号 `01…100`。

**根因**：8000 端口跑着的 uvicorn 是「结构抽表」**之前**启动的旧进程，仍在读
`work_combo.parent_id`。这一列在 12.15 抽表后已停止读写 —— 播种重建时新行一律写进
`product_node`，`work_combo` 的层级列保持 NULL。于是旧代码看到的父件 id 全是空，
100 条卡全都成了根节点，树就摊平了。

用同一份数据在新代码里跑（`TestClient` → `/api/cards?task_id=4`）：左栏 1 个根
「整机装配」+ 6 个部件 + 93 个零件，`max_level=3`。重启后界面完全一致
（缩进 6 / 19 / 32 / 45px 四档）。

**这不是代码缺陷，但暴露了一个真实风险**：`work_combo` 的层级列现在是**死列**，
读它的代码不会报错，只会安静地把结构摊平。所以：

1. **改完后端代码必须重启**（uvicorn 没开 `--reload`）。见到「结构全平铺」先查进程版本，
   别急着改查询。
2. 后续若想彻底消除隐患，可以考虑 `DROP COLUMN` 掉 `work_combo.parent_id / level /
   qty_per_unit / seq / level_src` —— 让旧代码直接报错而不是静默降级。
   这是生产库结构变更，需单独一轮做（备份 + 双基线核对）。

**顺手修的界面瑕疵**：分享链接 `#/cards?mode=task`（地址里没有任务号）直接打开时，
页面不自动选任务 —— 下拉空着、左栏一片空白，看着像「这一单没有卡」。
改为先空跑一次请求把任务清单拿回来，自动落到第一单再加载。

**另需分清的口径**：`SJ-2栓剂` 那一单在播种时挂了 100 条 `task_route`（整个产品的所有件），
所以「本单的卡」正好 100 张，与「按产品」视图数量相同。这是**任务挂线范围**决定的，
不是树没生效 —— 若想让一单只做部分件，应在任务挂线时只选需要的件，而不是靠页面过滤。

### 12.18 工艺编排左栏显示装配层级（2026-11-04 第十二轮）

**问题**：工艺编排页左栏「产品 / 件名」看似有两级，其实**只有一级半** ——
产品下面是件名平铺，47 个件名按件名字母排序（`parts.sort(key=lambda x: x["part"])`），
整机装配、电气部件、刀具、刀具Ф5.0 混在同一个缩进层级里。
看着像「47 个平级零件」，装配关系全丢。层级那一刻只存在于「结构」按钮打开的
弹窗里，而工艺员恰恰是照着结构自上而下逐件编工艺的。

**改法（数据 → 界面一条线，排序规则只留一处）**：

| 层 | 改动 |
| --- | --- |
| `services/routes.py tree()` | 读 `product_node`，给每个件名补 `level` / `parent` / `seq`；件名改按装配顺序排（深度优先：总装 → 部件 → 它的全部子件 → 下一个部件） |
| `RouteView.vue` | 按 `parent` 还原层级行：缩进 + 竖线 + 折叠箭头；`lvl1` 部件名加粗压深 |

为什么深度优先而不是按 `level` 分桶：分桶会把「部件 A 的子件」和「部件 B 的子件」
并成一段，缩进对得上、父子关系对不上，读起来更乱。

**几个刻意的取舍**：

1. **排序只放后端**。前端只算缩进和折叠，不重排 —— 两处排序规则必然慢慢跑偏。
2. **折叠状态不落库**。它是「此刻想看多细」，不是数据；换台电脑不该跟着走。
3. **搜索/只看未建时自动全展开**。否则命中的件藏在收起的部件里，人看到的是
   「没结果」，其实是自己把它收起来了。
4. **父件被筛掉时子件当顶层显示**。搜索只命中一个孙子件时，没有父行可挂，
   硬缩进会变成一个悬空的缩进块；退成顶层至少读得懂，悬浮标题里仍写着真实父件。
5. **没登记结构的件名（只有历史工时）level 为空**，前端按顶层处理 —— 缺结构
   不等于不该出现。

**验证**（Playwright，1440/1280 两档）：YUJ-18BZ 47 件呈 整机装配 → 4 个部件 →
其子件 → 3 个孙件（刀具Ф5.0 / 刀具去刺打花 / 挡套2）；收起「工作部件」后行数
541 → 517（正好是它名下 24 件），再展开回到 541；点孙件仍能打开右侧路线
（`YUJ-18BZ / 刀具Ф5.0 已发布 v1`）。1280 视口无省略号、无换行。
