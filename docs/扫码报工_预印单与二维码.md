# 扫码报工：预印单 + 二维码

> 起因：系统建成后回头问了一句「最初设计的识别报工，是不是还有更科学的做法」。
> 结论是——识别路线本身没错，但它的**位置**错了：它应该是兜底通道，不该是主通道。

## 1. 为什么「识别」注定只能是兜底

识别是一条适配器，用来把旧世界（手写纸单）接进新系统。它的三条缺陷是结构性的，
靠把 OCR 做得更好解决不了：

| 缺陷 | 说明 |
| --- | --- |
| **凭证粒度 ≠ 核算粒度** | 一张《加工路线单》跨多件、多工序、多人，它是**随件流转的卡**，不是报工凭证。而工资的核算单位是「人 × 件 × 工序」这一行。识别要做的「切行」，本质上是在弥补「一张纸承载了多个核算单位」。 |
| **概率 vs 确定** | 识别永远有 5~10% 需人工复核。复核成本落在文员身上，错误代价落在工人工资上。 |
| **纸面工时本身不可信** | 系统本来就不用「手写合计」，而是按「合格数 × 定额」重算（`total_hours` vs `declared_total` 只做比对）。既然还要重算一遍，手写那一遍就没有入账价值。 |

判断一套报工方式是否科学，看四条：

1. 数据**产生即结构化**（不经转录）
2. 报工单位 **= 核算单位**（人 × 件 × 工序）
3. 可追溯（谁、何时、哪个工位、哪版工艺）
4. 定额与实报**可对照**

## 2. 一张纸，三个视图

这是最容易误解的地方：**加工路线单和预印单是同一张纸**，全项目仍然只有
`app/render/route_form.py` 一份版式、一份 `form_spec.COLUMNS`。

| 对象 | 回答什么 | 何时产生 |
| --- | --- | --- |
| `PrintSheet`（预印单） | 这张纸**印出去时**是什么内容 | 系统打印那一刻（快照） |
| `Sheet`（识别单） | 这张纸**填完后**被读成什么 | 拍照上传识别后 |
| `WorkItem`（报工明细） | 最终认账的工时 | 两种来源共用一张表 |

分成两个对象不是为了搞两套单据，是因为「印出去的内容」和「回来的内容」
必须能对照：**有预印快照，才能自动核对**件名/工序/定额有没有被人改过、
工艺是不是中途改版了。这是预印省下打字之外的第二个价值。

唯一身份证是 **`form_no`（印刷体单号）**，格式 `RG2611-00001`：

- 打印时生成，印在纸面上
- 识别时读到这个号 → 知道「这张纸是我们印的」，可反查预印快照
- 它同时是**两条通道的幂等键**

## 3. 流程（谁做什么）

```
系统    按任务印预印单（一个件名一张纸，右上角带码）
  ↓
工人    加工，在纸上填数量、签字
  ↓
计划员  收单 → 扫码 → 屏幕上核数（不合格/报废就地改）→ 提交
  ↓
系统    直接写 work_item（source='scan'），工时 = 合格数 × 定额
```

**扫码的是计划员，不是工人** —— 这是整套方案能不能落地的关键。
扫码报工失败的项目，多数死在「要求每个工人在工位上掏手机扫」：换机型、没网、
手上有油、一天扫二十次。而计划员本来就要收单、本来就要把纸上的数字敲进电脑，
他只是把「打字」换成「扫一下 + 改两个数」，工作量下降，抵触自然小。

## 4. 数据模型

新表：

```sql
print_sheet        -- 预印单：form_no / task_id / part_name / part_no /
                   --   route_id / route_version / qty_plan / part_qty /
                   --   token / status(printed|reported|void) / printed_by / reported_*
print_sheet_line   -- 打印那一刻的工序快照：row_no / process_name /
                   --   unit_hours / qty_plan / total_hours
```

「快照」不是冗余：纸已经发到工位了，工艺员后来改了定额，纸上的数和库里的数
就会对不上 —— 按纸上算还是按库里算，都会有人不服。所以印出去那一刻就固化。

`work_item` 的改造（**扫码报工没有纸质单据**，所以它得自己带上下文）：

| 字段 | 为什么 |
| --- | --- |
| `sheet_id` 改为可空 | 扫码报工没有照片、没有单据 |
| `source` | `ocr` / `scan` / `manual`，三种来源要能分开统计 |
| `print_form_no` | 幂等键，也是追溯纸质凭证的线索 |
| `period_id` | 没有 sheet 就没有 `sheet→period` 这条路，工资会算漏 |
| `task_id` | 归不到任务就进不了「按任务看报工」 |
| `qty_done` | 完成数量，纸面「数量」栏基本不填，以前只能由合格+返修+废品反推 |
| `reported_at` / `reported_by` | 数据真正进系统的时刻（区别于纸上的完工日期） |
| `hours_actual` | 实报工时，不参与计件工资，只用来校准定额 |
| `sign_verified` | 计划员确认「纸上操作者签字已核对」 |
| `adjust_reason` | 有报废/返修时必填 |

`sheet.print_form_no`：识别单反查预印单，两条通道互认。
**它由识别流水线写入**（`print_sheet.bind_print_form()`，见 §6.1.3）——
在此之前这个字段只有模型定义、没有任何地方赋值，「两边互认」其实只活在注释里。

### 汇总链路的改动（最容易出事的地方）

`aggregation._load_items` 原来是 `JOIN sheet`。扫码明细没有 sheet，会**一条都进不了工资表**
—— 而且不报错，只是「少算了几个人的钱」。现在改成：

```python
outerjoin(Sheet).join(Period, Period.id == coalesce(Sheet.period_id, WorkItem.period_id))
```

状态过滤也要放行无单据的行（扫码报工提交那一刻就已经核过签字，
它天然是「已入账」，不该挂在一张不存在的单上等确认）。
`export_excel._person_items` 同步改，否则工资表会出现「汇总有金额、明细一行都没有」。

#### 同一个口径散在六处，改一处不算改

`outerjoin` 这件事最初只改了工资导出，结果工资表对、**页面上全错**：

| 位置 | 症状 |
| --- | --- |
| `api/dicts.stats()`（顶栏） | 已确认工时恒为 0.0 h —— 用户以为报工没进账 |
| `services/tasks.refresh_task()` | 任务「实报工时」不含扫码，进度条不动 |
| `services/process_card._sheet_stats()` | 工艺卡「已录单据」里没有扫码单 |
| `services/routes.py`（两处） | 按任务看报工看不到扫码明细 |

加上 `aggregation` 和 `export_excel`，一共六处。**扫码明细没有 `sheet`，
任何 inner join 都会让它静默消失 —— 不报错，只是少算了几个人的钱。**

统一口径：

```python
period_of = func.coalesce(Sheet.period_id, WorkItem.period_id)
verified_cond = or_(Sheet.status == "verified", Sheet.id.is_(None))  # 无单据=天然已确认
```

以后凡是要「按核算期取报工明细」，先把这两行抄过去，再谈别的。
排序也要跟着改：`order_by(Sheet.id, ...)` 换成 `order_by(func.coalesce(Sheet.id, 0), ...)`，
否则 NULL 排在 SQLite 结果集最前，扫码明细会全部堆到表头。

## 5. 二维码：印在页面右上角

位置在 x=266mm、y=3mm，14mm 见方，表格与标题之外的空白区：

- 不压公司名（居中在 148mm）和标题，也不压表格（从 y=32mm 开始）
- 计划员翻到单子第一眼就在右上角，不用低头找
- **离表格足够远**：识别侧靠 `COLUMNS` 的列锚点还原版面，表格里多一块黑白方块，
  整张单的列就会错位。放表格外，两边互不干扰 —— 这也是「预印单照样能被 OCR 读」的前提

绘制只有一份实现：`app/render/qr_stamp.py`。
**三个出图入口共用它**：工艺卡页打印 PDF、扫码报工页打印预印单、页内预览 PNG。
各写一份的后果是改了一个忘另一个，纸上的码跑进表格里，识别侧当场列错位。

### 5.1 码里装什么：只有单号和令牌

```
HY1:RG2611-00001:0aa5c390
 │   └─ 印刷体单号（纸面上也印着，人可读）
 └───── 固定前缀，用于快速排除别的二维码（网址、设备铭牌、物料码）
            └─ token：8 位令牌，用于验真伪 + 作废
```

合计 26 个字符。**刻意不装任何业务数据**（件名、工序、定额、件数、金额），三个理由：

1. **码面容量**。14mm 见方的码在 A4 纸上按 300dpi 打印，手机/扫码枪要能一次扫中，
   经验上限约 30~40 字符（中文字符还要占更多位）。塞进一整套工序数据，
   码点会密到扫不动，而且纸张稍微歪一点就废。
2. **数据必须以库为准**。码里带定额，等于**让一张纸决定工资** —— 纸被涂改、
   被复印、被换一张，系统无从发现。码只回答「这是哪张单」，定额回后端查快照，
   查的同时顺手验状态（作废/已报工就进不来）。
3. **可作废**。纯签名能防伪造，但防不了「单子印错、零件报废不做了，纸还在工人手里」。
   token 存库，作废就把 `status` 置 `void`，纸上的码立刻失效。这是纯算法签名做不到的。

需要「离线也能看到内容」的地方，靠**纸面上的人可读信息**解决（件号、件名、
工序、定额、件数都印在表里），而不是塞进码里 —— 纸已经是最好的离线载体。

将来真要扩，能进码的只有**定位与校验类**信息：单号、行号、版本、校验位；
定额、件数、金额这类**算钱的数**永远不进码。

### 5.2 只印一个单码，不印行码

报工是「整单一次提交」：扫一下把这张单的所有工序都载进来，要改哪一行在屏幕上点，
比在纸上找「第 3 行那个 9mm 的小方块」快得多，纸面也干净。

`qr.line_payload()` / `qr.parse()` 仍保留行号能力：将来若要做「只补报某一行」
的硬场景，版面上加一列行码即可，解析逻辑不用改。

### 5.3 单号什么时候生成

| 入口 | 建单？ | 说明 |
| --- | --- | --- |
| 工艺卡页 → 打印 PDF（任务模式） | **是**（复用已有） | 打印才产生凭证 |
| 工艺卡页 → 页内预览 PNG（单张卡） | **是**（复用已有） | 见 §5.4 |
| 扫码报工页 → 生成/打印 | **是**（复用已有） | 与上面共用同一批单号 |
| 按产品打印（无任务） | 否 | 那是「工艺标准」，不是某批活的执行凭证 |

**必须复用而不是各建一套**：同一张纸若有两个号，扫码只认其中一个，
另外几张永远报不了工。所以三个入口都走 `print_sheet.create_from_cards()`。

### 5.4 预览即建单（单张卡）

页内预览 PNG 原来「只看不建」，结果纸上有单号、预览图里没有码 —— 现场把预览图
当成「打出来的单」，扫不了，报不了工。现在改为：**预览也用同一批单号**。
已印过的复用原号，未印过的当场建一张 `printed` 单。

两个「预览打印」入口（列表行内、选中卡详情）都是**单张卡**，没有批量预览，
所以一次预览最多新增一个号，同一张卡反复看只用一个号。

**代价要认**：翻看十张没打印，就留十个 `printed` 空号。这是「预览没码」和
「废号堆积」之间的取舍，选了前者 —— 因为扫不了码是当场卡住人，废号只是整洁问题。
真要清，需要「手工作废预印单」入口（见体检报告 M6，待定）。
若把预览改成不建单，则前端预览图上的码区域必须显式印「打印后此码生效」，
否则又会回到「预览看着有码位、纸上没有」的误解。

## 6. 防线与锁止（三道防线 + 三道锁）

### 6.1 幂等：同一批工时不能进两次账

这是整条链最危险的地方。计划员扫了码，文员又把那张纸拍照上传识别了 ——
**重复入账 = 多发一份工资**，多发出去的钱基本追不回来。

- 提交前查 `print_sheet.status`，已报工直接拒绝，并返回 `ALREADY_REPORTED`
  （前端据此给出「撤销后重报」入口，而不是一句干巴巴的报错）
- **已报工的那一件，重印时沿用原单号，绝不发新号**。发新号 = 一张纸两个码，
  两个都能扫、都能报一遍，等于重复发工资。此时 `create_from_cards` 返回
  `already_reported`，前端提示「已报工，沿用原单号」
- 同一件名混着的**重复待报工单**（都是 `printed`、一个件名）自动 `void` 掉多余的，
  否则工位上会同时存在两张都能报工的纸
- **并发抢单**：两个人同时扫同一张单，靠 `UPDATE ... WHERE status='printed'`
  原子翻状态，`rowcount != 1` 直接退出并提示「已被其他人报工，请刷新后核对」。
  先读后写在这里必然双写
- 识别侧以 `sheet.print_form_no` 反查，命中已报工的单号只告警、不重复入账

### 6.1.1 提交闸门（顺序不能乱）

`submit()` 按下面的顺序逐道拦，前面的闸门不通过就不往下走 —— 顺序错了会出现
「先报上去再告诉你不该报」：

| # | 闸门 | 结果 |
| --- | --- | --- |
| 1 | 单号不存在 / 已 `void` | 拒收 |
| 2 | 已 `reported` | 拒收 + 给撤销入口 |
| 3 | **未勾「签字已核对」** | 拒收（凭证不落地不入账） |
| 4 | **任务已结案 / 已取消** | 拒收（结案后不再产生工时） |
| 5 | 同号识别单已入账 / 待核对 | 拒收（防两条通道撞车） |
| 6 | **核算期已锁账** | 拒收；跨月只告警放行 |
| 7 | 报工日期晚于今天 | 只告警放行（补录/时区场景） |
| 8 | 逐行校验：负数、`合格+返修+废品 > 完成数` | **整单拒绝**（含完成数为 0） |
| 9 | 去向不明 / 超计划 | 告警放行 |
| 10 | 返修、报废没填调整原因 | 拒收 |

第 3、4、6 道是本轮补的。第 8 道从「提示后照收」改成「整单拒绝」：
数字对不上就入账，错的会一路走到工资表，而工资表是最不好改的地方。

### 6.1.2 锁止：进去不容易，出来更难

| 动作 | 拦截 |
| --- | --- |
| 报工提交 | 核算期 `status='locked'` → 拒收 |
| 撤销报工 | 明细落在已锁账期间 → 拒绝，提示先解锁 |
| 调工时单价 | 该月已锁账 → 拒绝 |
| 任务结案后报工 | 拒收 |

锁账的语义是「这个月的钱定了」。凡是能改变这个月金额的操作，都必须先解锁 ——
否则锁账形同虚设。

### 6.1.3 识别侧怎么认出「这张纸是我们印的」

前面所有幂等规则都建立在同一个前提上：识别能知道这张纸是哪一张。做法是
**从 OCR 文本里找印刷体单号，再去库里命中**：

```python
qr.find_form_nos(lines)   # 纸面右上角那行「RG2611-00001」，黑体 3.7mm
  → 候选列表
  → bind_print_form() 拿候选查 print_sheet
  → 命中唯一一条才算数
```

容忍的错读：`RG 2611 - 00001`、连字符被吞（`RG261100001`）、全角减号、
汉字「一」、`O/o→0`、`l/I/|→1`、`S→5`、`B→8`。**认错的代价由「必须能查到」兜住**：
读成一个不存在的号，就等于没读到，什么都不发生。

| 命中状态 | 识别侧处理 | 为什么 |
| --- | --- | --- |
| 没读到号（`none`） | 照旧入账，标「未识别到预印单号」 | 老纸、外协单、手写单都是这样，不能因为没码就拒收 |
| 读到但库里没有（`unknown`） | 照旧入账，不绑定 | 可能是别的车间的号，也可能是读错了 —— 不当真 |
| 唯一命中，`printed` | 照旧入账（待核对） | 正常路径：这张纸进来了，扫码那边会被拦住 |
| 唯一命中，`reported` | **识别单直接 `rejected`，只留档** | 已经扫码报过工，再入一次账就是重复发工资 |
| 唯一命中，`void` | 同上 | 作废的纸（被重印替换 / 手工作废）同样不能再入账 |
| 一页读到多个有效号（`ambiguous`） | 不绑、不拒，写进备注交人工 | 一页纸只能是一张单，多个号里至少一个是错的，挑错就是把钱记到别人头上 |

**为什么要实测**：这套逻辑的前提是「印出来的单号 OCR 读得出」。已用
`scripts/check_form_no_ocr.py` 在 200dpi/300dpi 的版式渲染图上实测，两次都
完整读出 `RG2611-00042`（右上角三行读数也正确）。这是渲染图（干净、正射），
现场照片会歪会暗，所以绑定**只做「命中才认」**，读不到就保持原状 ——
宁可漏一次互认，也不能认错一张纸。

端到端另有一份验证：`scripts/verify_m1_e2e.py`，在库副本上真的走一遍
「渲染带码的纸 → 造一张已报工的预印单 → 送进识别流水线（真 OCR）」，
断言识别单落成 `rejected`、单号写进去了、原因写清楚了；再把这张单改回
`printed` 重识别一次，断言它正常回到待核对，且绑定关系没丢。

### 6.1.4 纠错：撤销要写原因，作废只能对未报工的单

| 动作 | 前置 | 必须 | 结果 |
| --- | --- | --- | --- |
| 撤销报工 | `status=reported` 且不在锁账月份 | 原因 ≥2 字 | 删明细、退回 `printed`；审计记「原 n 行 / x 小时 → 原因」 |
| 作废预印单 | `status=printed`（已报工先撤销） | 原因 ≥2 字 | `status=void`，纸上的码立刻失效；审计留痕 |

作废这个入口不是可有可无的：零件报废不做了、单子印错件名，那张纸还在工人手里。
没有它，这张单会永远停在「待报工」—— 每次「打印全部待报工单」都被重新印出来，
月底对账还得有人一条条确认「这些是真没干还是漏了」。

### 6.2 工时必须归到人

没有人认领的工时算不出工资，只会以「未匹配」留在汇总里，月底没人追。
所以：

- 操作者列做成**人员下拉**（可输入），手打名字错一个字就匹配不上
- 前端拦：有数量的行必须选操作者
- 后端仍允许写入，但返回明确告警（历史补录场景需要）
- **放宽匹配口径**：`print_sheet.worker_index()` 把「姓名 / 别名（`worker.aliases`
  逗号分隔）/ 工号」都建进索引。纸上写「张师傅」「张」而系统叫「张三」，
  以前直接掉进未匹配；现在能认。别名比模糊匹配安全 —— 模糊匹配会认错人，
  认错人比没认出来更糟（钱付给了别人）

### 6.3 核算期兜底不能静默

报工日期所属月份没有核算期时，会退回「最近一个未锁定期间」。这个兜底是必要的
（月初还没建新期，不能让人卡住），但绝不能悄悄发生 —— 12 月的活记到 11 月，
两个月工资都是错的。所以退回时返回告警写明记到了哪个月。

## 8. 界面

「扫码报工」页（`/report`）：

- 顶部扫码框常驻并自动聚焦（扫码枪打完回车即触发），也可手输单号
- 单头卡片：单号 / 产品 / 件号件名 / 投产台数 / 加工件数 / 定额合计 / 打印人
- 表格一行一道工序：定额、计划件数、完成数、合格、返修、废品、操作者、检验员、
  调整原因、**核定工时实时算**
- 底部：签字核对勾选（不勾不能提交）、报工日期、合计、提交
- 「打印预印单」弹窗：选任务 → 生成 → 打印 PDF
- 「最近单据」：状态、打印/报工时间；**待报工的可作废、已报工的可撤销**（都要填原因）

「报工台账」页（`/sheets`）有来源页签：

| 页签 | 主键 | 能做什么 |
| --- | --- | --- |
| 识别单据 | `Sheet` | 核对、确认、改挂任务、作废/恢复、打印 |
| 扫码报工 | `PrintSheet` | **只读**：看单号、件数、行数、实报工时、状态；点「明细」看纸上工序与实际报工明细 |

扫码一侧刻意只读：能改数的地方（完成数、签字核对）在扫码报工页，台账不该给
第二个改数的入口 —— 两个入口改同一笔工时，出事时谁都说不清是哪儿改的。

未报工的单在「工时」列显示的是**纸上定额合计**（悬停有说明），不是实报工时。

### 8.1 扫完码：完成数与合格数按计划带入

现场反馈的第一条就是「扫完还要一行行敲数量」。全合格是常态，所以：

- 扫码载入后，**每行 `完成数 = 合格数 = 计划件数`**，直接进入「只需确认」的状态
- 顶部提示条三个一键操作：**统一操作者**（一单多为一人干完）、**全部按计划**、**全部清零**
- 有返修/报废的行，改完小数字后**必须点「复核」**才算认过 —— 系统不会替人决定
  「这个 3 到底是返修还是废品」，这是钱的事
- 提交前前端再拦一次：未复核的行、`合格+返修+废品 > 完成数` 的行，都不许提交

这跟第 6.1.1 节第 8 道闸门是同一个判断的两处实现：前端拦是为了不让白填一遍，
后端拦是因为前端可以被绕过。

### 8.2 报工日期必须是本地日期

原实现用 `toISOString().slice(0, 10)`，那是 UTC 日期。**每月 1 号早上 8 点前
报的上月活，会被记成上月最后一天**（东八区差 8 小时），核算期直接错。
现改为本地日期。这类 bug 每月只在窗口期出现几小时，最难被发现，也最伤。

### 8.3 列宽

新增「调整原因 / 复核」列后表格超宽、出现横向滚动。已把各列收紧到刚好放得下
（工序 108、定额 70、计划 68、完成 88、合格 82、返修/废品 70、操作者 118、
检验员 84、原因/复核 146、核定 82）—— 报工时横向滚动比字小更难受。

## 9. 边界（明确不做）

- **不做工人自助 App**：工人只需要在纸上签字。多一个按钮少一分使用率。
- **不做摄像头扫码**（本轮）：计划员用扫码枪或手输单号；手机扫需要额外依赖，
  等现场确认再上。
- **不做派工**：`print_sheet_line.worker_name` 预留了预派工字段，但现在为空 ——
  谁干哪道活仍以纸上签字为准。
- **返修不另开报工行**：返修数只记在当行，返修工时按 `REWORK_FACTOR`（默认 0）折算。
  要做「返修再报一次工」需要独立单据，那是另一套流程。

只能重建表（按 ORM 模型生成 DDL → 搬数据 → 换名 → 重建索引），带库文件备份与自检。
生产库 18 行明细迁移后行数、工时合计一致。

> 写测试时踩过的坑：给 `submit` 加「未来日期拒绝」会挡住测试里用的 `2099-02-15`，
> 补录场景本身也合法 —— 所以未来日期**只告警不阻断**，测试断言也要相应放宽。
> 断言里写死亡日期（2099）看着稳，实际是在替业务做决定。
>
> 第二个坑：测试造的单号一直用 `ZZQR-F001` 这种测试名，M1 上线后一条都匹配不上，
> 因为识别侧只认 `RG` 前缀。**测试数据的形式必须和真实数据一致**，
> 否则测的是「假系统里的真逻辑」，一上线就现原形。
