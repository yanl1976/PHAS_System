# 系统角色 / 岗位角色 / 岗位职能：三层不是一回事

写这篇的原因：系统管理页里一度有两个都叫「角色」的东西，一个改完账号权限变、
一个改完工时归属变，但界面上没有任何说明，看的人只能猜。后来又要回答第三个问题——
**「生产任务编制、工艺卡编制、计划员报工，凭什么让这个人做？」** 于是多出第三层。

现在三层分开命名、分开入口、分开存储，且服务端真的拦。

## 一、三层各答一个问题

| | **系统角色** | **岗位角色** | **岗位职能** |
| --- | --- | --- | --- |
| 回答什么 | 这个账号**能走到哪一步** | 这个人在车间**是什么身份** | 这个岗位**能承担哪几件功能** |
| 存在哪 | `app_user.role` | `role` 表 + `worker_role` | `role.duties` |
| 取值 | 管理员 / 录入核对 / 只读 | 工作者 / 检验员 / 计划员（可自定义） | 任务编制 / 工艺卡编制 / 报工 / 工时单价 |
| 在哪儿改 | 系统管理 → **账号** | 系统管理 → **岗位角色** | 同左（岗位角色弹窗里勾选） |
| 谁需要 | 只有**用系统的人**有 | 名册里**每个人**都有 | 需要有账号才生效 |

一句话：**系统角色定上限，岗位职能定边界，岗位角色定身份。**

三者不互相推导，也不互相引用：

- 一个人可以是检验员，但**根本没有账号** —— 他不录单，只是单据上签名。
- 一个账号可以是只读，对应的人却是老师傅 —— 他只是进来看台账。
- 兼岗很常见（同一人既排产又编工艺），两个岗位都挂上，**职能取并集**。

所以 `app_user` 上**没有 `role_id`**，只有 `role`（系统角色字符串）和 `worker_id`
（指向名册那个人，可空）。测试里专门断言了这一点。

## 二、系统角色（权限上限）

唯一真源：`app/domain/sys_roles.py`。界面上的矩阵直接渲染这个接口的返回，
不另写一份说明 —— 那种说明迟早和服务端实际拦截对不上。

| 能力 | 管理员 admin | 录入核对 editor | 只读 viewer |
| --- | :-: | :-: | :-: |
| 查看页面与数据 | ✓ | ✓ | ✓ |
| 写操作总闸（只读账号由服务端直接拒绝） | ✓ | ✓ | — |
| 基础数据（件名 / 工序 / 材料 / 产品 / 人员 / 岗位角色） | ✓ | ✓ | — |
| 账号管理 | ✓ | — | — |
| 备份与恢复 | ✓ | — | — |

**为什么 editor 能改基础数据**：新件名、新工序出现时，计划员得当场能加，
否则识别对不上就得停下来找管理员。权限正确但活干不下去的设计，没人会用。
基础数据刻意**不按岗位授权**，理由同上。

**为什么只读只有 `read`**：它的价值就在于「一定改不了」。界面上按钮变灰不算数，
服务端必须真的拦（见第五节）。

## 三、岗位职能（具体授权）

只有这四件事按岗位授权，因为它们直接决定「谁能让系统里产生或改变生产数据」：

| 职能码 | 名称 | 管住哪些接口 |
| --- | --- | --- |
| `task_plan` | 生产任务编制 | `/api/tasks/*` 写操作：建任务、改任务、挂工艺路线、确认版本 |
| `route_edit` | 工艺卡编制 | `/api/routes/*`、`/api/combos/*` 写操作：建改路线、编工时、发布作废、工时组合与产品结构 |
| `report` | 报工（录单 / 核对 / 扫码） | `/api/sheets/*`、`/api/report/*` 写操作：改单、核对、扫码报工、生成预印单、补录维度 |
| `wage_rate` | 工时单价与工资核算 | `/api/wages/rates`：定单价、生成与导出工资表 |

### 判定顺序（`app/api/auth.py: require_perm`）

```
1. 管理员              → 直接放行（运维身份，不该因没挂岗位就做不了事）
2. 职能类权限           → 看这个人的岗位职能并集
3. 其它权限             → 看系统角色（查看 / 基础数据 / 账号 / 备份）
```

第 2 步排在系统角色之前是**故意的**：editor 本身没有「工时单价」这条硬能力，
但管理员可以给「核算员」岗位勾上，由岗位授予 —— 这就是「按岗位授权」的含义。
反过来，viewer 的默认职能集是空的，岗位勾得再多也进不到第 2 步。

### 「没配职能」不锁人

`DEFAULT_DUTIES_BY_ROLE` 决定兜底：

| 系统角色 | 岗位没配职能时默认拿到 |
| --- | --- |
| 管理员 | 四项全有（且不受岗位影响） |
| 录入核对 | 任务编制 + 工艺卡编制 + 报工（**不含**工时单价，与改造前一致） |
| 只读 | 无 |

**一旦该人的任一岗位勾了职能，就严格按并集判定**，没勾的那项立刻失效。
这条规则是为了两头都不出事：

- 不设兜底 → 所有历史账号会在升级当天突然什么都干不了；
- 只做兜底不收紧 → 「必须由专用岗位执行」永远落不了地。

所以口径是：**配了就严格，没配就沿用旧的粗粒度权限**。界面上把这句话写在
岗位角色弹窗和账号弹窗里，并给「未配职能」的岗位标黄提示。

### 一人多岗

`worker_role` 本来就是多对多，一个人挂几个岗位就取并集：

```
张三是「计划员（任务编制 + 报工）」+「工艺员（工艺卡编制）」
  → 有效职能 = {task_plan, report, route_edit}
```

权限是并集，**不是覆盖**，也不是"最大公约数"。测试里专门断言了「加了工艺岗之后
原来的任务编制职能没被顶掉」。

挂着一个「材料员」这种没配职能的岗位，不会把并集变成"没配"—— 只有勾了职能的
岗位才参与授权。

## 四、只读是**真的**拦，不是把按钮变灰

实现位置：`app/main.py` 的 `auth_middleware`。

```
写请求（POST/PUT/PATCH/DELETE）带令牌
  → 查账号是否有效（active + token_epoch）
  → 查系统角色是否含 business 权限
  → 不含：直接 403 {code: "READ_ONLY", message: "..."}
```

三个要点：

1. **拦在进 handler 之前**：业务函数一行都不会执行，"先写了一半再报错"不存在。
2. **唯一例外是 `/api/auth/password`**：只读账号必须能改自己密码，否则密码过期就死锁。
3. **提示说人话**：不是「无权限」，而是
   「当前账号的系统角色是「只读」，只能查看，不能修改数据。需要录入或核对时，请让管理员调整系统角色。」

职能不够时的 403 是另一套文案（`duty_deny_message`），因为**该找的地方不一样**：

> 「生产任务编制」是岗位职能，当前账号（系统角色「录入核对」，岗位：材料员）的岗位上
> 没有勾选这一项。请让管理员在「系统管理 → 岗位角色」里给对应岗位勾上「生产任务编制」，
> 或把你调整到能承担这项工作的岗位。

系统角色不够要去改账号，职能不够要去给岗位勾职能 —— 只说「无权限」会让人白跑一趟。

## 五、账号可以挂到名册里的人

`app_user.worker_id`（可空）。作用只有一个：回答「这个账号是谁」，
并**由他挂的岗位决定有效职能**。

- 可空：纯管理账号不对应车间任何人。
- 挂上之后，账号列表并列显示**岗位角色**和**有效职能**，来源标记三档：
  `admin`（管理员全给）/ `position`（岗位授予）/ `default`（岗位没配，按系统角色）。
- 人员停用/被删：账号照常可用，界面上标「人员已停用」「名册里已找不到」，不静默显示成空。

接口字段（`GET /api/auth/users` 每项）：

```json
{
  "role": "editor",                 // 系统角色（上限）
  "role_name": "录入核对",
  "worker_id": 12,
  "worker_name": "陈永安",
  "positions": ["计划员", "工艺员"],   // 岗位角色名
  "position_kinds": ["other", "other"],
  "duties": ["task_plan", "route_edit", "report"],  // 有效职能（并集）
  "duty_names": ["生产任务编制", "工艺卡编制", "报工（录单 / 核对 / 扫码）"],
  "duty_source": "position",
  "duty_configured": true,
  "worker_active": true,
  "worker_missing": false
}
```

挂一个不存在的人会被拒（400）。解绑用 `clear_worker: true` —— `worker_id: null`
在 JSON 里分不清「没传」和「要清空」。

## 六、护栏

- **唯一管理员保护**：把最后一个启用中的 admin 改成别的系统角色 → 400。
- **管理员豁免岗位限制**：admin 挂了一个只配「报工」的岗位，照样什么都能做 ——
  否则给管理员调个岗位就能把系统锁死。
- **未知角色降级只读**：库里的 `role` 被脚本改坏或是老版本遗留时，按只读处理而不是报错。
- **不传 `duties` 的 PUT 不清空**：老前端、脚本调用不会把已配的职能冲掉。
- **本机免登录仍是 admin**：单机部署下没人建第一个账号。
- **内置岗位不预填职能**：不替用户猜「计调员该不该报工」，由管理员显式勾。

## 七、代码位置

| 文件 | 职责 |
| --- | --- |
| `app/domain/sys_roles.py` | 系统角色、权限点、**岗位职能定义与默认值**、矩阵、403 文案 |
| `app/models.py` `Role` | `kind`（识别名册归类）+ `duties`（岗位职能） |
| `app/api/auth.py` | `position_duties` / `effective_duties` / `require_perm`、账号 CRUD |
| `app/api/admin.py` | 岗位角色 CRUD（含 duties）、系统管理卡片 |
| `app/api/tasks.py` `routes.py` `combos.py` `sheets.py` `report.py` `wages.py` | 各写接口上的 `require_perm(db, DUTY_*)` |
| `app/main.py` `auth_middleware` | 只读写请求 403 |
| `frontend/src/views/AdminView.vue` | 岗位角色弹窗（新增/编辑/勾职能）、账号弹窗（有效职能 + 两张对照表） |
| `frontend/src/components/WorkerDialog.vue` | 一个人挂多个岗位（多选） |

## 八、测试

```bash
.venv/Scripts/python.exe scripts/test_sys_roles.py   # 55 项：三层分离、只读拦截
.venv/Scripts/python.exe scripts/test_duties.py      # 39 项：岗位职能授权
```

`test_duties.py` 覆盖：

- 职能口径：四项、中文名、规范化（去重/丢非法值/顺序稳定）
- 岗位角色可新增 / 编辑职能；**PUT 不带 duties 不清空**
- 岗位没配职能 → 不锁人（editor 仍能建任务，但单价仍被拒）
- 配了职能 → 严格按并集（计划员建任务通过，建工艺路线 403）
- **一人多岗取并集**，且不覆盖原有职能
- 空职能岗位不把并集变成"没配"
- 只读不被岗位提权
- 管理员豁免
- 403 文案点名岗位
- 迁移：`role` 表有 `duties` 列
