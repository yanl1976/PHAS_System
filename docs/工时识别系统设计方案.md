## 一、样本分析

### 1.1 源单据：加工路线单（工时记录单）

车间现行空白表：**A4 横向**印刷表格 + 手写填表，手机拍照上传。
版式的唯一真源是 `app/ocr/form_spec.py`（毫米级坐标），`scripts/form_template.py` 用它
渲染出空白模板与自测样本，识别侧用它拟合列边界——三处共用一份数字，不会各写一套。

**表头区（印刷体，3 行 × 8 格 = 4 组「标签格 + 值格」）**

| 行 | 标签格 1 | 值 | 标签格 2 | 值 | 标签格 3 | 值 | 标签格 4 | 值 |
|---|---|---|---|---|---|---|---|---|
| 1 | 计调员 | 张喜军（手写） | 产品批号 | 河北凯诺（手写，常写客户名） | 件号 | — | 类别 | — |
| 2 | 材料员 | — | 产品代号 | GHL-2-18.5 | 件号 | —（现场常写件名，如「料包」） | 类别 | — |
| 3 | 投产台数 | — | 产品名称 | 双层炼药机 | 材料 | — | 加工件数 | — |

> 原表把「件号」「类别」各印了两遍（第 1、2 行各一格），不是笔误。第 2 格现场习惯写
> 件名，识别时若件号已有值就把第 2 格归到件名（`extract_header` 的 dup_fallback）。

**明细表体（12 列，印刷 10 行 + 小计行）**

| # | 列头 | 宽(mm) | 字段键 | 说明 |
|---|---|---|---|---|
| 1 | 序号 | 7.7 | `_idx` | 印刷 1~10，竖排两字，不入库 |
| 2 | 工序等级 | 65.3 | `process` | 手写工序名（切刀焊/包板折弯…），走工序字典+词干归并 |
| 3 | 数量 | 13.3 | `_qty` | 加工件数；「合格」列空时作件数兜底 |
| 4 | 定额工时-单件 | 19.6 | `unit_hours` | 手写，`0:45:00`/`25`/`25H`/`2.5` 多种写法 |
| 5 | 定额工时-合计 | 30.4 | `declared_total` | 应 = 单件 × 数量，只作校验，入账按计算值 |
| 6 | 操作者 | 29.6 | `worker_raw` | 手写签名 |
| 7 | 加工结果-合格 | 12.7 | `qualified_qty` | 手写数字，**这是"合格件数"** |
| 8 | 加工结果-返修 | 12.4 | `rework_qty` | 影响工时入账 |
| 9 | 加工结果-废品 | 19.5 | `scrap_qty` | 影响工时入账 |
| 10 | 检查员 | 27.1 | `inspector` | 草书签名，人员白名单可解 |
| 11 | 日期 | 16.1 | `finish_date` | 手写 `9.10`，需补年份 |
| 12 | 备注 | 13.3 | `remark` | — |

**表尾**：`小计：`（合计列印 `0:00:00`）+ `车间主任：`　`计划调度：`　`日期：`。
小计行是明细的终点——它后面全是表尾文字，识别时在小计行处截断，
否则「计划调度」会被当成明细的操作者。

> 早期样表还有「实时工时」「交接人」两列，现行标准表已取消；
> 列锚点仍保留这两个词做兼容，不会误伤标准表。


### 1.2 目标单据：车间工时核算汇总单

一个工作簿 = 一个核算期，**每人 1 个 sheet + 1 个「总工时」台账 sheet**，13 人。

个人 sheet 固定版式（第 1~3 行为标题区，第 4 行起为明细）：

```
A1: {YYYY}年{M}月份个人完成工时汇总表
A2: 姓名：{姓名}    E2: 工种：{工种}
第3行表头: 序号 | 产品名称/代号 | 批次 | 件名 | 工序 | 合格件数 | 单件工时 | 合计工时 | 完成时间 | 检验员 | 备注
第4行起: 明细行
末行:    合计行（仅 H 列有值）
```

「总工时」sheet 结构：`序号 | 人员 | 工序 | 工时`，**一人可跨多工序多行**（如王国良 车/刨、段爱国 车/磨/精磨、梁继斌 数车/磨、白小峰 线/折弯）。

### 1.3 字段映射（单据 → 汇总单）

| 汇总单列 | 来源（加工路线单） | 转换规则 |
|---|---|---|
| 产品名称/代号 | 产品名称 或 产品代号 | 优先产品名称，缺失取代号 |
| 批次 | 产品批号 | 原样 |
| 件名 | 件名（表头第 2 个「件号」格） | 原样 |
| 工序 | 工序等级 | 命中工序字典（镗/铣/立加/加工中心/车/钳/磨/精磨/数车/线切割/折弯/电工/刨…），复合工序按词干归并、原文留在 `process_raw` |
| 合格件数 | 加工结果-合格 | 整数，>0 才计入 |
| 单件工时 | 定额工时-单件 | 归一化为**小时小数** |
| 合计工时 | **计算得出** | `合格件数 × 单件工时`（不以手写合计为准，避免笔误） |
| 完成时间 | 日期 | `M.D` + 核算期年份 |
| 检验员 | 检查员 | 人员白名单比对 |
| 备注 | 备注 / 告警信息 | — |

### 1.4 数据质量实测结论（这是系统必须解决的问题，也是立项依据）

对 `9月2车间工时核算.xlsx` 全量核算后，发现 5 类系统性缺陷：

**缺陷 1：总工时表与个人明细表严重不勾稽（13/13 人全部不符）**

| 人员 | 总工时表 | 个人表明细累加 | 差异 |
|---|---|---|---|
| 陈永安 | 517.50 | 446.00 | +71.50 |
| 万庆泓 | 668.00 | 718.00 | -50.00 |
| 孙建成 | 597.33 | 619.83 | -22.50 |
| 崔建安 | 636.33 | 565.50 | +70.83 |
| 王国良 | 888.42 | 904.08 | -15.67 |
| 袁红华 | 596.58 | 173.50 | **+423.08** |
| 段小明 | 602.25 | 605.58 | -3.33 |
| 段爱国 | 668.17 | 747.58 | -79.42 |
| 宋国良 | 376.75 | 237.50 | **+139.25** |
| 孙广智 | 495.67 | 86.92 | **+408.75** |
| 白小峰 | 165.00 | 258.00 | -93.00 |
| 梁继斌 | 932.33 | 1045.00 | -112.67 |
| 马永刚 | 341.17 | 397.50 | -56.33 |

无一人对平，偏差区间 -112.67 ~ +423.08 小时。说明目前汇总靠人工转抄，无任何自动校验。

**缺陷 2：工时不规范存储导致显示错乱。**
累计工时被写成 Excel 日期时间值，超过 24 小时即溢出为 `1900-01-05`，前端显示成 `5 days, 0:00:00`；单件工时出现 `1 day, 0:00:00`、`2 days, 9:30:00`。根源是单元格用了 `h:mm:ss` 而非 `[h]:mm:ss`，且值为 datetime 而非数值。手工核对时分不清"5 天"还是"5 小时"。

**缺陷 3：单件工时有名无实（合格件数缺失）。**
大量行填写了单件工时但合格件数为空，合计工时被算成 0，实际是漏填：
袁红华 172 行中 78 行为 0（45%）、王国良 100 行中 61 行为 0（61%）、梁继斌 71 行中 32 行、马永刚 44 行中 19 行。系统应对此类行**告警**而非静默置 0。

**缺陷 4：月份与年份口径混乱。**
文件名"9月"，个人表标题分别为"2025年9月份"和"2026年9月份"混用，「总工时」sheet 标题写"2026年6月"；明细中完成时间同时存在 Excel 序列号（46290=2026-09-25、45902=2025-09-02、45925=2025-09-25）、真日期和空白三种形态。

**缺陷 5：结构不稳定。**
各 sheet 列数在 11~14 之间浮动；序号不连续（1,3,4,5…有删行残留）；段爱国合计行值为 70、孙广智为 1（明显异常）；个人表工种与总工时表工种不一致（王国良表内"铣工"/总表"车"，白小峰"线切割/刨床"/"线"）。

## 二、总体设计

### 2.1 设计原则

1. **人机协同，不追求全自动**。手写连笔签名与数字的识别率上限客观存在，系统价值在于"把 90% 的机械劳动自动化 + 剩下 10% 用最快的方式让人确认"，而非 100% 无人化。
2. **左图右单，就地核对**。核对界面必须能点字段即在原图上定位到 OCR 框，杜绝"对不上图只能凭经验猜"。
3. **可解释、可追溯**。每个字段保留：OCR 原文、置信度、来源坐标、修改人、修改时间、修改前值。
4. **计算列不入库为准，以公式重算为准**。`合计工时 = 件数 × 单件工时` 由系统重算，手写合计只作对照告警。
5. **汇总单一键生成且与现有 Excel 同构**。车间已习惯该版式，不改变使用习惯才是能落地的方案。

### 2.2 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| OCR 引擎 | PaddleOCR 3.x（PP-OCRv5 det+rec 中文模型） | 指定；CPU 可跑，单张 1~2s |
| 图像处理 | Pillow + numpy（透视变换用 opencv 可选） | 指定；EXIF 校正、增强、红笔抑制 |
| 后端 | Python 3.11 + FastAPI + Uvicorn | 与 OCR 同进程语言，异步任务简单 |
| 数据库 | SQLite（WAL）+ SQLAlchemy 2.x | 单车间数据量小（月千级），免运维；可平滑迁 PG |
| 前端 | Vue 3 + Vite + Element Plus | 与既有 quote-system 技术栈一致，团队可直接维护 |
| 导出 | openpyxl | 生成同构汇总单，`[h]:mm:ss` 格式正确 |
| 部署 | Windows 本地 + 局域网访问（`0.0.0.0:8000`） | 车间内网即可，无需服务器 |

**环境前置约束（实测）**：本机当前 `Python 3.13.14`，PaddlePaddle 无 3.13 官方 wheel。需新建 `Python 3.11/3.12` 虚拟环境（`py -3.11 -m venv .venv`），Pillow 13.0.0 已具备。

### 2.3 识别流水线（6 级）

```
上传图片
  ↓ ① 预处理 Preprocess
EXIF 方向校正 → 长边归一 2000px → 灰度/CLAHE 对比度增强
→ 红笔/红章抑制（R 通道掩膜，避免圈注干扰）→ 轻锐化
  ↓ ② 文档矫正 DocPreprocess
方向分类 + UVDoc 去弯曲（拍照透视/卷曲矫正）
  ↓ ③ 文本检测与识别 Detect/Rec
PaddleOCR 全文识别，输出 (text, box_poly, confidence)
  ↓ ④ 结构定位 Layout
锚点对齐：以印刷体关键词（工序/定额工时/工作者/合格/检查员/日期）及
表格线段（水平/垂直投影）建立网格，把每个 text 归入所属单元格
  ↓ ⑤ 字段抽取与归一 Extract/Normalize
工时解析器 / 日期解析器 / 人名白名单匹配 / 工序字典归一
  ↓ ⑥ 规则校验 Rules
合计=件数×单件、日期是否落在核算期、件数缺失告警、疑似重复单告警
  ↓
入库 status=recognized（待核对）
```

#### 关键算法细节

**A. 中国式手写表单的 OCR 精度提升手段**
1. **红色元素抑制**：红笔圈注、红色表格线是 PP-OCR 的主要误检源。用 numpy 计算 `mask = (R - max(G,B) > 40) & (R > 90)`，将该区域置白后再识别；同时**单独保留红色 mask**，用于提取"红笔圈出的姓名"这一业务信号（样本正是用红圈标注姓名）。
2. **单元格 ROI 切分**：不依赖全文重排，先用投影法定位表格线，按格切 ROI 再逐格识别。格内单行文字识别率显著高于整页识别，也天然解决"值属于哪个字段"的问题。
3. **锚点优先**：印刷体表头 OCR 置信度接近 1.0，作为坐标基准校准网格，抵消透视误差。

**B. 工时解析器（多写法归一为小时小数）**

| 输入样例 | 解析结果 |
|---|---|
| `25H` / `25h` / `25小时` | 25.0 |
| `2:30` / `2.30` | 2.5 |
| `2h30` / `2时30分` | 2.5 |
| `1 day` / `1天` | 按 `WT_HOURS_PER_DAY` 折算（默认 8h；**仅文字明写「天/日」时才折算**） |
| `2.5` / `25` | 数值直取 |

**单件工时合理性分级（2026-11 依据实测数据定稿）**

定额工时是工艺给定的标准值，**一件活可以跨多个工作日，不能用「一天几小时」封顶**。原来按 24 小时封顶会把 `25H`（真实单据写法）误判为识别错误。

实测依据（9 月真实数据 986 行）：中位数 0.67h、p75 为 1.33h、p95 为 10h、**最大 96h**；真实单据手写 `25H`，表内「天+小时」按 24h/天自洽。

| 区间 | 判定 | 说明 |
|---|---|---|
| `0 < x ≤ 8` | 正常 | 1 个工作日以内 |
| `8 < x ≤ 200` | `UNIT_HOURS_LONG` warn | 跨天件，提示「≈N 个工作日」，确认后放行 |
| `x > 200` | `UNIT_HOURS_ABNORMAL` block | 超出单人单月可用工时，几乎必然漏小数点/多认一位 |

**C. 人名识别策略：不做开放识别，做封闭集匹配**
车间人员是有限集合（13 人 + 检验员几人）。识别文本与名册做编辑距离 + 同音字/形近字映射，取 top1 且分数 > 阈值者自动填充，否则给候选下拉框由人选择。这比通用 OCR 显著更可靠。

**D. 低置信度处理分级**

| 置信度 | 处置 |
|---|---|
| ≥ 0.95 且规则通过 | 绿色，允许批量确认 |
| 0.70 ~ 0.95 | 黄色，需人工过目（仍可批量） |
| < 0.70 或规则冲突 | 红色，**禁止批量**，必须逐项确认 |

**E. 数量列单格补检（v1.2 追加，`app/ocr/cellprobe.py`）**

合格 / 返修 / 废品三列的手写值经常只有一个 `1`——孤立、细长、贴着格线的竖笔画。
DB 文本检测器把它当表格线，连候选框都不给，识别网络无从发挥作用。

实测排除过所有「调参」路径（同一张真实照片，结论可复现）：

| 尝试 | 检出 |
|---|---|
| `text_det_limit_side_len` = 960 / 1536 / 1920 | 0 |
| 叠加放宽 `det_thresh=0.15` / `box_thresh=0.3` / `unclip_ratio=2.2` | 0 |
| 换 `PP-OCRv5_server_det`（更强检测模型，单张 39s） | 0 |

因此设计为**绕开检测网络**：版面已经给出列边界与行高，直接把目标格裁下来 →
形态学去格线 → 放大 → 只走识别网络（`engine.recognize_cell`，rec-only）。
同一格实测：含表头字时误识成 `9`；按行带精确裁剪并去线后稳定输出 `1`。

四道防误报闸门（每一条都对应一次实测踩坑）：

| 闸门 | 作用 | 不设会怎样 |
|---|---|---|
| 只补「整页无文本」的格 | 已有识别结果的不动 | 覆盖正确结果 |
| 行必须已有单件工时/工作者/工序/日期 | 确认这是条真明细 | 页面底部「计划调度：张喜军」签名区被补成假明细 |
| 去线后裁剪框四边不得有墨 | 确认笔画完整 | 被切掉下半截的 `1` 读成 `7`（score 0.93） |
| 只认 `^\d{1,4}(\.\d{1,2})?$` 且 score ≥ 0.5 | 过滤噪声与 `十`、`—` 之类的伪数字 | 返修列把跨界的笔画读成 `十` |

第五道闸门「**形状兜底**」（v1.3 追加）接手第 3 条被放弃的那类格子：

| 判据 | 阈值 | 为什么 |
|---|---|---|
| 连通域数量 | 恰 1 个 | 多个＝有歧义（别的字被线切碎），不猜 |
| 高宽比 | ≥ 2.2 | 竖笔画的本质特征；表头字的横竖部件都过不了 |
| 宽 / 格宽 | ≤ 0.6 | 一个数字最多占格宽六成 |
| 纵向落在数据行核心区 | ≥ 55% | 排除完全待在表头里的印刷字 |
| 顶端伸进表头区 | `ay0 < header_bottom` | 真·压线书写；同时排掉格线残片与下一行笔迹 |
| 单独送识别 | 结果必须是 `1`，score ≥ 0.45 | 只兜「一根竖线」；其它数字带横画，常规路径本来就看得见 |
| 算术旁证 | `合计 ÷ 单件` 与 1 是否相符 | 相符提分至多 +0.2，矛盾降分但不否决 |

实现要点（都是实测撞出来的）：

- 裁剪窗口上沿取 `header_bottom - 0.15×行高`，**不能**取行带原始上沿：窗口卷进表头字后，
  纵向闭运算会把表头竖笔和手写笔画粘成一块，高宽比与覆盖率判据全部失效。
- 窗口下沿只取到行带下沿：多扩 5px 就会把下条横线卷进来，格内凭空多出一个细长连通域，
  把「恰 1 个」判据打掉。
- 手写 1 常是斜的，被格线拦腰一抹后上下两段在 x 上还错开十几像素，形态学闭运算接不上；
  改用 `_grow()` 按「纵向间隙 ≤6px、横向错开 ≤1/4 格宽」并块，每次合并后重校验形状，
  防止顺着合并链把表头字混进来。

真实单据 `e1d102461d0ed843` 实测：常规路径因 edge 检查放弃 → 形状兜底命中 `1`（score 0.56），
入库后 `qualified_qty=1`、`total_hours=25`，`QTY_MISSING` 告警消失。

开关：`WT_CELL_PROBE=0` 关闭；`WT_CELL_PROBE_CONF` 改采信阈值；`WT_CELL_PROBE_MAX` 限流。
回归工具：`scripts/verify_cell_probe.py`（擦掉一格数字、格内居中重写，验证常规补检能捞回且其余行不变）。

### 2.4 数据模型

```
worker        人员(name, alias_json, team, 默认工种, 是否检验员, 启用)
process_dict  工序字典(code, name, 工种, 是否计工时)
period        核算期(id, ym='2026-09', 起始日, 结束日, status=open/locked)
batch         导入批次(id, period_id, 来源, 备注, 创建人)
image         图片(id, batch_id, path, sha256, 原宽高, 旋转角, 上传时间)
sheet         单据(id, image_id, form_type, status, ocr_raw_json, preprocess_params,
                  header_json, verify_user, verify_at, reject_reason)
work_item     工时明细(id, sheet_id, seq, product_name, batch_no, part_name,
                  process, qualified_qty, unit_hours, total_hours,
                  finish_date, inspector, worker_id, worker_raw,
                  conf_json, flags_json, row_state=auto/edited/locked)
audit_log     审计(id, entity, entity_id, sheet_id, seq, field, old_value, new_value, user, ts)
rate          工价(可选：worker_id/工种, period_ym, 单价元/小时)
```

> `audit_log` 的字段名与取值在接口层翻成中文后再返回（`item:qualified_qty` → 「合格件数」、
> `worker_id` → 人员姓名、`verified` → 「已确认」），库里仍存原始键值，改文案不影响历史数据。
> `sheet_id` 是冗余列：明细行在「重新识别」时会被整批删掉重建、id 随之变化，
> 只按 `entity_id` 关联会让历史留痕查不出来。`seq`（明细行号）同理——行 id 每轮都变，
> 行号才是稳定的锚点，没有它第二次重新识别就找不到「上次保留的是哪一行的哪个字段」。
> 留痕同时是「重新识别保留人工值」的数据源：重新识别前从 `item:*` / `header` 记录里
> 还原人改过哪些字段，盖回新结果后再校验，避免重复识别推翻人工核对成果。
> 用户在确认框里取消勾选「保留」时写一条 `item:discard`，把此前的人工值显式作废，
> 下一次重新识别才不会又把旧值捞回来。

`flags_json` 承载告警码：`QTY_MISSING`（有单价无件数）、`TOTAL_MISMATCH`（手写合计≠计算）、`DATE_OUT_OF_PERIOD`、`UNKNOWN_WORKER`、`DUP_SUSPECT`、`UNIT_HOURS_ABNORMAL`。

### 2.5 核算规则

1. **明细入账口径**：仅 `status=verified` 的单据参与汇总；`total_hours = qualified_qty × unit_hours`。
2. **返修/废品**：默认不计工时（待确认是否按比例计）。
3. **个人月工时** = Σ 该人所有 verified 明细 total_hours，按工序分组得到多行台账。
4. **三级勾稽校验**（导出前强制）：
   `Σ明细行` == `个人 sheet 合计行` == `总工时表该人合计`，差异 > 0.5h 阻断锁定并列出差异明细。
5. **月度锁定**：`period.status=locked` 后明细只读，任何修改需走"解锁申请 + 审计留痕"。
6. **Excel 输出**：与现有版式 1:1 同构（每人 sheet + 总工时 sheet）。工时列写**数值（小时小数）**并设 `number_format='[h]:mm:ss'`，从根上消除 `5 days` 乱码；另加一列"小时数"便读。

## 七、v1.1 追加：系统管理（基础数据 = 识别兜底名册）

### 设计取舍

识别质量的瓶颈不在 OCR 引擎，而在「识别出来的字符串算不算数」。手写单上的产品代号、工序简称、
材料牌号、签名残字，形态发散但取值有限，因此全部按**封闭集**处理：OCR 只负责出候选文本，
最终值由字典裁决。字典因此从「参考数据」升级为「识别基础设施」，必须有独立的维护入口。

### 数据模型

| 表 | 内容 | 在识别中的作用 |
|---|---|---|
| `product_dict` | 产品名称/代号/规格/别名 | 表头「产品名称 / 产品代号」收敛 |
| `process_dict` | 工序名/编码/工种/别名/启用 | 明细「工序」列收敛 |
| `material_dict` | 材料/编码/规格牌号/别名 | 表头「材料」栏收敛 |
| `worker` | 姓名/工号/班组/工种/别名 | 工作者、检验员、接交人三类签名匹配 |
| `role` + `worker_role` | 角色与人员多对多 | 决定人员进入哪份名册（kind = worker/inspector/receiver） |

`worker_role.kind` 是关键设计：**角色本身可自定义，但内置角色的归类固定**。这样既能支持
「老师傅既干活又带检验」的一人多角色，又不会因为改角色名而导致历史单据匹配漂移。

### 三条口径（避免过度归一）

1. **精确命中保留原文**：单据写 `YUJ-18BZ`，字典标准名是「鱼机」，则存 `YUJ-18BZ`。
   强行归一会让核对界面与原图对不上——核对的第一诉求是「所见即原单」。只有错字（`YUJ-l8BZ`）
   才纠偏。
2. **名册为空 = 未启用该字段**：未维护接交人时不产生「接交人未匹配」告警，避免噪音淹没真问题。
3. **只有写了值但不在字典里才告警**：4 个新告警码 `UNKNOWN_PRODUCT` / `UNKNOWN_MATERIAL` /
   `UNKNOWN_INSPECTOR` / `UNKNOWN_HANDOVER`，全部 warn 级，文案直接指向「去系统管理补一条」。

### 字典回补（rematch）

字典是后补的，历史单据是先前识的，两者必然错位。因此提供
`POST /api/admin/rematch`：对未确认单据用现有原始文本重跑归一（不重跑 OCR，秒级完成），
回填字段并重算告警。这把「补一条字典」的成本从「重新拍照识别」降到「点一下」。

### 前端形态

系统管理页用卡片承载 5 个管理项（产品/工序/材料/人员/角色），点卡片弹窗设置。
卡片上直接给出「条数 / 启用数 / 未入档数 / 名册人数分布」，让「哪里还没维护」一眼可见，
而不是让用户逐项点进去找。弹窗内提供搜索、单条增改删、批量导入（Tab/逗号/竖线分隔，
支持「仅新增」与「覆盖」两种模式）。

### 验证结果

```
样张回归：4 张 / 8 行 / 人员匹配 8/8 / 告警 0（与 v1.0 一致，无退化）
真实单据：检验员「杰」→「杜文杰」由姓氏唯一兜底修正，阻断告警归零
识别名册：工作者 13 / 检验员 3 / 接交人 0 / 工序 19 / 产品 1 / 材料 4
临时库全流程：上传→识别→落库 49.25h / 0 告警，material 与 handover 字段正常落库
```

### v1.1.1 追加：字典录入的三条通道

字典必须能被车间自己维护，否则「兜底名册」永远是空的。因此每个管理项都提供三条通道：
手动新增单条（表单）、粘贴文本（临时补几条）、上传文件（把已有 Excel 台账搬进来）。

**表头自动对应**是文件导入的关键。实际操作中，用户手上的 Excel 列顺序各不相同，硬性要求
「按模板顺序」会让人先改表再导入，反而增加门槛。做法是：

1. 首行判定为表头 → 用列名（含别名，如「材料名称/材质」「规格/牌号/厚度」）映射到字段，
   列顺序任意；
2. 没有表头 → 按模板列顺序对应。

表头判定踩过一个坑：最初用「行内出现任一列名关键词」判断，结果数据行
`张三,201,2车间,车工,小张,工作者/接交人` 因为含「车间」「工作者」被整行当成表头丢掉。
现在的规则是**命中 ≥2 个不同列，且命中的单元格必须足够短（≤6 字）或与列名完全相等**——
数据行的长文本（`工作者/接交人`）不构成列名。

**别名分隔符收敛**：手写台账里别名常用 `/`、`、`、`;`，而识别端按逗号拆分。导入时统一
规范化为逗号并去重，否则「用户填了别名但识别匹配不上」这种问题极难定位。

**按名称或编码双重查重**：表里同时有「产品名称」和「产品代号」时，名称列可能是中文名而
字典主键是代号。只按名称查会重复建记录，因此查不到名称时再用编码兜底命中。

**一个隐蔽的前端坑**：`DictDialog` 原来用 `el-dialog` 的 `@open` 加载列表。从卡片切换管理项时
`:key="activeKind"` 会让组件带着 `modelValue=true` 重建，此时 `open` 事件不触发，列表永远是空的
（默认的「产品」卡片看不出问题，切到工序/材料才发现）。改为 `watch(modelValue, immediate)`。
同时把 SPA 的兜底路由修正为「`/api` 前缀未命中返回 404 JSON 而不是 index.html」——正是它把
一次错误的接口请求变成 200 空数据，让问题藏了很久。

## 八、v1.1.2 追加：从历史台账回填字典

### 起点

字典是空的，识别就无从兜底。车间手上有多年 Excel 台账（`doc/9月2车间工时核算.xlsx`，
13 个人 13 个 sheet + 总表），这是最现成的字典来源 —— 它记录的正是「这个车间真实用过哪些
产品、写过哪些工序」。

### 提取的两个坑

**表头列名可能是空单元格。** 袁红华那张表的「产品名称/代号」表头是空的，但第 2 列确实是产品。
只按列名定位会整张表漏掉。做法：先按列名匹配，匹配不到按台账固定列位兜底（产品=2、件名=4、工序=5）。

**表头行位置不统一。** 用「同一行同时含『序号』和『工序』」来判定表头，比固定行号稳。

### 归类：三种处理，不能只有一种

原始数据 96 种产品写法、81 种工序写法，其中相当一部分不是脏数据，而是**列语义本身混合**：

| 类别 | 数量 | 处理 | 理由 |
|---|---|---|---|
| 工艺工序 | 21 类（覆盖 50 种写法） | 归并为标准工序，原写法进别名 | 数字后缀是不同机台（车1/铣2），不是不同工序 |
| 件名类写法 | 29 个 | 不录工序字典 | 见下 |
| 噪声 | 5 个 | 丢弃 | 「合计」是汇总行，「工种：龙门刨」是批注串进数据区 |

**为什么件名类写法不能进工序字典。** 台账工序列既写工序（车/铣/磨），也写加工内容
（法兰、料仓、540内框、安装板1）。后者如果也当工序建档，月度「人员 × 工序」汇总会碎成
几十个只有一两条的"工序"，工时占比彻底失去意义。它们该进的是「件名」字段，不是工序字典。

脚本保留 `--include-unclassified` 开关，确有需要时以工种「加工内容」建档，但默认不开。

### 产品：只合并不可能错的

合并只做三件事：大小写（`YUJ-18Bz` → `YUJ-18BZ`）、词序颠倒（`90滚筒干燥` → `滚筒干燥90`）、
同一件名可证的错字（`移印记` 与 `移印机` 都有「输送链中间链轮轴」这一件，故合并）。

**存疑的一律不合并**，按原文独立成条并在报告里列出：`全剂`（疑为栓剂）、`双层`（疑为炼药机简称）、
`对辊`、`滚筒干燥`、`三辊`、`双制丸机`。理由是这类判断猜错后极难发现 —— 两条记录都"能用"，
只是汇总时数字对不上，而人不会去怀疑一条看起来正常的产品名。

非产品杂项剔除 7 个：零活、开车送货、装配、辅助试机、车间安装配电箱、外购拌料、材料试板。

### 顺带修掉的三个真问题

1. **字典里两条同名为「铣」的工序**（`XI` 与 `XICHUANG`），`lookup[name]` 会被后者覆盖，
   匹配到哪条取决于遍历顺序。已把 2 条历史明细改指向 `XI`，删除 `XICHUANG`，并同步 `seed.py`
   防止重置后复活。

2. **导入新建的工序插到列表最前面。** `sort_order` 默认 0，与「镗」并列后按 id 排序，
   新工序反而排第一。改为接在 `max(sort_order) + 1`。

3. **表头的「加工结果」被当成材料值。** 真实单据表头标签密集，「标签右侧最近文本」这个取值
   策略会取到相邻格**自己的栏目标签**（`material` → "加工结果"、`part_count` → "备注"）。
   原有的「值里含其他标签就切分」检查拦不住，因为「加工结果」是跨列表头（`SPAN_LABELS`），
   不在 `HEADER_LABELS` 里。新增 `HEADER_WORDS` 合集统一拦截，宁可留空让人工补。

   这个脏值还直接污染了系统管理页的「未入档值」KPI（显示 1，让人以为要补材料字典），
   说明**识别脏值和字典缺口在同一个指标上混在一起** —— 看这个数字时需要能分清是哪一类。

### 结果

```
产品字典 82 条（台账 96 种写法 → 去杂项 7、合并 6、并入现有 1）
工序字典 26 条（工艺工序 21 类 + seed 原立加/线切割/焊/配盘/送货等未在台账出现的 5 类）
未入档值 0（历史明细写法全部入档）
样张回归 4 张 / 8 行 / 人员 8/8 / 告警 0，无退化
```

## 九、v1.1.3 追加：真实单据 vs 合成样张的差距（2026-11-03）

第一张真机拍照（3072×4096，相机手写单）暴露出合成样张覆盖不到的问题：一张只有 **1 行数据**
的单据被识别成 4 行、合格件数 2 → 22、单件工时 4:10:00 → 24.17 小时、产品名称 → 「数量」。
逐条定位后确认**都不是识别模型的问题，而是版面与抽取规则缺位**：

| 现象 | 根因 | 规则 |
|---|---|---|
| 4:10:00 → 24.1667 | 表单有「数量」列，`COLUMN_ANCHORS` 里没有它，列区间从「工序」直接拉到「单件」，`数量=2` 与 `4:10:00` 并进同一格 → `24:10:00` | 新增占位列 `COLUMN_RESERVES`（数量/序号/件数）：只占 x 区间不直接入库 |
| 合格件数 2 → 22 | 「操作者」也不是锚点，`合计` 的右边界一直吃到 `合格`，签名残字「2」与合格「2」拼接 | `操作者` 映射到 `worker_raw`，签名独立成列 |
| 4 行 → 应为 1 行 | 空行、签名行、表尾「合计」行都被当成明细 | 行有效性判定：无数字无工序文字、或只剩 `declared_total` 的行一律丢弃 |
| 产品名称 → 「数量」 | 「标签右侧最近文本」取到相邻列头；同一列上下两行的值 x 相同，`产品代号` 取成上一行的 `26-1` | 改为「值左边最近的标签」并做全局最近优先配对，候选为列头/单据标题时跳过 |
| 工序 「1包板折弯」 | 序号格与工序格粘连 | 去掉行首序号 |
| 包板折弯 → 折弯 | 包含关系打分（0.9×0.85）把复合工序压成单工序 | 字典名只是原文一小段时保留原文，转「工序未入典」告警 |

结果（同一张照片重新识别）：

```
明细 4 行 → 1 行；合格件数 22 → 2；单件工时 24.1667 → 4.1667；
合计 8.33（手写 8:20:00，与 2×4:10:00 自洽）；告警 22 项 → 2 项（人员未匹配、工序未入典）
```

另外：**单据没有「日期」列时不再逐行报「日期缺失」**（有的路线单只有单件/合计两列工时，
日期由核算期决定），`validate_sheet` 现在接收版面列定义决定要不要报。

## 十、从全年工时账反哺基础数据（2026-11-03）

`doc/` 下 22 份月度个人工时表（2025-11 ~ 2026-09，286 个 sheet、16779 条明细）
是现成的「真值库」——手写单据要识别的每一个字段，这里都有一份人工核过的正确答案。
用它把字典从「靠人一条条补」变成「一次统计到位」。

### 10.1 能提取什么

| 提取项 | 数据来源 | 结果 | 改前 → 改后 |
|---|---|---|---|
| 人员名册 | sheet 名 + 表头「姓名/工种」+ 文件名车间 | 29 人（2车间 13 / 1-3车间 16） | 16 → 40（含 9 名检验员） |
| 工序字典 | 「工序」列 2603 种写法 | 归并成 51 类 | 26 → 51，覆盖 61% → 93.7% |
| 产品字典 | 「产品零部件图号」列 677 种写法 | 拆成「设备类名 + 型号」535 组 | 82 → 548，覆盖 62% → 99.8% |
| 件名字典 | 「名称/件名」列 2303 种写法 | ≥2 次的 1361 条 | 无此表 → 1361 条 |
| 单件工时标准 | (产品, 件名, 工序) 三元组 | 一致率 ≥60% 的 1279 条 | 无此表 → 1279 条 |
| 批次/客户 | 「批次」列 443 种 | 只统计不入库（26-1 这类是年份-期数） | — |

### 10.2 三个关键判断

**① 产品必须按「设备类名 + 型号」拆，不能靠编辑距离。**
`5B箱式微波` 与 `HWZ-30B箱式微波` 的字面相似度比 `5B箱式微波` 与 `HWZ-5B箱式微波`
更高——模糊匹配会把 5B 认成 30B。拆成 (箱式微波, 5B) 与 (箱式微波, 30B) 之后，
型号是**全序敏感**的字符串，必须完全相同才算同一个产品。
同理 `600滚筒筛` / `450滚筒筛`、`140B隧道微波` / `140B-5隧道微波` 都是一字之差的两个型号。

**② 工序是混合列，必须做词干归并。**
2603 种写法里，纯工序只有几十个（车/铣/焊/磨…），其余是「零件/部位 + 主工序」的复合描述
（`腔体上下端焊`、`门铰链打磨`、`包板折弯`）。归并规则：取最长词干；同长取**最靠后**
（中文是「修饰语 + 动作」，`打磨酸洗` 以酸洗收尾）。归并分值固定 0.72，明显低于精确命中，
上层据此区分「认出来的」和「归出来的」。
**归并后的原文写进 `work_item.process_raw`**，核对界面在工序下拉下方用小字露出
「原文 包板折弯」——否则对着原图找不到「折弯」两个字。

**③ 单件工时标准的键必须是三元组。**
只按 (产品, 工序) 分组时样本一致率只有 41%，加上件名后升到 75%。
同一个产品同一道工序，刀具和机架的工时能差十几倍。

### 10.3 标准工时怎么用

不是替代识别，是**校验**：识别出单件工时后拿标准值比一下，超过 2 倍（或低于 1/2）
就报 `UNIT_HOURS_DEVIATE`：「单件工时 0.75 小时，历史标准 0.25 小时（165 条样本），相差 3.0 倍」。
只提醒不拦截——改制、试制、临时加价都是真实存在的，最终仍由人判断。

### 10.4 提取脚本（可复跑）

```bash
python scripts/analysis/scan_doc.py       # doc/*.xlsx → data/doc_scan.json（结构化明细）
python scripts/analysis/extract_dicts.py  # → data/extracted/*.json（六类基本数据）
python scripts/analysis/apply_dicts.py    # 写入字典表（--dry 只预览不落库）
```

`apply_dicts.py` 只增不删、只补不覆盖：已有条目一律保留（历史单据有引用），
新产品/新工序匹配不上的才新建，已有条目只补别名和空着的工种/规格。可重复执行。

## 十一、按标准空白表重做模板（2026-11-03）

前面的合成样张是「照着印象画」的表格：列顺序、表头字段、行数都跟车间真表有出入，
于是出现了最尴尬的一种情况——**自测全过，真表全错**。这一节把模板换成车间现行的
标准空白《加工路线单》（手写内容忽略，只取版式）。

### 11.1 一份数字，三处使用

版式的唯一真源是 `app/ocr/form_spec.py`：列宽（mm）、列头文字、字段键、表头 8 格、
跨列母表头。三个使用者都 import 它，不存在「改了一处忘了另一处」：

| 使用者 | 用途 |
|---|---|
| `scripts/form_template.py` | 渲染空白模板（A4 横向，300dpi，同时出 PNG + PDF）与自测样张 |
| `scripts/make_sample.py` | 用同一渲染器出 4 张「拍照效果」样张（轻微倾斜/纸色/柔焦） |
| `app/ocr/layout.py` | 用相对列宽拟合现场照片的列边界 |

```bash
python scripts/form_template.py      # data/templates/加工路线单_空白.png + .pdf（可直接打印）
python scripts/make_sample.py        # data/samples/sample_01..04.jpg（自测样张）
python scripts/dbg_file.py data/samples/sample_02.jpg   # 单张图跑完整抽取，不写库
```

### 11.2 换模板换出来的三个真 bug

换成真表版式后，四张样张立刻暴露出三个此前被合成表遮住的缺陷：

**① 窄列吃掉了宽列。** 列边界原本取「相邻列头锚点的中点」。锚点是文字中心，
而「序号」7.7mm、「工序等级」65.3mm，两者中点落在工序等级格内部靠左——正是手写
工序名的起笔处。结果 `工序` 整列为空，序号列却宽达 200px。
改法：用标准表的相对列宽拟合（只解 `x = b + s·rel` 两个未知数，12 个列头参与最小二乘），
残差 > 1.2% 页宽说明不是这张表，自动退回中点/竖线方案。

**② 0.5° 的残差就足以让竖线检测全灭。** 纠偏原先是 0.5° 网格粗扫，残差最大 0.5°，
一千像素高的竖线横移 8px，列投影散成一团，`detect_lines` 一条竖线都检不到。
改为两段搜索（0.5° 粗扫 + 0.1° 细扫），残差降到 0.2° 以内。

**③ 表尾被当成明细。** 「小计：」后面的「车间主任／计划调度／日期」聚成了数据行，
`计划调度` 被写进明细的操作者列。现在在小计行处截断明细（`cut_at_total_row`）。

另外顺手修了两处：
- 表头第 2 个「件号」格 → 件名（`dup_fallback`），否则真表上的件名永远抽不到；
- 值行与标签行配对时按 `dy×5 + dx` 排序，避免「产品批号」抢走下一行「产品代号」的值。

## 十二、工时格复查：换表格结构识别之前，先把「认字」这一层做扎实（2026-11-03）

### 12.1 为什么不是换引擎

一度考虑过「让引擎直接输出结构化表格 JSON，省掉自己算坐标」。用 PaddleOCR 3.x 的
表格结构识别（SLANet）在两张真单据上实测：

| 单据 | 检出单元格 | 结构置信度 | 明细行归属 |
|---|---|---|---|
| 7（横向清晰） | 175 | 0.979 | 正确 |
| 6（竖版 + 右侧被裁，最难） | 133 | 0.978 | 正确 |

结构层确实稳，省掉列拟合也可行。但把同一批 OCR 文本落进这些格子，**字段值一个都没变**：
`0:45:00` 仍是 `0:48:00`、`9.10` 仍是 `9.0`、草书「杜文杰」仍是「定生」。

结论：当时 7 张单据里 6 张结构已经全对，错误 100% 发生在**字符识别**这一步。换结构引擎
解决不了认字问题，还会让表头键值区（3 行 × 8 格，SLANet 当成 `colspan` 合并格）退化。
所以先把力气放在「关键数值格的二次识别」上。评估用的两个脚本留在
`scripts/probe_table.py`（结构输出）与 `scripts/probe_cell.py`（单格对照）。

### 12.2 单格复查怎么做

对每条明细的**单价格**：裁下 → 去格线 → 放大 3 倍 → 只跑识别网络（不经检测）→ 多参数投票。

三件实测出来的事，都写进代码注释了，别凭直觉改：

1. **padding 奇偶会翻转结果。** 同一格 `pad=0/2/4` 得 `0:45:00`，`pad=1/3/5` 得 `0:48:00`。
   裁剪框差 1px，斜线残留量就不同。因此对 `pad∈{0,2,4}` × `去线/不去线` 共 6 次识别投票。
2. **去线会连带抹掉标点。** 冒号和小数点紧贴格线，被线掩膜膨胀吃掉：`2.5`→`25`、
   `0:45:00`→`04500`。所以候选的冒号/小数点形态必须与整页原文一致，否则丢弃
   （`shape_kept`），否则会把 2.5 小时改成 25 小时。
3. **不能按置信度取舍。** 错值反而更自信：`0:48:00` score 0.97，正确值 `0:45:00` score 0.93。
   于是只按业务勾稽仲裁：

| 情形 | 处理 |
|---|---|
| 整页没读到单件工时、裁格读到了 | 直接采用（补检） |
| 整页值对不上「数量×单件=手写合计」、候选值对得上 | 自动采用候选 |
| 两边都对不上、或没有合计数可对 | 保留整页值，报「工时识别分歧」，提示里带两个读法与单格原文 |

**姓名格、日期格不复查**：草书签名在这个尺度下只会读出「机生」「生」「立」；
手写 `9.10` 的「1」只有 2px 高，试遍 `pad 0~12 × 放大 2~4 × 去线与否` 全部失败。
硬做只会把噪声写进库，不如留给人工 + 告警。

### 12.3 效果与代价

| 单据 | 前 | 后 |
|---|---|---|
| 7（真照片） | 单件 0.8，无提示 | 单件 0.8 + 「工时识别分歧：整页 0.8 / 单格复查 0.75（原文 0:45:00）」 |
| 6（真照片） | 单件 4.1667 | 不变（复查结果一致，不产生噪声） |
| 1/2/3/4（合成样张） | — | 全部不变、0 提示（`2.5` 未被误改成 `25`） |
| 5（旧版式） | 4 条提示 | 不变 |

代价：每行 6 次 rec 调用（约 0.1s/次），单张多 0.6~2s；`WT_CELL_RECHECK_MAX` 默认 8 行封顶，
可用 `WT_CELL_RECHECK_CONF` / `WT_CELL_RECHECK_MAX` 调节，`WT_CELL_RECHECK_*` 关掉即回退。

自测：`scripts/test_recheck.py` 用打桩覆盖三种仲裁分支 + 标点形态校验。之所以打桩，是因为
「整页读错 + 候选读对 + 合计能勾稽」这三个条件同时成立在现有样本里碰不到，不测就永远发现
不了那条分支写错。

## 十三、签名认不准怎么办：不猜，让人一秒认出来（2026-11-03）

用户指着一张单据的检验员格说「这是杜文杰」。模型读的是「定生」，置信度 0.35。
这类字段（检验员、操作者签名）的识别上限很低：草书是个人化的连笔，笔画拓扑和人名之间
没有稳定映射，20~50 张样本也训不出可靠模型。所以这里不做"更好的识别"，做三件成本极低的事。

### 13.1 让人一眼认出来

- 核对页「检验员」从自由输入改成**名册下拉**（`allow-create` 保留手动填新名字的能力）。
- 格子里挂一张**签名缩略图**（26px），点开 Element Plus 大图预览。
  新接口 `GET /api/sheets/{sid}/items/{iid}/crop?field=inspector&pad=10&zoom=3`：
  按明细 `bbox.inspector` 从处理图裁格、灰度、放大 3 倍。
- 明细的 `bbox` 现在包含 `inspector`，所以「在原图定位」也会把签名格框出来。

### 13.2 原文与人名分开存

新增 `work_item.inspector_raw`：签名格的 OCR 原文。界面在名字下面显示「原文 定生」，
一眼能看出这是识别结果、不是人名；也是下一步学习别名的原料。

配套改了一处判定：`conf.inspector` 从「签名几笔的 OCR 置信度」改成「**人名匹配的把握**」。
签名 OCR 永远在 0.3 上下，一旦按别名认出「定生 = 杜文杰」，这个人就是确定的，
不该再挂一条「低置信度」让人重看。没认出来时给 0，由「检验员未匹配」单独提示，
避免同一个问题弹两条。

### 13.3 人工改正即记别名

`app/services/learn.py`：人工把检验员/操作者改成名册里的人时，把签名原文记成该人的别名。

```
签字原文「定生」 ──人工确认是杜文杰──▶ 杜文杰.aliases += "定生"
下次同一写法 ──match_worker 别名命中──▶ inspector = 杜文杰（score 1.0，不再告警）
```

三条克制（缺一条名册就会被灌脏）：

| 规则 | 原因 |
|---|---|
| 只在人工确认后写入 | 识别侧自己造别名，错一次就永久错下去 |
| 原文已被别人占用则不写 | 防止把甲的名字记成乙的别名 |
| 单人最多 20 条 | 手误或误改不会把名册刷满 |

留痕：`item:inspector_alias`（旧值空、新值即别名），在「修改留痕」里能看到是谁教的。

批量补历史单据（已识别错、又不想逐张点开改）：`scripts/learn_alias.py`。

```bash
python scripts/learn_alias.py 杜文杰 定生            # 只记别名
python scripts/learn_alias.py 杜文杰 定生 --sheet 7  # 记完把单据 7 重新归一（含告警重算）
python scripts/learn_alias.py 杜文杰 定生 --all --dry
```

### 13.4 实测

| 单据 | 前 | 后 |
|---|---|---|
| 7（真照片） | 检验员「定生」+ 未匹配 + 低置信度，共 5 条提示 | 检验员 **杜文杰**（原文 定生），共 3 条提示 |
| 7 重新识别一遍 | — | 仍然读成「定生」，仍正确归到杜文杰（别名命中，score 1.0） |
| 1/2/3/4/5/6 | — | 全部不变 |

签名的裁图与用户提供的那张截图逐笔一致（同一格），说明 `bbox.inspector` 定位准确。

### 13.5 为什么不再往前走一步（签名图像比对）

同一个人反复签同一个样式，理论上可以用图片相似度做模板匹配。现在没做，因为**库里只有
一份真实签名样本**，任何阈值都无法验证；一旦误配，就是把甲认成乙、工时记到别人头上。
等每个人攒到 5 份以上真实签名，再用「图片相似度只做下拉排序建议、不自动赋值」的方式引入。
