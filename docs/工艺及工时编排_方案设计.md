# 工艺及工时编排（Routing & 工时定额）方案设计

> 版本：v2.0（**已实施完成**）　编制日期：2026-11-03
> 目标系统：加工路线单工时核算系统（E:\tedri_project\hy）
> 状态：**S0~S5 全部完成，首期 80 条草稿已生成待人工确认**
>
> 已确认决策（2026-11-03）：
> - D1 **片段制**：允许只登记已知工序即发布，不作「缺工序」告警
> - D2 **维护 51 道工序的工艺默认序**（前置任务 S0）
> - D3 **引入准备工时 + 标准批量**，默认留空，不填则按纯单件工时计算
> - D4 **首期按价值取前 50~80 条**，覆盖约 80% 工时
>
> **实施结果（2026-11-03）**：
> | 步骤 | 状态 | 产出 |
> |---|---|---|
> | S0 工序默认序 | ✅ | `process_dict.default_seq`，51 道工序全部排定并留痕 |
> | S1 建表+生成算法 | ✅ | `process_route` / `process_route_step` 两表 + `services/routes.py` |
> | S2 API | ✅ | `api/routes.py` 12 个端点 |
> | S3 前端工作台 | ✅ | `RouteView.vue`，左树 + 工序表 + 覆盖看板 + 批量生成 |
> | S4 接入校验 | ✅ | 2 个告警码，**7 张单据零回归** |
> | S5 覆盖率+首期建线 | ✅ | 80 条草稿，覆盖 74.1% 工时 |
>
> **与方案的三处实测偏差**：
> 1. 告警码由 4 个减为 **2 个**（`ROUTE_MISSING` 静默、`ROUTE_STEP_MISSING` 不做）。
> 2. D4 的覆盖预估偏乐观：前 80 条实际覆盖 **74.1%**（非 80%），
>    要到 150 条才 82.7%。首期按 80 条建。
> 3. 首期 80 条**全部为草稿、0 条发布**——发布即定基准，必须人工确认后由人点。

## 一、结论先行

1. **不做通用 MES 工艺路线的全量复制。** 本厂现有 1361 个件名、801 个「产品×件名」组合，其中 **601 个组合历史上只出现过 1 道工序**、只有 47 个组合出现过 3 道以上。按教科书方式"给每个零件建一条完整工艺路线"，既建不完，建出来也大半是空的。

2. **做的是「工艺工时定额 + 有序工序片段」**：以 `(产品, 件名)` 为轴，维护一串**有顺序、有定额、有版本**的工序；能建全的建全，只有两三道的就存两三道，**允许不完整，不阻塞任何现有功能**。这比"完美路线"实用，也是能在一周内见到效果的做法。

3. **价值三段，按落地顺序**：
   - **定额**——单据上的工时对不对，从此有了厂内基准（不再只依赖历史统计的 1279 条散数据）；
   - **归集**——计划工时 vs 实际工时，按零件/工序/人三个维度可比；
   - **输出**——工艺过程卡、派工单，可打印下发到机床。

4. **越用越准的机制**：每张识别进来的加工路线单都带着真实序号（`work_item.seq`）。系统按 `(产品, 件名)` 把历次单据的工序序列合并去重，**自动建议路线补充/修正**。单据越多，路线越完整——这是本系统相对纯手工建档的结构性优势。

## 二、现状盘点（方案的事实基础）

### 2.1 已有基础数据

| 数据 | 数量 | 可用性 |
|---|---|---|
| 工序字典 `process_dict` | 51 条（含工种 `category`、别名表） | 良好，别名已覆盖「包板折弯」等现场写法 |
| 产品字典 `product_dict` | 547 条 | 良好 |
| 件名字典 `part_dict` | 1361 条 | 名称可用，**`category` 全为空** |
| 历史单件工时 `standard_hour` | 1279 条，覆盖 117 个产品、801 个组合 | 有工时，**无顺序** |
| 人员名册 `worker` | 40 人 | 良好，含工种 `default_process` |
| 已识别明细 `work_item` | 11 条 | 量太少，仅够验证机制 |
| 历史台账 `doc/*.xlsx` | 21 个月度工时表 | 原始来源，可重跑补数 |

### 2.2 三条关键缺口（决定了方案形态）

**缺口一：有工时、无顺序。**
`standard_hour` 只回答"这道工序多少小时"，不回答"这是第几道"。工艺路线最核心的信息恰恰是顺序。

**缺口二：有件名、无分类。**
`part_dict.category`（所属设备/产品族）1361 条全空。行业通用做法是"模块化路线：工序模板 + 参数表"来应对多品种小批量，而模板必须有挂载点（零件族）。缺这一层，1361 条路线只能一条条手建。

**缺口三：数据覆盖极不均衡。**

| 组合内工序数 | 组合数 | 占比 |
|---|---|---|
| 1 道 | 601 | 75.0% |
| 2 道 | 153 | 19.1% |
| 3 道 | 26 | 3.2% |
| ≥4 道 | 21 | 2.6% |

只有 21.2%（116/547）的产品有工时数据。**结论：不可能也不应该"全覆盖"，只能按价值排序分批建；且路线必须允许不完整（已确认 D1 片段制）。**

## 三、行业参照与本项目的取舍

参考国内离散制造 MES / ERP 工艺管理的通行模型（工序/工步两级结构、准备工时与单件工时分离、关键工序与检验点、路线版本管理、模块化路线模板），逐项取舍如下：

| 行业通用能力 | 本项目是否采纳 | 理由 |
|---|---|---|
| 路线 → 工序 → **工步** | **不采纳工步** | 本厂单件在分钟到小时级，工步（上料/定位/清渣）拆下去只会让录单成本翻倍，收益为负 |
| **准备工时 / 单件工时** 分离 | **采纳**（可选填） | 装夹、找正、换模的时间确实不随件数线性变化；但默认留空，避免一上手就逼人填 |
| **工作中心 / 设备**独立档案 | **降级为文本字段** | 第一版用「工种（来自工序字典）+ 设备名（自由文本）」，不建独立表；等真要排产时再升格 |
| **关键工序 / 检验要求** | **采纳** | 与现有检验员字段天然衔接，可用于"该工序必须有检验员"的校验 |
| **路线版本与状态** | **采纳（必须）** | 没有版本，改一次路线就会污染所有历史单据的比对基准 |
| **模块化路线模板** | **采纳，P1 落地** | 依赖件名分类补录，作为第二阶段；P0 先提供"复制现有路线"应急 |
| **外协 / 委外工序** | **采纳（字段级）** | 只标记 `op_type`，不做外协对账 |
| **排产 / 报工 / 工序流转（F-to-S）** | **不采纳** | 超出本系统"工时核算"的定位，属于另一个项目 |

## 四、数据模型设计

### 4.1 新表 1：`process_route`（工艺路线）

一条记录 = 某个「产品×件名」的某一版工艺路线，或一份可复用的路线模板。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int PK | |
| `kind` | str(16) | `route` 实际路线 / `template` 路线模板（P1 启用） |
| `product` | str(128) idx | 产品名称（关联 `product_dict.name`）；模板时为空 |
| `part` | str(128) idx | 件名（关联 `part_dict.name`）；产品级通用路线时可为空 |
| `title` | str(64) | 模板名 / 路线别名 |
| `version` | int | 版次，从 1 起 |
| `status` | str(16) | `draft` 草稿 / `released` 已发布 / `archived` 归档 |
| `completeness` | str(16) | `full` 完整 / `partial` 片段。**确认采用片段制**：默认 `partial`，界面标注「本路线登记了 N 道工序，不代表该零件全部工艺」，避免使用者误以为缺工序是系统漏了 |
| `batch_qty` | float | 标准批量，用于准备工时分摊 |
| `allowance_rate` | float | 宽放率（默认 0，可为 0.10），预留 |
| `source` | str(16) | `manual` 手工 / `history` 历史生成 / `template` 套模板 / `sheet` 单据学习 |
| `effective_from` / `effective_to` | date | 生效区间，可空 |
| `remark` | str(255) | |
| `created_by` / `created_at` / `updated_at` | | |

约束：`UNIQUE(product, part, version, kind)`。
规则：**同一 `(product, part, kind)` 同时只允许一条 `released`**；改已发布路线必须升版（旧版自动 `archived`，保留比对）。

### 4.2 新表 2：`process_route_step`（工序行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int PK | |
| `route_id` | int FK idx | |
| `seq` | int | 工序号，按 10/20/30 递增，便于插行不重排 |
| `process_code` / `process_name` | str | 关联 `process_dict`；显示名沿用现有"字典有的写法照原文"口径 |
| `op_type` | str(16) | `self` 自制 / `outsource` 外协 / `inspect` 检验 |
| `category` | str(32) | 工种，从工序字典带出，可覆盖 |
| `work_center` | str(64) | 设备/工位（自由文本） |
| `setup_hours` | float | 准备工时（每批） |
| `unit_hours` | float | 单件工时定额 |
| `hours_src` | str(16) | `history` 取自历史实测 / `manual` 人工 / `sheet` 单据实际 |
| `samples` | int | 生成时的样本数（用于显示可信度） |
| `is_key` | bool | 关键工序 |
| `inspect_required` | bool | 需检验 |
| `sop` | str(255) | 作业要求 / 图纸号 |
| `remark` | str(255) | |

约束：`UNIQUE(route_id, seq)`。

**不做 `prev_seq` 显式前道指针**：本厂是单线单件流转，顺序即序号；一旦引入指针，拖拽排序的维护成本远超收益。

### 4.3 字典增强（不加表，补数据）

- `part_dict.category` 补录零件族（P1 模板化的前提）。建议先补**有工时数据的 801 个组合涉及的件名**，其余按需。
- `process_dict` 增加 `default_seq`（int）：51 道工序的**工艺默认序**（下料→车/铣/镗→钳→焊→折弯→装配→试机），用于自动生成路线时排序。只需一次性维护 51 行。

### 4.4 与既有表的关系（不改结构）

```
standard_hour（实测统计，只读） ──┐
                                  ├──→ process_route（定额，主口径）
work_item（单据实际，逐张）    ──┘
```

**明确不把路线定额回写 `standard_hour`**：一个是"定额"，一个是"实测"，混在一起就再也分不清是标准错了还是现场超了。两者在界面上并列显示偏差，由人决定是否采纳。

## 五、功能设计

### P0（首期，建议 4~5 个工作日）

#### F1 路线工作台
- 左侧：产品树（547）→ 件名（1361）→ 已有路线（版本/状态徽标）；支持关键词搜索、"只看未建路线"、"只看已建"。
- 右侧：工序步骤表格，支持**拖拽排序**、插入行、复制行、删除行、一键"引用其他路线"。
- 顶部 KPI：工序数 / 单件合计 / 准备工时 / 批量分摊后单件 / 与历史实测偏差。
- 底部：工时汇总条 `单件总工时 = Σunit + Σsetup ÷ batch_qty`。

#### F2 从历史数据生成草稿（核心）
- 入口：「生成路线」按钮，按 `(产品, 件名)` 拉取 `standard_hour` 全部工序。
- 顺序推断分三档，并标注来源：
  1. 该 `(产品, 件名)` 在 `work_item` 里有真实 `seq` → **直接用真单据顺序**（最可信，`source=sheet`）；
  2. 否则按 `process_dict.default_seq` 排（工艺常识序，`source=history`）；
  3. 同序号并列时按样本数降序。
- 输出**草稿**，不自动发布；每一行带样本数徽标，样本 <3 的行标黄提示"数据薄弱"。

#### F3 发布 / 升版 / 归档
- 草稿可编辑；发布后锁定，改动须走"升版"，旧版自动归档并保留，供历史单据比对。
- 全部操作写 `audit_log`（`entity='route'`），与现有留痕一致。

#### F4 覆盖率看板
- 按价值排序的"待建清单"：`该组合的历史工时总量 × 出现次数` 高的排前面。
- 分四档展示：已发布 / 草稿 / 未建但有工时数据 / 未建且无数据。
- 一眼看出"建哪 50 条能覆盖 80% 工时"。

#### F5 接入识别校验（让路线立刻产生价值）
新增 3 个告警码（片段制，**取消「缺工序」告警**——片段本身就不完整，报缺工序等于天天误报），接入 `rules.validate_sheet(..., routes=...)`，与现有 `std_hours` 同一注入方式：

| 告警码 | 级别 | 触发条件 | 提示示例 |
|---|---|---|---|
| `ROUTE_MISSING` | 不上报 | 该零件无已发布路线 | 静默（否则新系统上线首月满屏告警） |
| `ROUTE_STEP_EXTRA` | warn | 单据工序不在路线内 | 「工艺路线中没有『刨』这道工序，可能是新工艺，也可能读错」 |
| `ROUTE_HOURS_DEVIATE` | warn | 单件工时 / 路线定额 超出 ±50% | 「定额 1.5h，本单 2.2h（+47%），请确认是否改制」 |

> 与现有 `UNIT_HOURS_DEVIATE`（对比历史统计）的区别：新码对比的是**有人签字确认过的定额**，可信度更高，因此阈值可以更严（±50% vs ±100%）。

### P1（第二阶段，建议 3~4 个工作日）

#### F6 路线模板 + 批量套用
- 按 `part_dict.category`（零件族）建模板（如「钣金件-箱体」「轴类-传动」）；
- 选一批件名 → 套用模板 → 生成草稿（工时取该件名的历史值，无则留空待填）；
- 解决"1361 件名不可能手建"的根本矛盾。

#### F7 工艺过程卡导出
- 按 `(产品, 件名)` 输出 Excel：工序号 / 工序名 / 工种 / 设备 / 准备工时 / 单件工时 / 批量工时 / 检验要求 / 备注；
- 复用 `export_excel.py` 现有 openpyxl 样式体系（宋体、细边框、灰度表头），保证与工时核算单一致。

#### F8 单据驱动路线学习
- 每次单据确认，把该 `(产品, 件名)` 的工序序列并入"路线建议池"；
- 当某零件累积 ≥3 张单据，且序列一致率 ≥80%，在覆盖率看板上提示"可据此补全路线"；
- 这是"越用越准"的落地点，也是当前 11 条明细数据的长期价值出口。

### P2（按需，暂不排期）
- F9 计划 vs 实际工时对比报表（按零件/工序/人）；
- F10 与 `rate`（工价）联动，定额工时可预算金额；
- F11 设备/工作中心独立档案 + 产能负荷视图。

```
│ 单件合计 2.58h ＋ 准备 0.5h÷批量 10 = 2.63h/件 　[保存草稿] [发布]      │
└─────────────────────────────────────────────────────────────────────┘
```

**交互要点**
- 拖拽排序用原生 HTML5 drag 或上下移按钮，**不引入新依赖**（现有前端只有 vue + element-plus）。
- 工序选择复用核对页的 `el-select filterable allow-create`，并显示「归入字典 X」的既有口径。
- 工时输入统一提供 `hms()` 换算小字（`1.75 → 1:45:00`），与核对页保持一致。

## 九、实施计划（每步可独立验收）

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| **S0** | **工序字典加 `default_seq`，51 道工序排一次工艺默认序**（前置，见 §10 D2） | 系统管理里可拖动排序并保存；生成路线时能按此排序 |
| S1 | 建表 + `services/routes.py` + 生成算法 | 对 `SJ2栓剂/主动轴` 生成草稿，工序与工时与 `standard_hour` 完全一致，顺序符合默认工艺序 |
| S2 | API（列表/详情/保存/发布/升版）+ 覆盖率 | `curl` 全通；发布后旧版自动归档；重复发布被拒 |
| S3 | 前端工作台 | 能建、能改、能拖、能发布；刷新后数据一致 |
| S4 | 接入校验（3 个告警码） | **全量重跑 7 张单，未建路线的单据结果与今天完全一致（零回归）** |
| S5 | 覆盖率看板 + 待建清单，按价值建前 50~80 条 | 输出并建完"覆盖 80% 工时"的名单 |
| P1 | 模板 + 工艺卡导出 + 单据学习 | 按需启动 |

### 首期"价值排序"的具体口径（D4）

```
value_score(产品, 件名) = Σ over 工序 [ unit_hours × samples ]
```

即该零件历史上累计投入工时的近似量。取前 50~80 条即可覆盖约 80% 工时。这一口径写在 `GET /api/routes/coverage` 里，界面上直接显示"建这 N 条可覆盖 X% 工时"。

**回归红线**：S4 完成后必须重跑 `scripts/recheck_all.py`，确认 1~7 号单据的识别结果、提示条数**逐张不变**。这是本方案唯一的硬性约束。

## 十、决策记录（已确认 2026-11-03）

| 编号 | 决策项 | 确认结论 | 对方案的影响 |
|---|---|---|---|
| D1 | 路线粒度 | **片段制** | 允许只登记已知工序即发布；取消「缺工序」告警；`completeness` 默认 `partial` 并在界面提示 |
| D2 | 工序默认序 | **现在维护** | 新增前置任务 S0：`process_dict` 加 `default_seq`，51 行一次填完，系统管理支持拖动排序 |
| D3 | 准备工时 | **引入，默认留空** | 模型保留 `setup_hours` + `batch_qty`；两者为 0 或空时按纯单件工时计算，与现行口径完全一致 |
| D4 | 首期范围 | **按价值取前 50~80 条** | 覆盖率看板以 `Σ(unit_hours × samples)` 排序，输出"覆盖 80% 工时"的名单 |

### 决策带来的三个连带结论

1. **片段制下不许报「缺工序」**。片段本身就意味着不完整，报缺工序会让 75% 的单据天天误报，用户三周内就会把告警全部忽略。只报"多出路线外的工序"和"工时偏离定额"这两类真信号。
2. **准备工时留空必须等价于不存在**。`setup_hours=0` 与 `batch_qty=0` 都走纯单件路径，禁止出现 `÷0` 或"填了批量反而单件工时变小"这类让车间不信任的算术。
3. **S0 是硬前置**。没有 `default_seq`，"从历史生成"只能按样本数排序，等于把排序工作量从 51 行转嫁到每条路线，D4 的 50~80 条就变成了 50~80 次手工排序。

## 十三、升版提醒（P4，2026-11-04 落地）

### 13.1 要解决的问题

发布升版之后，引用被系统重指到新版，**但干活的人不一定知道定额变了**。
「改标准」和「按新版干」是两件事：前者是工艺科的动作，后者是车间的事实。
过去的实现里两者被一次 `UPDATE task_route SET route_id=新版本` 合并掉了 ——
表面上「引用自动同步」很优雅，实际是把「这张单按哪一版做的」从可回答变成不可回答。

### 13.2 机制

| 层 | 落点 | 作用 |
|---|---|---|
| 留痕 | `route_version_notice` | 每次发布顶掉在用基准时记一条：vX → vY、谁发的、何时、单件工时差、影响多少任务 |
| 确认状态 | `task_route.seen_route_id / seen_at / seen_by` | 本单「确认到哪一版」。落后于 `route_id` 即待确认 |
| 判定 | `services/tasks.py::_ref_state` | 四种情形：`upgraded`（还引用旧版）、`draft`/`archived`（引用非基准版本）、`unconfirmed`（已切新版没人认） |
| 出口 | `POST /api/tasks/{id}/ack` | `adopt` 采用新版；`keep` 按**当初确认的那一版**固化为副本，从此脱钩 |

`keep` 一定要回到 `seen_route_id`（而非当前引用）去冻结：那张单真正干着的是它确认过的那一版，
重指之后的新版恰恰是它不接受的那一版。

### 13.3 提醒出现在哪里（同一口径，全部读 `version_alerts`）

1. 生产任务：列表任务号旁的红色徽标、摘要条「升版待确认」、抽屉顶部红块（逐条「采用新版/保留现版」）、路线行标红；
2. 工艺编排：左侧树件名与产品行的「待确认 N」、右栏「升版影响」条（含「看是哪几单」）、引用订单抽屉里的标签与红块；
3. 单据侧：核对工作台顶部红条 + 「保存/保存并确认」前的确认框；单据台账任务列的徽标；
4. 业务待办：`version_notice`（错误级，点击进任务页）；
5. 动作回执：任务内改基线、副本进阶、编排页发布，返回值都带 `affected_tasks`，界面当场列名。

### 13.4 两条工程红线

1. **回填只能做一次**。`seen_route_id` 的回填只在「本次启动刚加上这一列」时执行。
   每次启动都回填的后果是：引用被升版重指后 `seen` 落后，重启一次就被自动确认一次，提醒会凭空空消失。
2. **版本删了要带走通知**。`delete_route` 同时清理指向该版本的 `route_version_notice`，
   否则「最近一次升到 v7」会指向一个不存在的版本。

### 13.5 验证

`scripts/test_version_notice.py`（54 项）覆盖：首版无提醒 → 升版后他人被提醒 → 采用新版 → 保留现版（固化旧口径且此后不受升版影响）→ 编排页发布不重指时的 `upgraded` 提示 → 一键确认 → 单据侧提醒位。

## 十四、单据改挂任务（P5，2026-11-04 落地）

### 14.1 为什么必须有这个入口

单据归集是**自动**的：确认时按「产品 + 批次 + 期间」找已有任务，找不到才新建。
自动就一定会有错的时候——同规格两批活分给了两个订单、批次号抄错、补录时期间填错。

在没有入口的阶段，「这张单归错了订单」只能改库。归属一旦能被随手改库，
账就不可信了：没有人知道谁在什么时候把哪张单从哪个订单挪到了哪个订单。
所以这不是「便利功能」，是**账务归属的人工出口 + 责任留痕**。

### 14.2 一次改挂动三样东西

| 动的东西 | 为什么必须一起处理 |
|---|---|
| 两个任务的 `sheet_count` / `actual_hours` | 物化字段。只改 `sheet.task_id` 不重算，列表上的实报工时就是错的 |
| 新任务的工艺参照面 | 该件名在新订单下有没有路线；没有就「核不出差异」，必须当场说 |
| 审计留痕（`audit_log`，field=`task_id`） | 谁、何时、从哪挪到哪，是账务动作的记录 |

此外还要把「后果」带回来，而不是只回一个 200：`checks[]` 里逐条给出
`no_baseline`（该件名还没有已发布基线）、`no_route_ref`（有基线但新订单没引用）、
`from_task_empty`（原订单已清空，可考虑结案）、`detached`（已摘下，下次确认会重新归集）、
`cross_period`（跨期，两个月汇总都会变）、`version_notice`（新订单有升版待确认）。

### 14.3 三种拒绝，都有业务理由

1. **核算期已锁定** —— 那个月的账已经封了，再改归属等于事后改结算；
2. **目标订单已结案 / 已取消** —— 往封账订单里塞单据，与自动归集同一口径；
3. **跨期改挂未确认** —— 单据属 A 月、任务属 B 月，两边汇总同时失真。
   `force=True` 可放行，但结果必定带 `cross_period` 警告回来，不能悄悄过。

### 14.4 入口（同一套接口，三处出现）

- 单据台账：任务列旁的「改挂」；勾选多行后工具栏出现「批量改挂」；
- 核对工作台：顶部「归属订单」条右侧「改挂订单 / 归集到订单」；
- 生产任务抽屉：单据表新增「归属」列，就地挪走（发现某单不属于本订单时）。

接口：`POST /api/sheets/{id}/task`（单张，`task_id=null` 即解绑）、
`POST /api/sheets/batch-task`（批量，逐张独立成败）。
服务层：`services/tasks.py::move_sheet_task / move_sheets_task`。

### 14.5 界面不放 toast 了事

改挂成功后弹窗**不立即关闭**，而是切到结果面板：绿/橙标题说明「从哪到哪」，
下面按级别列出 warnings 与 info，用户点「完成」才关。
理由与升版提醒一致：一句 toast 一闪而过，而这里每一条都在说「你的账会怎么变」。

### 14.6 验证

`scripts/test_sheet_task_move.py`（45 项）：正常改挂并重算两侧物化字段、幂等不改、
补挂引用、结案拒绝、跨期拒绝与 force 放行、期间锁定拒绝、解绑、批量逐张成败、
审计留痕、台账与单据详情的归属/升版徽标同步。
`scripts/check_data.py` 新增三项体检：单据与任务跨期归属、单据挂在已结案任务上、
已确认但未归集单据。

## 十五、任务基本信息编辑与版本号（P6，2026-11-04 落地）

### 15.1 为什么任务要有版本号

任务（订单）的基本信息是**成本归集与月度汇总的口径**：多少台、什么时候交、算在哪个月。
这些数字一旦能随手改而不留痕，事后问「这单当初按多少台下的」就答不上来 ——
而这个问题正是对账的起点。所以改口径必须是一次**可追溯的修订**，不是一个 UPDATE。

### 15.2 口径字段与流程字段的分界

| 类别 | 字段 | 改动的后果 |
|---|---|---|
| 口径字段（升版） | 任务号、订单名、客户、订单数量、下单日期、交期、核算期间 | version + 1，写一条 `task_revision`，记清每项旧值→新值 |
| 流程字段（不升版） | 状态（草稿/在制/结案/取消） | 状态本身有独立含义，算进版本号会让版本退化成切换次数 |
| 说明字段（不升版） | 备注 | 不参与任何计算 |

`update_task` 用「改前快照 → 应用 → 改后快照 → 逐字段比对」的方式判定，
所以**原样保存不会涨版本**（点保存 ≠ 改口径）；一次改多项只升**一版**，
`changes` 逐条列出，界面直接念「已升到 v3：订单数量 120→150」。

### 15.3 不改库、不静默顺延

- 任务号手工改撞号 → 直接 400「任务号 X 已被其它任务占用」。
  建单时的「撞号自动加后缀」是合理的（自动合成的号本来就会重复），
  但手工改名如果悄悄变成 `A-2`，用户以为改成了 `A`，账立刻对不上。
- 删任务连带删 `task_revision`（外键+语义都要求），否则删任务会 500 并留下孤儿版本。

### 15.4 改核算期间的连带后果要说出口

期间一改，已归集的旧单据仍留在原期间 → 「单据属 A 月、任务属 B 月」，
两个月的汇总同时失真。`update_task` 因此返回 `warnings`，
界面在保存成功后弹确认框点名「N 张已归集单据仍属原期间（YYYY-MM），改成 YYYY-MM 后跨期」，
而不是给一句绿色的「保存成功」就完事。

### 15.5 界面落点

1. 任务列表：新增「版本」列（v1 灰、改过口径的 vN 琥珀），操作列新增「编辑」；
   hover 版本号说明「最近一次由谁于何时修改」。
2. `TaskEditDialog`：任务号/期间/订单名/客户/数量/下单日/交期/备注 + 修订说明；
   产品只读（派生自路线，改产品要去调路线）；改动时实时显示「本次将升版 vN，改动了：…」，
   按钮文字同步变成「保存并升到 vN」；未改动时按钮禁用并说明「保存不会产生新版本」。
   若任务有升版待确认，保存前再问一次（与其它写动作同一口径）。
3. 抽屉表头：任务号旁可点的版本徽标 + 「编辑基本信息」+「修订史 N」。
4. 修订历史弹窗：版本/时间/操作人/改动（旧值划线→新值）/说明。

### 15.6 验证

`scripts/test_task_version.py`（42 项）：建单 v1 → 改数量升版并记清变化 → 原样保存不升版
→ 状态/备注不升版 → 一次改多项只升一版 → 撞号被拒且任务号未被偷改 → 改任务号升版
→ 列表与详情版本一致、修订史新的在前 → 改期间给出跨期警告。
`scripts/check_data.py` 新增「任务版本」段：版本号缺失/非法、无主修订记录、
版本号与最新修订记录不一致。
