# 产品结构：新增件与计划生产数量

> 2026-11-05。对应问题两条：「工艺及工时编排页无法在现有结构中新增」、
> 「部件和零件上下级没有数量关联，部件改 2、零件也要跟着 2」。

## 一、原来缺什么

| 缺口 | 后果 |
| --- | --- |
| `product_node` 没有任何新增入口 | 结构只能靠迁移和「按件名重铺」生成，漏登记的件只能改库 |
| 「新建路线 / 新建组合」不建结构节点 | 建完的件在结构里根本不存在，成了孤儿：结构树、工艺卡沿结构展开都看不到它 |
| 编排页左树不含「结构里有、没工艺没历史工时」的件 | 就算结构里有，左栏也找不到，人以为没加成功 |
| 只有 `qty_per_unit`（每台用量），没有「这一批做几件」 | 部件做 2 台，下面零件该做几个，系统答不出来 |
| `R.tree()` 连 `qty_per_unit` 都不返回 | 左栏连 ×2 都看不见 |

## 二、两个数量不是一回事（别混）

| 字段 | 含义 | 谁决定 | 会不会随订单变 |
| --- | --- | --- | --- |
| `qty_per_unit` | 装**一台上级**用几件 | 设计定额 | 不会 |
| `plan_qty` | 这一批做**几件** | 排产输入 | 会 |

`plan_src` 记这个计划量是**怎么来的**：

* `auto` —— 由「父件计划量 × 本级每台用量」派生，父件一变它就跟着变；
* `manual` —— 人填的。上级再变，这一件不动。

派生规则写在 `app/services/node_plan.py`，界面不自己算。

## 三、联动规则

改任意一件的计划量（`PATCH /api/combos/plan`）：

1. **向下**：本件的 auto 后代 = 本件计划量 × 各级用量，逐层推下去。
2. **向上**：本件的上级按「本件计划量 ÷ 本件用量」反推；不整除时**向上取整**
   （计划是台数，不能是 1.5 台），取整前后都写进返回的 `warnings`。
   上级改了，它的其它 auto 分支跟着重算，然后继续往上，一直推到根 ——
   否则「零件 3 个、部件 1 台」这种自相矛盾会留在库里。
3. **人工设定优先**：反推遇到一个 `manual` 且数值已经对得上的上级就停下，
   不再往上动它。

所以「部件 1 台 → 零件 1 个；部件改 2 → 零件变 2」和反过来的「零件改 3 →
部件按用量反推」，是同一套规则的两个方向。

人工值与当前上级算出来的应有数量不一致时，`combo_tree` 每个节点会带
`plan_expect`，界面把那行标黄（「人工设定；按当前上级与每台用量应为 N 件」）。
**需求不足比多做几件严重得多**，所以这一项必须显式提示，不能悄悄过。

## 四、新增与删除

* `POST /api/combos/node`：在现有结构里加一件，可指定挂到哪个上级、每台用量、
  计划数量。只建结构 —— 「结构里有、工艺里没有」是合法状态，台账显示「无工艺」。
* `DELETE /api/combos/node`：删件。**护栏**：有下级 / 编过工艺路线 / 有订单引用 /
  有报工明细，任一条命中就拦住。删掉一个被工资表引用的件，
  比留一行脏数据危险得多。

  注意「有工艺身份（工时组合）」这条已改成**按真实引用判断**，见第七节：
  身份行本身不算引用，空壳身份不再拦人，删件时顺手收掉。
* 「新建路线」`POST /api/routes` 与「新建组合」都会 `ensure_node`：
  只建路线不建结构位置，等于编了工艺但装配结构里没这个件。

存量库升级时 `plan_qty` 按「根 = 1 台、下级 = 父 × 用量」用递归 CTE 回填一次，
只在首次加列那一版跑；之后 `manual` 的值不会再被覆盖。

## 五、界面

* **结构弹窗**（工艺编排页 / 工时组合页的「结构」按钮）：
  工具条「＋ 新增件」；行尾「＋」直接以该件为上级加子件；行尾「✕」删件；
  每行显示 `×用量` 与 `计划 N`，点一下就地改。
* **编排页左栏**：每行带 `×用量` 和 `计划 N`（用量为 1 时不显示 ×1，避免每行都挂个 ×1）。

## 六、边界

* 计划量按**产品结构**存（用户确认的口径），与生产任务的订单数量是两套：
  任务里改了 `qty` 不会回写结构计划量，反之亦然。要联动得另做，且要想清楚
  一个产品同时有多个在制订单时以谁为准。
* 反推向上取整只作用于「反推链」，不修改被取整件下面的其它人工值。
* 删件不级联：有下级就不让删，必须先处理下级。

## 七、删了工艺之后为什么还能删结构（空壳身份）

现场链路：新增件 → 编工艺 → 发布 → 撤回发布 → 删除工艺 → 删结构，
最后一步被「有工时组合（工艺身份）」拦住，而工艺明明已经删干净了。

原因：`work_combo` 是工艺的**身份行**，`process_route` 是它的版本。
删路线时没人管身份行，最后一版删掉后这一行还在、`status` 还挂着 draft：

* 树上显示「草稿」，看着像还有一份工艺躺在那里；
* 删结构被「有工艺身份」拦住。

### 规则（`app/services/combo_registry.py`）

**「有工艺」的判据是有路线，不是有一行身份。** 一条身份行同时满足下面四条
才是**空壳**（`orphan_shell`），否则一律当真实引用：

1. 没有任何 `kind='route'` 的路线；
2. 没有 `standard_hour` 历史工时；
3. 没有被 `task_route` 引用；
4. 没有 `work_item` 报工明细。

`status='released'` 的空壳不算空壳 —— 已发布却没有路线是数据不一致，
要留给台账报警，不能静默抹掉「发布过什么」的证据。

### 两个清理口，都留审计（`combo:drop_shell`）

* `delete_route` 之后调 `cleanup_after_route_delete`：删掉最后一版且是空壳 →
  身份行一起删；还有别的版本 → 只清悬空的 `route_id`，其余不动。
* `delete_node`：身份行是空壳时不拦人，删件时顺手收掉 —— 这是历史遗留
  残渣（旧版本删路线不清理）的自愈口。

### 连带效果

* 这一件回到「结构里有、工艺还没编」，树上状态变成 `none`（无工艺）；
* 有历史工时（481 个件有 `standard_hour`）的件身份行留着，删结构照样拦 ——
  那是真引用，不是残渣；
* 回归脚本 `scripts/test_route_delete_shell.py`（31 项）钉住以上全部规则。

## 八、结构里新增的件，工艺卡上看不见（2026-11-05）

现场：在装配结构里新增 `1112`（挂在「出条轮」下），工时组合台账能看到它，
但**工艺卡的「部件层级」里没有**。

### 根因

工艺卡的整棵树（`build_cards` 的 `tree` / `cards[].children` / 编号 / 工时）
全部只由 **`printable`** 生成，而 `printable` 的条件是：

```python
printable = [c for c in released if _key(c.product, c.part) in routes]
```

也就是「**有组合身份 + 工艺已发布 + 能取到生效路线**」。新加的件只有
`product_node`（结构），既没有 `work_combo` 也没有 `process_route`，
自然不在树里 —— 它不是"没同步"，是从来没进过这条链路。

### 口径：层级里占位，但绝不出卡

| 做什么 | 为什么 |
|---|---|
| 在**已出卡的部件**下面补结构里存在的直接下级 | 回答「我刚加的那件去哪了」，且只补一层，不把整棵结构铺开 |
| 标 `has_route=false` + 真实状态（`none` / `draft` / `archived`） | 「没编」「编了没发」「停用了」是三件事，混成「未建」会让人去重编一个已有草稿的件 |
| **不生成卡片**、`code` 留空、工时为 0 | 没有工序可印；空白卡会让车间以为漏了工序，也会污染编号与定额合计 |
| 占位件下面还有纯结构子件 → 递归显示 | 新挂一个部件时，它下面的零件也要能看到 |

编号、卡片张数、本层/含子件工时**都不受影响**：占位件不参与 `_numbering`，
也不进 `owned_of` / `subtotal`。

### 为什么不全铺结构

生产库 889 个结构节点里有 **348 个从来没编过工艺**。整棵铺出来，左栏会突然
多出一大片「未建」，看着像工艺大面积缺失，反而没人看得懂。真正要回答的问题
只有「我刚加的那一件为什么不在」。

### 实现

* `app/services/process_card.py`：新增 `struct_kids`（结构父子索引）、
  `placeholder_node()`（占位节点，含递归）、`brief()`（卡片下级与树共用一套字段）；
  `node()` 与 `card_of().children` 都把占位和真卡片按 `seq` 混排。
* `summary.unbuilt`：这一批里「结构有、出不了卡」的件数，界面用它提示
  「不是漏印，是还没编工艺」。
* `frontend/src/views/ProcessCardView.vue`：左栏占位行 `件号 — / 灰标 未建·草稿·停用 /
  工时 —`；点击不发请求，直接提示去「工艺及工时编排」处理。

### 验证

`scripts/test_card_unbuilt.py`，26 项：纯结构件可见且不出卡、编号与合计不变、
草稿状态区分、发布后转正并补编号、占位递归、兄弟按结构序号混排。

### 补充：状态从两张表来

草稿阶段**不登记 `work_combo` 身份**（身份是「这版工艺可以用了」才写的），
所以只看身份表会把「编了草稿还没发布」误判成「根本没编」，工艺员会去重编一遍。
`placeholder_node()` 的取法：

```
有组合身份        → 取 combo.status（released 的已经进 printable 了，这里只剩 draft/archived）
没有身份但有草稿  → draft      ← 读 process_route.status
没有身份但有停用  → archived
两者都没有        → none
```

同理，`test_combos.py` 的「来源」口径也改成了**已发布路线**：草稿路线本来就不该
出现在台账里，原来把全部路线都算来源，任何人新建一条草稿就会让断言变红。
