# 数据备份：整库全量口径

> 系统管理 →「数据备份」。用户口径：**要的是系统数据库全量备份**，不是几张业务表的导出。

## 一、一句话口径

一份备份 = 当前 `data/worktime.db` 的**完整副本**：全部 27 张表、全部索引、全部数据，
一行不筛、一表不漏。实现是 SQLite 的 `VACUUM INTO`（在线一致性快照，不停服务）。

## 二、为什么不能直接拷 .db

库跑在 **WAL 模式**。已提交但还没 checkpoint 的事务留在 `worktime.db-wal` 里，
只拷主文件得到的是一个**连表都没有的空壳**——恢复时才发现，那时已经晚了。

`tests/scripts/test_backup_full.py` 第 2 节把这个差异钉住了：在源库保持连接、
数据只在 -wal 里时，`VACUUM INTO` 拿到 9 行，直接拷主文件拿到 **0 行**。

## 三、包含什么 / 不包含什么

| 内容 | 是否在备份内 | 说明 |
| --- | --- | --- |
| 全部业务表（报工单、明细、结构、工艺、工资单价、审计…） | 在 | 整库拷贝，不挑表 |
| 索引、触发器、视图 | 在 | VACUUM INTO 连 schema 一起写 |
| `data/uploads` 里的原始单据照片 | **不在** | 图片是文件不是数据，需另行同步该目录 |
| 出厂清单 `xxx.db.json` | 在（旁边一格） | 校验用旁证，不属于数据库内容 |

## 四、出厂清单（`.db.json`）解决什么

校验要回答的是「这份备份**完整**吗」，难点在于：备份里比现在少几张表，可能是
**损坏**，也可能是**那会儿还没这功能**（`worker_rate` 是 2026-11-04 才加的，
`print_sheet` 是预印单上线时才加的）。靠现有库做基准分不开这两种情况。

所以备份时顺手在库文件旁边写一份清单：

```json
{"at": "2026-11-05 12:41:05", "source": "worktime.db",
 "tables": 27, "rows": 5083, "table_list": ["audit_log", "batch", ...]}
```

校验拿**清单**当基准：清单说当时有 `worker_rate`，备份里没有 → 真损坏（红）。
清单里本来就没有 `print_sheet` → 那会儿还没有，正常（不红，只在提示里写「本份之后新增 5 张表」）。

**为什么放库外，而不是库里建一张 `_backup_meta` 表**：备份文件必须与源库一模一样，
恢复回去不能凭空多出一张表。清单丢了（有人只拷了 .db）只是退回「只核核心表」的
老口径，不影响恢复。

## 五、判定顺序

```
1) quick_check 通过，且不是空表壳（tables > 0）
2) 有出厂清单 → 对着清单核表，缺任意一张即不合格（与当前库无关）
3) 没有清单（历史备份） → 退回「9 张核心表都在」兜底
4) 与当前库的结构差、行数差 → 只作提示，不参与合格判定
```

第 2 条和第 4 条的区别是这套机制的核心：**完整性看清单，新鲜度看当前库**。
把「现在库里多出来的表」当成备份的错，会让所有历史备份无端标红。

## 六、界面上怎么看

- 卡片：`最近备份可用 · 12:41 · 27 表`，说明里写明「当前库 27 张表、5,083 行全部在内」。
- 列表列：文件 / 备份时间 / 校验 / 表 / 行数 / 单据 / 工时明细 / 大小 / 明细。
- 校验标签悬停：`quick_check=ok，27 张表 / 5,083 行，与备份时清单（2026-11-05 12:41:05）逐表一致`。
- 「明细」→ 逐表对照：备份行数 vs 当前库行数 vs 差异；老备份会注明
  「其中 5 张表是这份备份之后才加的（当时还不存在，属正常）」。

## 七、命令行与定时

```bash
.venv/Scripts/python.exe scripts/backup_db.py            # 备份一次，保留最近 14 份
.venv/Scripts/python.exe scripts/backup_db.py --list     # 列表 + 逐份校验
.venv/Scripts/python.exe scripts/backup_db.py --verify X # 校验某一份
```

界面上的「立即备份」与这里走**同一个函数**（`app/services/backup.py: create`），
两处口径必须一致，否则界面上说的和定时任务做的不是一件事。

定时任务（管理员 PowerShell 跑一次）：

```bat
schtasks /Create /SC DAILY /ST 21:30 /TN "工时系统备份" /TR ^
  "\"E:\tedri_project\hy\.venv\Scripts\python.exe\" \"E:\tedri_project\hy\scripts\backup_db.py\""
```

清理：`prune(keep)` 按 mtime 留最近 N 份，**清单文件跟着一起删**，不留孤儿 `.json`。

## 八、恢复

两条通道，按「库能不能打开」选：

| 场景 | 用哪条 | 停服务 | 回退手段 |
| --- | --- | --- | --- |
| 误删数据、数据被搞乱了（库本身正常） | 系统管理 → 备份 → 某行「恢复」 | 不用 | 自动 `pre-restore` 快照 |
| 库文件损坏 / 换机器 / 整机迁移 | `scripts/restore_db.py` | **必须停** | 自动 `pre-restore` 快照 |

### 8.1 在线恢复（界面）

点某行的「恢复」→ 确认框会列出「备份 vs 当前库」的时点、表数、行数、单据数，
并说明三件事：数据会被整表替换、系统会先自动拍快照、恢复期间别人不能操作。
勾选确认后按钮才可点。

实现是**标准 SQL 事务 + 整表替换**，不是覆盖文件：

```
ATTACH 备份 → BEGIN IMMEDIATE → 逐表 DELETE + INSERT → COMMIT
```

为什么不用「把 .db 覆盖回去」：服务是多进程（Web 4 worker + 独立 OCR worker），
库文件被一堆连接占着，Windows 上替换文件本身就失败；就算成功，其他进程手里还有
旧 WAL 和旧页面缓存，接着写就把恢复结果冲掉了。

这个做法换来三件事：
- **单事务**：任何一张表失败整体回滚，不会留下「一半旧一半新」；
- **不用重启**：走 WAL 正常路径，其他进程读到的是事务后的新版本；
- **结构不动**：只覆盖数据，当前库的表/索引/触发器保留，恢复旧备份不会把新版本
  加的表结构一起降级。

规则细节：

- 备份里有、当前库没有的表 → **保留不动**，结果里列出来（`kept`）。
  从旧备份恢复时 `worker_rate`、`print_sheet` 当时还不存在，清空它们等于把后来
  录的工时单价一起抹掉 —— 宁可提示，不可自作主张删数据。
- 备份里缺的新列 → 用该列的默认值填（`defaulted_columns` 会列出来）。
- 备份本身校验不合格 → 拒绝恢复，当前数据一个字节不动。
- 识别队列有 `pending/processing` → 拒绝恢复（worker 正在写，会互相覆盖）。
- 留痕：`audit_log.field='backup:restore'`，**写在恢复之后**（audit_log 也是被覆盖
  的表之一，写在前面会被备份里的旧审计冲掉），内容含回退快照名。
- 恢复后 `engine.dispose()` 重建连接池，避免本进程的会话还停在旧快照上。

### 8.2 停服恢复（命令行）

```bash
.venv/Scripts/python.exe scripts/restore_db.py --list
.venv/Scripts/python.exe scripts/restore_db.py --file worktime-20261105-125029-manual.db
.venv/Scripts/python.exe scripts/restore_db.py --file D:\U盘\xxx.db --yes
.venv/Scripts/python.exe scripts/restore_db.py --file xxx.db --check-only   # 只校验
```

流程：校验备份 → `backup.create('-pre-restore')` → 复制到临时文件 →
`os.replace` 原子替换 → **删掉 `-wal` / `-shm`**。

两点必须知道：
- `os.replace` 在目标被占用时会失败。**失败是好事**：说明服务没停，原库完好无损。
- 旧的 `-wal` 一定要删。留着它，SQLite 会把备份时点之后的旧日志重放进新库，
  等于把旧数据盖回来 —— 这是最容易踩、也最难看出来的坑。

### 8.3 恢复之后

- 界面恢复会自动刷新页面（内存里的期间/单据 id 全是旧的）。
- `data/uploads` 里的照片不随库回退：恢复后可能出现「单据指向已经不存在的图」，
  或反之。以库为准，图片按需另行处理。
- 恢复后建议点一次「立即备份」，让最新快照对齐到恢复后的状态。

## 九、测试

```bash
.venv/Scripts/python.exe scripts/test_backup_full.py      # 44 项：备份是否真的全量
.venv/Scripts/python.exe scripts/test_backup_restore.py   # 33 项：能不能真的恢复回去
```

`test_backup_full.py` 覆盖：整库表数/行数逐表相等、WAL 未 checkpoint 不丢数据
（含「拷主文件」反证）、缺非核心表判坏、空壳判坏、基准库不可读时降级、
备份后新增行只提示、清单是权威（当前库删了表也判坏）、只拷 .db 时降级不误报、
缓存不盖住文件变化、清单随 prune 一起清。

`test_backup_restore.py` 覆盖：恢复后逐表行数与备份一致、自动留可回退快照、
删掉的数据连具体行一起回来、备份里没有的表保留不清空、缺的新列取默认值、
坏备份/空壳拒绝恢复且不动当前数据、中途失败整体回滚、文件名不给路径穿越机会、
恢复后能正常再备份。
