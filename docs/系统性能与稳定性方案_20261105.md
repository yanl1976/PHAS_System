## 0. 一句话结论

系统现在的瓶颈**不在机器**（12 核 / 32G，只用了 1 核），在三个具体的写法上：

| # | 问题 | 实测证据 |
|---|---|---|
| R1 | 组合台账用 **547 条 SQL** 取一份数据 | 541 次逐条懒加载 `route.steps` |
| R2 | 组合列表**每翻一页就全量同步一次库**（GET 写库） | 单次 `sync_combos` 58ms + `commit` |
| R3 | 单进程把所有 CPU 活串起来 | 并发 8 时吞吐**下降**，p50 从 45ms 涨到 1218ms |

三处都能改，且**不碰业务规则**。改完后并发能力提升 5~7 倍，识别速度的问题需要单独决策（见 C2）。

## 1. 实测数据

### 1.1 单请求（生产库，18 条报工明细）

| 接口 | 耗时 | 备注 |
|---|---|---|
| `/api/periods` | 15 ms | |
| `/api/stats` | 15 ms | 顶栏统计 |
| `/api/sheets` | 14 ms | 报工台账 |
| `/api/tasks` | 45 ms | 任务列表 |
| `/api/cards` | 100 ms | 工艺卡 90 KB |
| **`/api/combos`** | **194 ms** | **最慢，547 条 SQL** |

### 1.2 并发（单进程，混合 8 并发）

| 接口 | 并发 1 | 并发 8 | 结论 |
|---|---|---|---|
| `/api/periods` | 60 req/s | **299 req/s** | 正常扩展（I/O 型） |
| `/api/stats` | 79 | 185 | 正常 |
| `/api/sheets` | 62 | **38.6**（p50 14→207 ms） | 反扩展 |
| `/api/tasks` | 23 | **6.4**（p50 45→1218 ms） | 严重反扩展 |
| `/api/combos` | 5.1 | **1.9**（p50 194→4157 ms） | 崩溃 |

**吞吐量随并发升高反而下降**，这是单进程 + GIL 的典型特征：CPU 时间长的请求互相抢 GIL，
切换开销叠加，比排队还慢。`/api/periods` 能扩展，说明 **SQLite 和线程池本身没问题**。

### 1.3 多进程（4 worker，同一份库）

| 接口 | 并发 8 单进程 | 并发 8 四进程 | 提速 |
|---|---|---|---|
| `/api/tasks` | 6.7 req/s / p50 1186 ms | **50.1 req/s / p50 88 ms** | **7.4×** |
| `/api/sheets` | 42.6 / 180 ms | **219 / 30 ms** | **5.2×** |
| `/api/combos` | 1.9 / 3999 ms | 12.3 / 585 ms | 6.3× |
| 单请求 | — | 慢约 20% | 0.8× |

### 1.4 消除 N+1 的效果（原型验证）

```
现状  list_combos（541 条 N+1）      172.6 ms   547 条 SQL
原型  5 次批量查询 + 内存组装         18.7 ms     5 条 SQL      → 9 倍
```

### 1.5 并发写（扫码建单，真实写压力）

| 场景 | 结果 |
|---|---|
| 6 任务并发重印 | 2.95 s，p50 2717 ms，新建 333 张，**失败 0** |
| 3 任务并发重印 | 0.77 s，p50 708 ms，新建 144 张，**失败 0** |
| **单号唯一性** | 524 张单 / **524 个不同号，零重复** |

写是串行的（SQLite 单写者），但**不报错、不丢号**。以「20 个计划员、一天几百次提交」的量算，
**现在的库完全够用，不需要换数据库**。

### 1.6 OCR（真正的等待来源）

| 指标 | 实测 |
|---|---|
| 模型加载 | 3.6 s，常驻 **331 MB**，识别峰值 **401 MB** |
| 单张识别 | **5.7 s**（960 边长，v6_small，关 oneDNN） |
| 连续 3 张 | 401→402→401 MB，**无泄漏** |
| **两进程并行** | 单进程 3 张 17.1 s；**两进程同时各 3 张 → 34.6 / 35.2 s** |

**最后一行是关键**：并行跑 OCR **吞吐一点没涨**（0.175 张/s → 0.171 张/s）。
Paddle 在 CPU 上已经吃满多核，加进程只会互相抢核、每个进程再多占 400 MB。
**所以「多开进程让识别变快」这条路走不通**，别再往这个方向投入。

推算出的人体感：**50 张一册 ≈ 4.8 分钟**（不含 cellprobe 二次识别的额外耗时）。

## 2. 根因

### R1 组合台账的 N+1

`app/services/combos.py` 第 143 行 `len(r.steps)`，对每个组合的锚定路线触发一次懒加载。
541 个组合 = 541 条 SQL。**这条随组合数线性增长**：将来 2000 个组合就是 2000 条。

### R2 GET 请求里写库

`app/api/combos.py` 第 69-73 行：`offset == 0` 时调 `CR.sync_combos()`，那是
「全量读 StandardHour + ProcessRoute + WorkCombo，比对后可能写库并 commit」。

后果有三层：
1. 每次翻回第 1 页都付 58 ms；
2. 多个人同时打开组合台账 → 抢 SQLite 写锁 → 互相阻塞（这是 combos 并发崩溃的主因）；
3. **违反了「读接口不改数据」**，也让审计里出现没人主动触发的变更。

### R3 单进程 GIL

FastAPI 的同步路由跑在 40 个线程里，但 Python 一次只能执行一个线程的字节码。
接口 CPU 时间越长，并发时越像在排队，还要额外付线程切换成本。

### R4 OCR 串行 5.7 s/张，且不可横向扩展

见 1.6。**并行无收益**，只能从「让用户不用干等」这个角度解决（进度、优先级、后台化）。

## 3. A 档：零风险优化（改完不影响任何业务口径）

预计工作量：**半天**。收益：组合台账 194 ms → 25 ms 以内，并发不再互相踩。

### A1 消除 combos 的 N+1 `【必做】`

把 `len(r.steps)` 换成一次 `GROUP BY route_id` 的计数查询（1.4 已原型验证 9 倍）。
同时给 `list_combos` 的 5 个读查询加 `execution_options(populate_existing=True)` 之外无需改动。

**风险**：无。`step_count` 语义不变，只是取法变了。

### A2 `sync_combos` 移出 GET `【必做】`

从 `list_combos` 接口里删掉，改为四个触发点：

| 触发点 | 说明 |
|---|---|
| 启动时（已在 lifespan 里） | 保留 |
| 上传识别落库后 | 新单带出新「产品×件名」时立刻登记，工艺科当天就能看见 |
| 工艺路线新建/改名后 | 已有入口，补一次调用 |
| 组合台账页「同步」按钮 | 手动兜底，替代现在的「翻页即同步」 |

**为什么这样改不掉业务**：登记逻辑完全不变，只是从「每次读都顺手同步」变成「有数据变化才同步」。
原来那句注释担心的场景（今天录一张老单就要看见新组合）由「识别落库后触发」覆盖，**覆盖得更准**。

### A3 前端收敛

- 组合台账 `limit` 默认 100 → 50，并开虚拟滚动或分组折叠（541 行 el-table 渲染本身要 300ms+）
- 任务页、工艺卡页首次加载改 `Promise.all` 并发拉取（现在是串行等待）

### A4 组合台账加 5 分钟缓存（可选）

组合数据变化频率极低（一天几次）。按 `work_combo/process_route` 的 `max(id)`+`count` 做版本键，
命中直接返回序列化结果。**不建议先做**——A1+A2 之后它已经 25ms，缓存只会增加「数据不刷新」的困惑。

## 4. B 档：稳定性与防错纠错（这是「稳定性」的正题）

预计工作量：**一天**。这一档不提升速度，但决定「出事时能不能救回来」。

### B1 定时备份 `【必做，最高优先】`

**现状：只有手动按钮和脚本，没有任何定时。** 库坏了 / 误删了 / 硬盘挂了 = 全部工时数据没了。

方案：进程内起一个后台线程（不用引入调度框架），每天 **02:00 和 12:30** 各做一次
`VACUUM INTO` 备份，复用现成的 `services/backup.py::create()`（含 `quick_check` 校验 + 保留 14 份）。
备份失败必须**记日志并在系统管理页显红**，不能静默。

> 为什么要两次：单机部署没有运维值班，一次备份点遇到「上午误操作 + 下午才发现」就来不及。

### B2 `/api/health` 改成真探活

现在只返回 `{"ok": true}`，库坏了它照样说 ok。改为检查三件事：

| 检查 | 判据 |
|---|---|
| 数据库 | `SELECT 1` + `PRAGMA quick_check` 的轻量版（只在启动后首次做全量） |
| 磁盘 | 剩余空间 < 2 GB 报 `degraded` |
| 识别队列 | 积压 > 20 张 或 有 `failed` 图片 报 `degraded` |

返回 `{"ok": true, "status": "ok|degraded", "problems": [...]}`，`degraded` 时 HTTP 仍 200
（否则监控会误判成服务挂了），但前端顶栏显示黄条。

### B3 上传限制 `【必做】`

`upload_images` 现在是 `await f.read()` 全量读进内存，**没有大小和像素上限**。
一张 200 MB 的 TIFF 或 1 亿像素的扫描件，能把进程内存打满。

加三道上限：单文件 ≤ 30 MB、单次总 ≤ 200 MB、像素 ≤ 8000×8000（读完后用 PIL 校验）。

### B4 OCR 超时 + 重试上限 `【必做，防启动死循环】`

**这是当前最危险的稳定性缺口**：

```
resume_orphaned() 把 status in (pending, processing) 的图全部重新入队
   → 如果某张图必然导致崩溃（超大图 OOM / 引擎段错误）
   → 进程崩溃 → 重启 → 又捞到这张 → 又崩溃 → 服务永远起不来
```

加两个字段（`_ADDED_COLUMNS` 里登记即可）：
- `image.attempts INTEGER DEFAULT 0`
- `image.last_error`

规则：`attempts >= 3` 的图**不再自动入队**，标 `failed` 并写清原因，等人手动点「重新识别」。
单张识别加超时（默认 120 s，环境变量可调），超时按失败计一次。

### B5 日志落盘 + 轮转

现在只打 stdout。后台运行时日志要么丢、要么无限增长。
改为 `RotatingFileHandler`（`logs/app.log`，10 MB × 10 份），同时保留 stdout。

### B6 识别进度可见

现在前端只知道「done / 没 done」。50 张一册要等 4.8 分钟，**中途没有任何反馈**，
人只会以为卡死了，然后去点重新识别——那会让队列更长。

加一个 `/api/queue` 返回：总张数、已完成、当前正在识别的图、**排队位置**、预计剩余时间
（按最近 5 张的移动平均算）。前端导入页显示进度条。

### B7 识别崩溃隔离（与 B4 配套）

识别线程池里任何异常只影响这一张（现在已是），但**进程级崩溃**（Paddle 段错误）兜不住。
配合 C1 把 OCR 拆成独立进程后，这个风险自然消失——Web 崩不了，OCR 崩了自动重启。

### B8 报工提交防连点

后端已经有 `status='printed' → 'reported'` 的原子翻转，**重复提交是安全的**。
前端按钮 `loading` 已有。这一项只需补一条测试固化，不用改代码。

### B9 审计与图片的清理策略

`audit_log` 只增不减，`data/processed` 已 22 MB。当前总量很小（E 盘剩 715 GB），
**不是现在的问题**，但要有明确的处置口径：

- 审计日志：**永不删除**（工资争议时的唯一凭证）
- 图片原图/处理图：核算期锁账满 2 年后可归档（写进文档，暂不实现）

## 5. C 档：并发能力（需要你拍板）

### C1 Web 多进程 + OCR 独立进程 `【推荐，但有改造量】`

实测 4 进程能把 `/api/tasks` 从 6.7 提到 50 req/s（7.4 倍）。但直接 `--workers 4` 有三个坑：

| 坑 | 后果 |
|---|---|
| 每个 worker 各加载一份 PaddleOCR | 内存 400 MB × N（可用只有 7 GB） |
| `resume_orphaned()` 被每个 worker 各跑一遍 | **同一张图被识别 N 次**，写 N 份明细 |
| OCR 队列在每个进程各一份 | 无法统一限流、无法看总进度 |

所以正确做法是**把 OCR 从 Web 进程里拆出去**：

```
Web 进程 ×4（不加载 Paddle，约 120 MB/个）
   │  上传 → image.status='pending'（数据库即队列）
   ▼
OCR 进程 ×1（加载 Paddle，400 MB）
   │  原子领取：UPDATE image SET status='processing', attempts=attempts+1
   │            WHERE id=(SELECT id FROM image WHERE status='pending' ORDER BY id LIMIT 1)
   │            AND status='pending'   ← rowcount 必须为 1，否则跳过
   ▼
   识别完成写回 sheet / work_item
```

**收益**：
1. Web 并发 5~7 倍；
2. Web 进程内存 400 → 120 MB（4 个才 480 MB）；
3. OCR 崩了不影响界面，重启自动续；
4. 进度、排队位置、预计时间都变成一次 SQL 就能查（B6 顺带解决）；
5. 多进程下不再有「重复识别」风险（原子领取天然互斥）。

**代价**：改造 `pipeline.py`（约 80 行）、新增 `scripts/ocr_worker.py`、启动脚本改成两条命令。
**风险**：识别延迟从「立即」变成「轮询间隔」（设为 0.5 s，人体无感）。

### C2 OCR 提速 `【不建议投入】`

实测两进程并行吞吐不涨（1.6）。**唯一还有效的方向**，按性价比排序：

| 方向 | 预期 | 代价 |
|---|---|---|
| 关掉 `cellprobe` 二次识别（`WT_CELL_PROBE=0`） | 快 20~40%，但**单字符数量识别准确率会掉** | 需先测准确率损失 |
| 检测边长 960 → 800 | 快约 15% | 小字漏检风险 |
| 换 GPU | 10 倍以上 | 要买卡，车间机器不一定有 |
| 多机分摊 | 线性 | 部署复杂度上一个台阶 |

我的建议：**先做 B6（进度可见）**。用户的痛点有一半是「不知道还要等多久」，不是「等得久」。
等 B6 上线后观察一周，如果确实还不够，再单独评估 `cellprobe` 的取舍（那属于识别口径，要你定）。

### C3 数据库 `【明确不建议】`

实测并发写 0 失败、单号零重复、524 张单 2.95 s 建完。当前是「20 人、一天几百次提交」的量级，
SQLite + WAL 绰绰有余。换 PostgreSQL/MySQL 的迁移风险（外键、触发器、事务语义、
现有 27 个测试脚本全要重跑）**远大于收益**。

触发换库的真实阈值（写下来备查）：**日提交 > 5000 次，或并发写 > 50**。到那天再谈。

## 6. 建议的执行顺序

| 阶段 | 内容 | 工作量 | 验收标准 |
|---|---|---|---|
| 第 1 步 | **A1 + A2** | 半天 | combos 单请求 < 30 ms；8 并发 p50 < 100 ms；SQL 条数 < 10 |
| 第 2 步 | **B1 + B3 + B4** | 半天 | 断电式杀进程重连不崩；超大图被拒；毒图 3 次后停 |
| 第 3 步 | **B2 + B5 + B6** | 半天 | health 能反映库/盘/队列；进度条准确 |
| 第 4 步 | **C1**（需你确认） | 一天 | 8 并发 tasks ≥ 40 req/s；多进程下无重复识别 |
| — | A3 前端收敛 | 随第 1 步 | 首屏无横向滚动、无 500ms 以上白屏 |

**为什么先 A 后 C**：A 是纯收益（9 倍，零风险），做完可能就已经够用了。
C 有改造量和运维复杂度，应该用实测数据决定要不要付这个代价，而不是一开始就上。

## 9. 我不建议做的事（避免过度工程）

- 引入 Redis / Celery / RabbitMQ：当前没有跨机需求，多一个组件多一个故障点

## 10. 执行记录（2026-11-05，按 C 档落地）

C 档不是「加个 `--workers 4`」就完事。它有两个前置，不做的话多进程会把问题放大：

| 前置 | 不做的后果 |
|---|---|
| A1 消除 combos N+1 | 4 个进程各跑 547 条 SQL，数据库先被自己打满 |
| A2 `sync_combos` 移出 GET | 4 个进程同时全量扫库 + commit，抢 SQLite 写锁 |
| B4 重试上限 + 队列外置 | 每个 worker 各有一条私有队列、各跑一遍 `resume_orphaned` → **同一张纸识别 N 次、写 N 份明细** |

### 10.1 改了什么

| 文件 | 改动 |
|---|---|
| `app/services/combos.py` | `len(r.steps)` 逐条懒加载 → 一次 `GROUP BY` 计数；台账为空时不再顺手 sync |
| `app/api/combos.py` | 删掉「`offset==0` 就 sync」；新增 `POST /api/combos/sync` 手动入口 |

### 10.2 改完的实测（同一台机器、同一份生产库、8 并发）

| 接口 | 改前 | 改后 | 变化 |
|---|---|---|---|
| `/api/tasks` | 6.4 req/s，p50 1218ms | **40.1 req/s，p50 121ms** | **6.3×** |
| `/api/combos` | 1.9 req/s，p50 4157ms | **24.3 req/s，p50 273ms** | **12.8×** |
| `/api/combos` 单发 | 194ms（547 条 SQL） | **69ms（6 条 SQL）** | 2.8× |
| `/api/sheets` | — | 109.6 req/s，p50 50ms | 8 并发下不再退化 |

关键变化不是「变快了一点」，而是**吞吐随并发上升**：改前并发从 1 加到 8，吞吐反而从 23 掉到 6.4（p50 1218ms，人会觉得「点了没反应」）；改后是 22.4 → 40.1。

### 10.3 内存账（这是 C1 拆进程的真正理由）

| 进程 | 实测内存 |
|---|---|
| OCR worker（**唯一一份 Paddle**） | 354 MB |
| Web worker × 4 | 112～116 MB 各，共约 456 MB |

对照：如果直接 `uvicorn --workers 4` 而把 Paddle 留在 Web 里，就是 4 × 400 MB ≈ 1.6 GB —— 本机可用内存只有 7 GB。**拆进程不是为了跑得更快，是为了「多进程」这件事在内存上成立。**

### 10.5 现在怎么启动

```
scripts\start_all.bat            # 一键：先 OCR 进程，再 4 进程 Web
scripts\start_backend.bat        # 只起 Web（默认 4 进程，WT_WEB_WORKERS 可改）
scripts\start_ocr_worker.bat     # 只起识别进程
.venv\Scripts\python.exe scripts\ocr_worker.py --status   # 看队列与心跳
.venv\Scripts\python.exe scripts\ocr_worker.py --once     # 把当前队列跑完就退（补跑用）
```

**Web 起几个都行，OCR 只能一个**（文件锁会挡住第二个）。多开不会更快：实测两进程并行识别吞吐 0.171 张/s，还不如单进程 0.175。

### 10.6 已知边界（写下来免得以后当成 bug）

1. **心跳是「按数据目录」而不是「按库」**。同一台机上如果同时跑两套库，健康检查会把「A 库的 worker」当成「B 库的 worker 也在」。当前部署只有一个库，不影响；真要多库部署，心跳文件要按库名区分。
2. **队列就是 `image.status`**，没有单独的队列表。好处是不会出现「队列说在跑、图片说完成了」的分叉；代价是不能给不同优先级排队（现在也不需要）。
3. **worker 没启动时上传的图会停在 pending**，`/api/health` 会 `ok=false` 并提示去启动 —— 这是设计意图（宁可报警，不要静默堆积），不是故障。
4. **引擎首次加载约 4 秒**，期间顶栏显示「识别引擎启动中」（黄灯），不是异常。
5. **`--once` 只处理「当前队列」**，不会等新上传的图。

## 11. 前端：左栏树展开/折叠的顿感（2026-11-05 晚）

现场反馈「工艺及工时编排页点展开、折叠明显卡一下」。

### 实测（Edge + CDP，1440×900）

| 动作 | 修复前 | 修复后 |
|---|---|---|
| 件名收起 | 90 ms，**1 个 77 ms 长任务** | 8.6 ms，无长任务 |
| 件名展开 | 75 ms，1 个 60 ms 长任务 | 25 ms，无长任务 |
| 产品收起 | 70 ms，1 个 58 ms 长任务 | 13 ms，无长任务 |
| 产品展开 | 72 ms，1 个 56 ms 长任务 | 18 ms，无长任务 |
| 件名展开（CPU 4× 节流） | 693 ms | 114 ms |

`sync`（点击处理本身）从头到尾只有 0.1~0.2 ms，说明**慢的不是事件处理，是
紧接着 Vue 的渲染任务**。

### 两个根因

1. **纯 JS 渲染成本与「展开行数」同步增长**：整棵树写在 `RouteView` 一个
   render 函数里，10 个产品共 393 行（全量 541 行）。点一次折叠，Vue 会把
   **所有产品所有行**重新 diff 一遍 —— 明明只有一棵子树变了。
2. **`v-show` 让折叠的产品留在 DOM 里**：541 行、5737 个节点常驻，任何一次
   显隐都要让浏览器重算样式与布局。

### 改法

* 新增 `frontend/src/components/TreeProduct.vue`：**一个产品一个组件**。
  行计算（`buildRows`）与折叠状态读取都搬进组件内，`collapsed` 里只有它
  自己的 key 被读 → 点击只让这一个产品重渲染。
* 产品用 `v-if` 而不是 `v-show`：折叠的产品不进 DOM。
* 相应样式（`.tree-product*`、`.tree-part*`、`.tree-caret` 等）从 `RouteView`
  的 scoped 样式里整体迁入组件，避免同一套类名两处漂移。

### 为什么不是虚拟滚动

虚拟列表要处理「产品分组 + 树缩进 + 吸顶」三件事，滚动位置和键盘操作都要
重写；而把渲染范围收到一个产品（最多几十行）已经让长任务消失。等单产品
出现上千行再上虚拟滚动，现在的复杂度不值。

## 12. 结构弹窗：el-tree 展开/折叠的「卡一秒」（2026-11-05 晚第二版）

第 11 节把编排页左栏拆成 `TreeProduct` 之后，用户反馈「还是有 1 秒的卡顿」。
用 PerformanceObserver 的 **event timing**（`duration` = 事件开始 → 下一帧绘制完成）
重新量，找到了另一棵树。

### 量出来的数（541 个结构节点）

| 动作 | 修复前 dev | 修复后 dev |
|---|---|---|
| 全部展开 | **688 ms，长任务 660 ms** | 32 ms 首帧 / 长任务 108 ms / 全完成 ~1.3 s |
| 全部折叠 | 416 ms，长任务 385 ms | 208 ms，长任务 198 ms |
| 打开弹窗 | 64 ms，长任务 103 ms | 56 ms，长任务 92 ms |

之前第 11 节的 67 ms 是**测量基线**（rAF 等待固定 2~4 帧），不是真实成本。
换成 event timing 后，660 ms 的长任务才暴露出来 —— 那段期间页面完全不响应，
就是用户说的「点一下卡一秒」。

### 三个叠加的原因

1. **每个树节点挂着 2 个 `el-tag` + 6 个 `el-button`**。`el-tree` 的节点内容
   是作用域插槽，541 个节点 = 1082 个 el-tag + 3246 个 el-button。`opacity: 0`
   一个都省不掉，组件照样实例化。展开一个产品就是当场建 300+ 个组件。
2. **`全部展开 / 全部折叠` 走 `treeKey += 1`**，等于把整棵 el-tree 销毁重建。
3. **一次性展开 541 个节点**，单个 660 ms 的长任务。

### 改法

* `StructurePanel` 的节点插槽里**不留任何 Element Plus 组件**：状态标签换成
  `<span class="tstate s-...">`（CSS 复刻 el-tag plain 外观），6 个操作键换成
  原生 `<button class="tn-btn">`。
* `expandAll / collapseAll` 不再重建树，直接驱动 `el-tree` 的
  `node.expand()` / `node.collapse()`。`default-expanded-keys` 只在 store 构造时
  读一次（无 watch），所以必须走节点 API。
* **展开按子树分批**（`BULK_STEP = 3`），批间用 `MessageChannel` 让出主线程。
  - 不能用 `await nextTick()`：微任务，整条 await 链还在同一个事件处理区间里，
    浏览器照样一次卡到底。
  - 也不用 `setTimeout(0)`：嵌套调用被钳到 4 ms，50 批就是 200 ms 无谓等待。
  - `MessageChannel` 是宏任务但不受节流，实测总时长从 2.4 s 降到 1.3 s。
* **折叠不分批**，一次性做完且由外向内：它不创建节点，浏览器把所有 visibility
  改动合并成一次重排。切成小批反而每批都逼浏览器重排 541 行 —— 实测从 0.4 s
  恶化到 1.0 s，方向是反的。
* 展开时**刻意不写 `expanded`**：`el-tree` 节点在**新建时**会读
  `default-expanded-keys`，提前把 541 个 key 写进去，展开第一个产品就会顺着
  递归建完整棵子树，分批等于没分。展开状态改由 `rebuildTree()` 从
  `store.nodesMap` 采集后再重建。

### 调参记录（同一个 541 节点场景）

| BULK_STEP | 首帧 | 最长任务 | 全部完成 |
|---|---|---|---|
| 一次全做 | 56 ms | 660 ms | 0.7 s |
| 24 | 120 ms | 264 ms | 0.3 s |
| 2 | 32 ms | 67 ms | 2.4 s |
| 1 | 32 ms | 0 ms | 2.4 s |
| **3（采用）** | **24~32 ms** | **52~108 ms** | **1.2~1.7 s** |

批越细越不卡，但每批都要重绘一次，总时长会涨。3 是当前数据下的平衡点。

### 复跑方式

`data/diag/measure_tree_perf.py`（Playwright + event timing，8000/5173 各跑一遍）。

## 13. 展开/折叠时页面横向漂移（滚动条挤宽度，2026-11-05 晚第三版）

第 12 节把卡顿压下去之后，用户反馈「展开和折叠时页面有轻微漂移，观察发现会
出现纵向滚动条」。这不是渲染性能问题，是**布局宽度问题**。

### 现象与原因

Windows 上经典滚动条占 **15px**。容器从「内容不满、无滚动条」变为「内容超出、
有滚动条」时，可用宽度少 15px，里面的文本/标签整体横向跳一次；折叠回去再跳回来。
两个容器同时存在这个问题：

| 容器 | 为什么会切换滚动条 |
|---|---|
| `.sp-wrap`（结构弹窗树，`height: min(58vh,560px)`） | 默认展开 20 个节点 → 有滚动条；「全部折叠」后内容变矮 → 滚动条消失 |
| `.tree-body`（左栏树，`max-height: calc(100vh-250px)`） | 产品收起时树矮 → 无滚动条；展开到超过上限 → 出现滚动条 |
| `.content`（App 页面级滚动区） | 左栏树变高把整页撑过一屏 → 整页出现滚动条，**所有页面元素一起左移** |

### 改法：`scrollbar-gutter: stable`

给上述三个滚动容器加 `scrollbar-gutter: stable`，滚动条**槽位常驻**：

* 无滚动条时也保留 15px 槽位 → 出现/消失不再改变内容宽度；
* 代价是内容不满时右侧有 15px 空白，与「一直有滚动条」的观感一致，可接受。

```css
/* App.vue */
.content { flex: 1; overflow: auto; scrollbar-gutter: stable; }
/* RouteView.vue */
.tree-body { max-height: calc(100vh - 250px); overflow: auto; scrollbar-gutter: stable; }
/* StructurePanel.vue */
.sp-wrap { height: min(58vh, 560px); overflow: auto; scrollbar-gutter: stable; }
.an-list { max-height: 320px; overflow: auto; scrollbar-gutter: stable; }
```

**为什么不用 `overflow-y: scroll`**：它也能恒定占位，但会画出**禁用态的灰色
滚动条槽**（明明没得滚却显示一条空轨道），视觉更脏。`scrollbar-gutter` 只占空间
不画轨道，是标准做法。

**为什么不用 `::-webkit-scrollbar` 自定义细滚动条**：把宽度从 15px 改成 8px 只是
减小跳动幅度，没有消除；而且会改变全站滚动条外观。

### 验证（`data/diag/drift_check.py`）

headless Chromium 默认 overlay 滚动条（宽 2px，不占布局），量不出问题，所以在页面
里注入 `::-webkit-scrollbar { width: 15px }` 强制经典占位滚动条来还原真实环境。

| 场景 | 动作 | 容器 clientWidth | 首行 left |
|---|---|---|---|
| 结构弹窗 | 初始 | 991 | 219 |
| | 全部展开（541 节点） | **991** | **219** |
| | 全部折叠 | **991** | **219** |
| 左栏 | 收起态 | 295 | — |
| | 展开 6 个产品 | **295** | — |

三个状态宽度完全一致，差 0px。同一容器把 `scrollbar-gutter` 临时改回 `auto`，
宽度立刻变成 1006（多 15px）—— 反证跳动的就是这 15px。

### 顺带的经验

`scrollbar-gutter: stable` 只对**自身是滚动容器**（`overflow` 非 `visible`）的元素
生效。给 `.content` 加上就能一次性兜住全站所有页面的「滚动条出现导致整页左移」，
不必逐页改。
