# 工时识别核算系统

车间《加工路线单》（业务上就是**报工单**）从「纸」走到「工资」的一套系统。

它不只是「把照片识别成表格」，而是完整的一条工资链条：

```
工艺卡（定额：该怎么干） → 报工单（实际：干成什么） → 报工工时 → 工时工资
```

技术栈：FastAPI + SQLite + SQLAlchemy 2 · PaddleOCR（默认 PP-OCRv6 small）· Vue 3 + Element Plus + Vite。

## 一、业务链条与定位

现有流程是纯手工转抄：纸质工时单 → 人工录入 Excel → 人工汇总。实测 `doc/9月2车间工时核算.xlsx`
后发现 5 类系统性缺陷（详见 `docs/工时识别系统设计方案.md`）：

| 缺陷 | 实测证据 | 系统对策 |
|---|---|---|
| 总工时表与个人明细表不勾稽 | 13/13 人全部不符，偏差 -112.67 ~ +423.08 小时 | 三级勾稽校验，差异 > 0.5h 阻断导出 |
| 工时存成 Excel 日期值溢出 | 显示 `5 days, 0:00:00`，无法求和 | 工时统一存小时小数，另加 `[h]:mm` 展示列 |
| 有单件工时但合格件数为空 | 袁红华 45%、王国良 61% 的行合计被静默计 0 | `QTY_MISSING` 告警，不再静默 |
| 月份/年份口径混乱 | 文件名 9 月、标题 2025/2026 混用、总表写 6 月 | 核算期强绑定，日期越界即告警 |
| 结构不稳定 | 列数 11~14 浮动、序号跳号、合计行异常值 | 明细行标准化，计算列由系统重算 |

### 两条报工通道，一张纸只算一次

现场的取舍是明确的（用户拍板，不要擅自改）：

```
系统按任务预印《加工路线单》（一个件名一张纸，右上角带二维码）
  → 工人加工、在纸上填数量并签字
  → 计划员收单，扫码 → 屏幕上核数（不合格/报废就地调整）→ 提交
```

- **扫码的是计划员，不是工人。** 让每个工人掏手机扫的项目基本都失败了；计划员本来就要收单打字，
  他只是把「打字」换成「扫一下改两个数」。
- 纸质签字是凭证，电子数据是账；两者靠 `print_sheet.form_no`（印刷体单号）绑定。
- OCR 仍是必要通道：历史补录、外协件、断网现场、外包队用纸。
- **两条通道以单号互认。同一张纸绝不能算两次工时**——那等于多发一份工资。

## 三、快速开始

### 1. 环境要求

- Windows 10/11
- **Python 3.11 或 3.12**（PaddlePaddle 没有 3.13 的 wheel，3.13 装不上）
- Node.js 18+

### 2. 安装

```bat
scripts\setup_env.bat
```

首次会下载约 1GB 依赖（PaddlePaddle 较大），请耐心等待。

### 3. 启动

```bat
scripts\start_all.bat
```

它会依次开两个窗口：**OCR 识别进程**（预热约 4 秒）+ **Web 服务**，浏览器访问
<http://127.0.0.1:8000>。也可以分开启动：

```bat
scripts\start_backend.bat      :: Web，默认 4 个 worker（WT_WEB_WORKERS 可改）
scripts\start_ocr_worker.bat   :: OCR 识别进程，只能开一个
scripts\start_frontend.bat     :: 前端开发模式 http://127.0.0.1:5173
```

开发时前后端分离：`cd frontend && npm run dev`，代理默认指向 8000
（`API_TARGET` 可改，用于「指向库副本的演示后端」而不碰生产库）。

> **只启 Web 不启 OCR 进程，上传的照片会一直停在「待识别」。** 这不是 bug：
> `/api/health` 会 `ok=false` 并提示启动识别进程。识别引擎只在 worker 里加载，
> Web worker 不背 Paddle——这是多进程能在 7GB 可用内存上成立的前提。

### 4. 首次登录

首次启动自动建管理员 `admin / admin123`（`WT_DEFAULT_ADMIN_PASSWORD` 可改），
**登录后立刻改密码**。单机部署默认 `WT_TRUST_LOCAL=1`，本机 loopback 请求免令牌
（身份记为「本机操作员」）；需要严格身份时置 `WT_TRUST_LOCAL=0, WT_AUTH_REQUIRED=1`。

### 5. 初始化顺序

1. **系统管理** → 产品 / 工序 / 材料 / 件名 / 人员 / 岗位角色（这些就是识别兜底名册）
2. **产品结构**（工艺编排页左栏「结构」或工时组合页「产品结构」）→ 建装配层级与每台用量
3. **工艺及工时编排** → 给件编工序与定额 → 发布
4. **生产任务** → 建任务、挂件名（自动引用已发布工艺）
5. **工艺卡** → 打印带二维码的《加工路线单》发给车间
6. 车间填完签字 → **扫码报工**（主通道）或拍照 → **导入与识别**（兜底）
7. **核对工作台** → 逐字段核对确认
8. **月度汇总 → 工资核算 → 导出与勾稽**

### 6. 核对页的几个约定

核对页右上角的 **修改留痕** 记录每一次人工改动（谁、什么时候、把哪个字段从什么改成什么）。
字段名与取值都按中文展示：`item:qualified_qty` 显示为「合格件数」，`worker_id=13` 显示为「马永刚」，
`recognized/verified/rejected` 显示为「待核对/已确认/已作废」，明细改动还会标出「第几行」。
留痕只读、不参与任何计算；明细行每次「重新识别」都会被重建，所以留痕另存了一份单据 id，
避免历史记录跟着行 id 一起消失。

**重新识别的语义**：它就是「按原图重跑一遍」，但**不会推翻你手动核对过的值**——
人工改过的字段（合格件数、工序、工作者、表头等，取自修改留痕）会在新结果上原样盖回去，
其余字段按新识别结果更新，保留下来的行标成 `edited`。已确认的单据必须先「撤销确认」
才能重新识别，防止一次点击把已确认的数据打回待核对。真被覆盖掉的行会写一条
「重新识别覆盖」留痕，记下丢掉的原值。

点「重新识别」会先弹一个确认框，把「哪些字段会被保留」逐条列出来（第几行 / 字段 / 当前值），
默认勾选「保留」；不想保留就取消勾选，那些字段改用本次识别结果，同时写一条「放弃人工修改」
留痕，保证再点一次重新识别也不会把旧值捞回来。

识别是异步的：点完之后**页面会立刻按数据库现状刷新一次**（表格里没保存的改动就此丢弃），
顶部出现「正在重新识别…」进度条，识别跑完自动刷新明细并弹出「共 N 处变化」的对比提示。
手工改动如果不点「保存」，就不在数据库里，也就不存在「保留」一说——它会在点重新识别的一瞬间被丢弃。

## 四、系统架构

### 进程模型（定型，别再合回一个进程）

| 进程 | 干什么 | 不干什么 |
|---|---|---|
| Web（uvicorn，默认 4 worker） | 接口、页面、上传落库、把图标 pending | **不加载 Paddle、不跑识别** |
| OCR worker（`scripts/ocr_worker.py`，单实例文件锁） | 领取 pending → 识别 → 落库；启动自愈；组合同步 | 不对外提供服务 |

- **队列就是 `image.status`**（pending → processing → done/failed），没有单独的队列表。
  好处是不会出现「队列说在跑、图片说完成」的分叉。
- `claim_next()` 两步：挑候选 → `UPDATE ... WHERE id=? AND status='pending'`，
  只有 `rowcount==1` 才算领到。并发领取不会重复识别（重复识别 = 重复入账 = 多发工资）。
- `resume_orphaned()` 只在 worker 启动时跑，且 `attempts >= 3` 直接标 failed ——
  否则毒图会造成「启动→崩→启动」死循环。
- OCR **只能开一个**：实测两进程并行吞吐 0.171 张/s，不如单进程 0.175，还多占 400MB。

实测收益（同机同库、8 并发）：`/api/tasks` 6.4 → 40.1 req/s，`/api/combos` 1.9 → 24.3 req/s。

### 数据流

```
上传照片 ──→ image(pending) ──→ OCR worker ──→ sheet(recognized) ──┐
                                                                    ├─→ work_item ─→ 月度汇总 ─→ 工资
扫码预印单 ──→ print_sheet(reported) ──────────────────────────────┘
```

### 一张纸 = 三个视图（不要混）

| 对象 | 是什么 |
|---|---|
| `PrintSheet` | 预印单：印出去那一刻的快照（无照片、带 token） |
| `Sheet` | 识别单：填完的纸读回来（有 `image_id`） |
| `WorkItem` | 报工明细：两源共用（`source` = ocr / scan / manual） |

`work_item.sheet_id` 可空；扫码明细自带 `period_id` / `task_id`。
**按核算期取明细必须 outer join + `coalesce(Sheet.period_id, WorkItem.period_id)`**，
否则扫码工时进不了工资表——而且不报错，只是少算几个人的钱。

## 五、报工通道 A：预印单 + 扫码（主通道）

### 流程

1. **工艺卡页**「预览打印」或 **扫码报工页**「打印预印单」打印《加工路线单》，
   右上角印二维码与印刷体单号（`RG{YYMM}-{00001}`）。
2. 工人加工、填数量与工时、签字。
3. 计划员**扫码报工** → 屏幕带出该单每一行的件名、工序、定额、计划件数，
   **完成数 / 合格数默认按计划带入**，只需改有差异的行。
4. 返修、报废行必须点「复核」才算认过；`合格 + 返修 + 废品 > 完成数` 前端先拦。
5. 提交 → 生成 `work_item`（`source='scan'`），单据进入月度汇总与工资表。

### 二维码的硬规矩

- 只装 `HY1:<form_no>:<token>`（约 26 字符），**不装定额/件数/金额**。
  码里带定额等于让一张纸决定工资；纸被改、被复制都没人知道。
- 位置固定在页面**右上角 14mm 见方**（x=266 / y=3mm），**必须在表格之外**：
  表格里多一块黑白方块，`form_spec.COLUMNS` 的列锚点会被破坏，识别侧整张单列错位。
- token **存库**而不是纯签名：纯签名防伪造但**没法作废**。单子印错、零件不做了，
  那张纸还在工人手里，扫了照样能报工。存库 + `print_sheet.status='void'` 让码立刻失效。
- 唯一实现在 `app/render/qr_stamp.py`；工艺卡打印、预印单打印、页面预览三处共用。
  三处各建一套单号 → 同一张纸两个号，扫码只认一个，其余永远报不了工。
- **单号只在真正打印（或单张预览）时生成**；`create=False` 的批量预览不建单。

### 十道闸门（`print_sheet.submit`）

已作废 → 已报工 → 未勾签字核对 → 任务结案/取消 → 同号识别单已入账 →
锁账拒收 → 未来日期 → 逐行校验（合格+返修+废品 > 完成数，**整单拒绝**）→
去向不明 / 超计划 → 返修报废缺原因拒收。

- 提交是「先校验再原子翻状态」：`UPDATE ... WHERE status='printed'`，`rowcount != 1` 即被抢。
- 幂等入口是 `print_form_no`：重复提交拒绝并返回 `ALREADY_REPORTED` 给撤销入口。
- **已报工的件重印沿用原号，绝不发新号**——新号能扫能再报一遍，等于重复发工资。
- 撤销必填原因（≥2 字），审计记「原 n 行 / x 小时 → 原因」；作废只对未报工的单。

### 两通道互认

`qr.find_form_nos()` 从 OCR 文本里提取印刷体单号，数字位放宽 `0-9OoQDlIi|ZSB`，
分隔符容忍连字符被吞。**只提候选，必须查库命中才算数**——认错等于没认出，不猜。

- 命中 `reported` / `void` → 识别单直接 `rejected` 并写原因（不进账，防重复计薪）。
- 命中 `printed` → 绑定，识别单与预印单归为同一张纸。
- 命中多张（ambiguous）→ 只写备注不绑定，交人工。
- 重识别读不到号时**保留原绑定**，不清空。

## 六、报工通道 B：OCR 识别（兜底）

### 流水线

```
上传图片（同图去重：同一张照片重复拖入会跳过并指出已有 image_id）
  ↓ ① Pillow 预处理
  EXIF 方向校正 → 长边归一 2000px → 投影法倾斜校正
  → 红笔/红章抑制（R-max(G,B) 掩膜置白）→ 对比度增强 + 锐化
  ↓ ② PaddleOCR 全文识别
  输出 (文本, 四点坐标, 置信度)
  ↓ ③ 结构定位
  表格线检测（行/列投影）→ 印刷体表头锚点定义列 → 每段文字归入单元格
  ↓ ③b 数量列单格补检（app/ocr/cellprobe.py）
  合格/返修/废品三列里整页完全没检出的格子，砍格去线后单独跑一次识别
  ↓ ④ 字段抽取
  表头键值对 + 明细行按列取值
  ↓ ⑤ 字段归一
  工时：25H / 2:30 / 2h30 / 1天 / 2.5 → 小时小数
  日期：7.15 / 2026.7.15 / Excel 序列号 → 补全核算期年份
  人名：名册白名单 + 编辑距离（封闭集匹配，不做开放识别）
  工序：工序字典 + 尾号剥离（铣1 → 铣）
  产品/材料：字典 + 别名；精确命中保留原文，错字才纠偏
  检验员/接交人：按角色名册匹配，残字走姓氏兜底
  ↓ ⑥ 规则校验 → 告警
  ↓
入库 status=recognized（待核对）
```

单张耗时约 5~9 秒（本机 CPU，含预处理）；一册 50 张约 4.8 分钟。

### 为什么红笔抑制是关键

现场用红笔圈注姓名、红色表格线与印章是 OCR 的主要误检源。预处理把红色像素置白后再识别，
同时单独留存红色掩膜，用于识别「被红笔标注的姓名」这一业务信号。

### 为什么人名不做开放识别

车间人员是有限集合。识别文本与名册做编辑距离 + 包含匹配，取 top1 且分数过阈值才自动填充，
否则留空由人选择。这比通用 OCR 可靠得多。

**签名照样认不准，所以做了三件事。** 用真单据实测：杜文杰的签名被读成「定生」，
OCR 置信度只有 0.35——草书签名是「人眼一秒、模型十分钟」的典型。

1. 核对页「检验员」改成名册下拉（可 allow-create 新名字），旁边挂一张**签名缩略图**，
   点开放大。与其让模型猜草书，不如让人看一眼就选。
2. 签名格的 OCR 原文单独存 `inspector_raw`，和最终人名分开。界面显示「原文 定生」，
   一眼能看出这是识别结果、不是人名。
3. **人工改正的那一刻自动记别名**：把签名原文记到该人名下（`app/services/learn.py`），
   下次同一写法直接命中。规则很克制——只对已确认的人工修改生效，绝不自己猜；
   原文已被别人占用就不写；每人最多 20 条。操作者列同一套机制。

历史单据批量补：`python scripts/learn_alias.py 杜文杰 定生 --sheet 7`（`--all` 全库、`--dry` 只看）。

### 手写工时的写法（用户确认，最高优先级）

「定额工时 / 单件」栏：

| 手写 | 含义 | 说明 |
|---|---|---|
| `2ʰ` | 2 小时 | ʰ 是**上标 h** |
| `30'` | 30 分钟 | `'` 是**上标的分符号** |
| `1ʰ30'` | 1 小时 30 分 | 时 + 分组合 |

OCR 现实与对策：上标 `ʰ` 常被认成 `u`/`U`/`4`/`1`/`°` 或直接吞掉，`'` 常被吞掉。
`1ʰ30'` 可能变成 `1430` / `130`，`2ʰ30'` 变成 `2030'`。
**纯数字 > 24 小时一律视为「丢了分钟符号」**，按「首位=小时、末两位=分钟」还原——
正常单据工时 ≤ 8 小时，这个阈值不会误伤。

### 为什么合格件数会「看不见」

合格 / 返修 / 废品三列手写时经常只有一个 `1`——一根孤立、细长、紧贴格线的竖笔画。
DB 文本检测器会把这种形状判成表格线，**根本不出候选框**。

这不是调参能解决的，实测过（同一张单据，结论可复现）：

| 尝试 | 结果 |
|---|---|
| `text_det_limit_side_len` 960 / 1536 / 1920 | 0 检出 |
| 再加放宽 `det_thresh=0.15`、`box_thresh=0.3`、`unclip_ratio=2.2` | 0 检出 |
| 换 `PP-OCRv5_server_det`（更强检测模型，单张 39 秒） | 0 检出 |

所以采用「绕开检测网络」的补检（`app/ocr/cellprobe.py`）：版面已经知道列边界和行高，
把目标格直接裁下来、去掉格线、放大，只送**识别网络**。同一个格子实测：含表头字时误识成 `9`，
按行带精确裁剪并去线后稳定输出 `1`。

防误报的五道闸（缺一不可，都是踩过坑才加的）：

1. **只补空格子**：整页 OCR 在该格已有文本的，一律不动。
2. **行必须是真明细**：该行至少已识别出单件工时 / 工作者 / 工序 / 日期之一。
   否则页面底部「计划调度」签名区会被补成一条合格件数=1 的假明细。
3. **笔画必须完整**：去线后裁剪框四边若还有墨，说明笔画被框切断了，直接丢弃。
   实测被切掉下半截的 `1` 会被读成 `7`（score 0.93）——错值比空值危害大得多。
4. **只认纯数字且够分数**：`^\d{1,4}(\.\d{1,2})?$`，score ≥ 0.5。
5. **形状兜底**：笔画压在表头里、常规裁剪必然切断时，改用连通域形状判定——
   去线后恰有一个高宽比 ≥2.2、宽度不超过格宽 60%、纵向 ≥55% 落在数据行核心区、
   且顶端伸进表头区的连通域。只认 `1`，因为它带横向笔画的兄弟整页检测器本来就能看见；
   放宽到 `7` 会跟表格竖线残片混淆。

可调开关：`WT_CELL_PROBE=0` 关闭补检；`WT_CELL_PROBE_CONF` 调阈值；
`WT_CELL_PROBE_MAX` 限制单张最多补检多少格（默认 40）。

## 七、工艺域：结构 / 工艺 / 版本

### 结构与工艺是两张表（定案，别再合并回去）

| 对象 | 表 | 回答什么 | 入口 |
|---|---|---|---|
| 产品结构 | `product_node` | 谁装在谁下面、每台几件、同级先后、这一批做几件 | 「产品结构」弹窗 `StructurePanel.vue` |
| 工时组合 | `work_combo` | 这个件有没有工艺、发没发布 | 工时组合台账 |
| 工艺路线 | `process_route` | 这个件怎么做、几道工序、多少工时 | 工艺及工时编排 |

- 结构与工艺以 **`(产品, 件名)`** 关联，没有外键。工艺卡 / 工时汇总沿结构展开、按每台用量加权。
- `work_combo` 上的 `parent_id / level / qty_per_unit / seq / level_src` 是**死列**，
  已停止读写（迁移后保留只为免删表风险）。新代码一律走 `ProductNode`，字段叫 `source` 不叫 `level_src`。
- 建工时组合时必须同步 `ensure_node()`——只建组合不建节点，这件在结构里就不存在，
  自动铺层和工艺卡都看不见它。
- 工艺卡把结构值盖到 ORM 对象上要用 `set_committed_value()`，直接赋值会被当成脏字段写回死列。
- 审计分流：结构改动记 `entity="node"`，组合改动记 `entity="combo"`，两套 id 不能混。

### 计划生产数量

「数量」= **计划生产数量**（不是每台用量），存在 `product_node.plan_qty`，与生产任务的订单数量
互不干扰。父子都能改：**改上级按用量推下级，改下级按用量反推上级**（除不尽向上取整，
台数不能是 1.5，取整前后都进 warnings）。人工设定的 `plan_src='manual'` 不会随上级变，
界面用 `plan_expect` 标黄提示「按当前上级应做 N 件」——人的决定优先，但差异要看得见。

### 版本与发布

- 草稿可改；**已发布不许就地改，只能「升版修改」**——发 v2 草稿，旧版继续当基准，
  改完再发布才切换。这样改工艺的期间不会出现「没有基准」的空窗。
- **升版会顶掉在用的基准**，所以必须有人确认：`route_version_notice` 记录每一次
  vX→vY，相关任务的路线行标红「升版待确认 N」，保存/提交前弹确认，
  两个出口「采用新版」或「按我确认的那版固化为副本」。
- 工艺卡**只印已发布**（闸在 `work_combo.status='released'`），编号只按已发布连续编
  （根 `01` → 部件 `01-01` → 子件 `01-01-01`）；上级是草稿时，下级在本子里当顶层。
- 三个工时口径并排，不要混：**本层**（报工只认这个）/ **含子件**（下级按 `qty_per_unit` 加权）/
  **产品单台**。含子件必须加权，否则一台机器重复装的零件只算一次，定额天生偏低。

### 工艺卡 = 加工路线单

工艺卡不是新东西，它就是加工路线单的「还没干活」阶段。`app/services/card_print.py` 只做
「工艺卡 → 版面格」映射，交给 `app/render/route_form.py` 渲染——与识别侧共用同一份
`form_spec.COLUMNS` 列锚点。预印：件号（带层级编号）、类别、投产台数、加工件数、工序名、
单件定额（`2ʰ/30'/1ʰ30'`）、合计、小计。

**留白**：操作者 / 合格·返修·废品 / 检查员 / 日期 / 计调员 / 材料员 —— 这些都要人签，预印等于编数据。

## 八、核算口径

口径参数集中在 `app/config.py`，可用环境变量覆盖：

| 项 | 默认 | 环境变量 |
|---|---|---|
| 一天折算小时（仅单据明写「天/日」时生效） | 8 | `WT_HOURS_PER_DAY` |
| 返修件折算系数 | 0（不计工时） | `WT_REWORK_FACTOR` |
| 废品折算系数 | 0（不计工时） | `WT_SCRAP_FACTOR` |
| 勾稽容差 | 0.5 小时 | `WT_RECONCILE_TOLERANCE` |
| 跨天工时提示阈值（超过即提示，可放行） | 8（1 个工作日） | `WT_UNIT_HOURS_WARN` |
| 单件工时上限（超过即阻断） | 200（约 25 个工作日） | `WT_UNIT_HOURS_LIMIT` |
| 金额核算开关 | 关 | `WT_ENABLE_AMOUNT` |
| Web worker 数 | 4 | `WT_WEB_WORKERS` |
| OCR 重试上限 | 3 | `WT_OCR_MAX_ATTEMPTS` |
| 本机免令牌 | 开 | `WT_TRUST_LOCAL` |
| 默认管理员口令 | admin123 | `WT_DEFAULT_ADMIN_PASSWORD` |

**合计工时 = 合格件数 × 单件工时 + 返修 × 系数 + 废品 × 系数**，由系统重算，
不采用手写合计（手写值只作对照告警）。两个系数默认 0，所以现状事实上是**按合格数计件**——
只有合格数产生工资，**改这两个系数前必须问用户**。

### 单件（定额）工时的计量口径

定额工时是工艺给定的标准值，**一件活可以跨多个工作日，不能用「一天几小时」封顶**。

实测依据（9 月真实数据，986 行明细）：单件工时中位数 0.67h、p95 为 10h、**最大 96h**
（对辊镗 4 个班）；真实单据手写为 `25H` 这类直接带小时单位的写法。因此：

- **单位统一为小时**，`25H`、`2:30`、`2.5`、`30分` 一律归一为小时小数
- `> 8 小时` → `跨天工时` warn，附「≈N 个工作日」换算，确认无误即可放行
- `> 200 小时` → `单件工时异常` block，几乎必然是漏了小数点或多认一位数字
- 只有单据文字**明写「天/日」**时才按 `WT_HOURS_PER_DAY` 折算，避免把「4 天」误当 96 小时

### 告警分级

| 级别 | 含义 | 表现 |
|---|---|---|
| `block` | 数据不可用或明显误读，必须处理 | 禁止确认，需强制确认才放行 |
| `warn` | 数据可疑，允许人工判断后放行 | 黄色提示，可确认 |

告警码：`QTY_MISSING`、`UNIT_HOURS_ABNORMAL`、`UNIT_HOURS_MISSING`、`TOTAL_MISMATCH`、
`DATE_OUT_OF_PERIOD`、`DATE_MISSING`、`UNKNOWN_WORKER`、`UNKNOWN_PROCESS`、`LOW_CONF`、
`NO_ITEM`、`MISSING_PRODUCT`、`MISSING_PART`、`MISSING_PROCESS`（block）、`DIM_MISSING`、
`UNKNOWN_PRODUCT`、`UNKNOWN_MATERIAL`、`UNKNOWN_INSPECTOR`、`UNKNOWN_HANDOVER`。

### 三级勾稽

个人明细 → 人员合计 → 总工时，差异 > 0.5h 阻断导出。
**账内/账外要分开判**：未入账单据（待核对、驳回、作废）不参与 error 判定，
否则一张作废单能永久挡住整月导出。

## 九、工资核算

**金额 = round(该人该月报工工时 × 该月工时单价, 2)**，合计由各人金额相加。
**不要拿总工时 × 平均单价**——会差几分钱，财务必退。

- 表 `worker_rate(worker_id, effective_ym, rate, note)`，唯一约束 `(worker_id, effective_ym)`。
  **单价按生效月留档**，取「生效月 ≤ 核算月」的最近一条；同月再写 = 改这条并进审计。
  绝不在 `worker` 上放「当前单价」——那会让历史工资表随调价而变。
- 两条不能静默：**没设单价 ≠ 工资 0 元**（页面标「未设单价」并计数）；有未确认报工单时，
  工资表只是半成品（顶部横幅提示）。
- 导出门槛与汇总导出同口径：勾稽 error / 有待核对单据 / 有人未设单价 → 400 并列明原因，
  可 `preview=1` 导预览版。
- 工时取自 `monthly_summary()`，扫码与 OCR 两源都在内（见第四节的 outer join 口径）。

接口：`GET /api/wages`、`GET/PUT /api/wages/rates`、`GET /api/wages/export`。
代码：`app/domain/wages.py`、`app/api/wages.py`、`export_excel.build_wage_workbook`、
`frontend/src/views/WagesView.vue`、系统管理「工时单价」卡片。
文档：`docs/工资核算_工时单价与工资表.md`。

## 十、权限：三层

这套系统里「角色」有两个，再加「职能」，一共三层，各自回答不同问题：

| 层 | 存在哪 | 取值 | 回答什么 |
|---|---|---|---|
| **系统角色** | `app_user.role` | admin / editor / viewer | 能走到哪一步（能不能写、能不能管账号/备份） |
| **岗位角色** | `role` + `worker_role` | 工作者 / 检验员 / 接交人 / 计划员… | 车间里是谁、进哪份识别名册 |
| **岗位职能** | `role.duties` | 任务编制 / 工艺卡编制 / 报工 / 工时单价 | 这个岗位能承担哪几件系统功能 |

一句话：**系统角色定上限，岗位职能定边界，岗位角色定身份**。

- 一个人可以是检验员，但根本没有账号——他不录单，只是单据上签名。
- 一个账号可以是只读，对应的人却是老师傅——他只是进来看台账。
- 一人多岗很常见：把两个岗位都挂上，职能取**并集**。
- 所以 `app_user` 上**没有 role_id**，只有 `worker_id` 指向名册里的人。

### 判定顺序（`require_perm`，顺序不能换）

1. **管理员直接放行**（运维身份不该因没挂岗位做不了事）
2. **职能类权限** → 看岗位职能并集
3. **其余权限** → 看系统角色

第 2 步排在第 3 步之前是故意的：editor 本来没有 `wage_rate` 硬权限，但要能由「核算员」岗位授予。

### 「没配职能」不锁人

`DEFAULT_DUTIES_BY_ROLE`：editor 默认 = 任务 + 工艺 + 报工（等价改造前），viewer 空。
**一旦该人任一岗位勾了职能，就严格按并集判定**，没勾的立刻失效。

这是刻意的取舍：不设兜底 → 升级当天所有历史账号瘫痪；只兜底不收紧 →
「必须由专用岗位执行」落不了地。viewer 即使挂岗位也不会提权（默认职能集为空）。

**基础数据不按岗位授**：计划员遇到新件名、新工序得当场能加，按岗位授权会卡住活。
备份与账号管理只给管理员。

### 只读是真的拦

`app/main.py` 中间件对无 `business` 权限的写请求返回 403 `READ_ONLY`，
不只是界面把按钮变灰。唯一例外是 `/api/auth/password`（否则密码过期死锁）。

唯一的管理员不能被降级（否则没人能管账号）；未知 role 降级为只读、不报错
（让人登不进来更糟）；本机免登录仍是 admin。

文档：`docs/系统角色与岗位角色.md`；真源：`app/domain/sys_roles.py`（界面矩阵直接渲染它）。

## 十一、备份与恢复

### 备份：整库全量

底层用 `VACUUM INTO`（WAL 模式下直接 `cp` 主文件会得到空壳——已用测试钉住）。

**关键设计：出厂清单 sidecar。** 备份时在 `.db` 旁边写 `xxx.db.json`，记录当时源库的
表清单与各表行数。难点是「备份比现在少几张表」到底算坏还是正常——`worker_rate` 是后加的、
`print_sheet` 也是后加的，历史备份本来就少。分不开这两种情况，所有老备份都会被误标红
（实测 5 份里 3 份）。

- 有清单 → 对着清单核表，缺一张即红（与当前库无关）
- 无清单（老备份）→ 退回「核心表都在」兜底，不误报
- 与当前库的结构差/行数差 → 只提示（`schema_gap` / `row_delta`），不参与判定

清单**不放在库里建表**：备份文件必须与源库一模一样，恢复回去不能凭空多一张表。

```bat
.venv\Scripts\python.exe scripts\backup_db.py            :: 备份一次
.venv\Scripts\python.exe scripts\backup_db.py --list     :: 列出并逐份校验
.venv\Scripts\python.exe scripts\backup_db.py --verify x.db
.venv\Scripts\python.exe scripts\backup_db.py --keep 14  :: 只保留最近 14 份
```

### 恢复：在线事务，不覆盖库文件

服务是多进程（Web 4 worker + OCR worker），库文件被一堆连接占着。Windows 上替换文件
本身就失败；就算成功，其他进程手里还有旧 WAL/页面缓存，接着写会把恢复结果冲掉。

所以在线恢复走**标准 SQL 事务 + 整表替换**：
`ATTACH 备份 → BEGIN IMMEDIATE → 逐表 DELETE/INSERT → COMMIT`。
换来三件事：单事务可整体回滚、不用重启、结构不降级（只覆盖数据）。

规则：

- 恢复前自动 `snapshot('-pre-restore')`，失败就中止（没有回退方案的覆盖不做）
- 备份里有、当前库没有的表 → **保留不动**。清空 `worker_rate` 等于把后来录的单价全抹掉
- 备份缺的新列 → 用列默认值
- 备份校验不合格 / 空壳 / 识别队列非空 → 拒绝恢复，当前数据一个字节不动
- 文件名只认 `backup_dir()` 里的 `worktime-*.db`，`resolve_backup()` 挡路径穿越
- 审计 `backup:restore` **写在恢复之后**（audit_log 也被覆盖），含回退快照名
- 恢复后 `engine.dispose()` 重建连接池

两条通道：

| 场景 | 通道 | 停服 |
|---|---|---|
| 误删数据 / 数据乱（库正常） | 系统管理 → 备份 → 恢复 | 不用 |
| 库文件损坏 / 换机器 | `scripts/restore_db.py`（`os.replace` 原子替换，替换后必删 `-wal`/`-shm`） | 必须 |

> 备份范围仅数据库文件。`data/uploads` 里的原始单据照片需另行同步（界面已注明）。

文档：`docs/数据备份_整库全量口径.md`。

## 十二、导出格式

### 工时汇总（与现有《车间工时核算.xlsx》同构）

- **每人一个 sheet**：`{年}年{月}月份个人完成工时汇总表`，第 3 行表头，末行合计
- **总工时 sheet**：`序号 | 人员 | 工序 | 工时 | 工时(时:分)`，一人多工序多行
- **口径说明 sheet**：生成时间、口径参数、总工时

与旧表的关键差异（已修正缺陷）：

1. 「单件工时」「合计工时」存**小时小数**（格式 `0.00`），可直接求和；
2. 新增「合计(时:分)」列，用 `[h]:mm`，显示 `25:00` 而不是 `1 day, 1:00:00`；
3. 完成时间统一为 `yyyy-mm-dd` 日期型。

### 工资表

每人一表（原 11 列逐字不动 + 合计(时:分) + 工时单价 + 工时工资）+ 总工时（原样保留）
+ 工资汇总（新增）+ 口径说明。

> **凡是让浏览器下载文件，优先同源 URL，不要走 blob。** 内嵌浏览器/受限预览环境会静默拦掉
> `blob:` 下载，界面零反馈，表现就是「按钮像坏的」。下载链接要 `target="_blank"`，
> 否则接口报错时返回的 JSON 会把整个 SPA 跳走。

## 十四、环境适配

PaddleOCR 在 Windows/CPU 上有三个坑，本系统已全部处理，改环境时不要回退：

| 问题 | 现象 | 当前处理 |
|---|---|---|
| 模型源被墙 | `No available model hosting platforms detected` | `PADDLE_PDX_MODEL_SOURCE=bos`（engine.py 顶部设置） |
| oneDNN 算子不兼容 | `ConvertPirAttribute2RuntimeAttribute not support` | `enable_mkldnn=False` |
| 关闭 oneDNN 后变慢 | 单张 40~60 秒 | 换 `PP-OCRv6_small_det/rec` + `text_det_limit_side_len=960`，降到 5~9 秒 |

版本组合：`paddlepaddle==3.3.1` + `paddleocr>=3.7.0` + Python 3.12。
`paddlepaddle==3.0.0` 会报 `Type of attribute: strides is not right`，不要用。

模型可换（`app/config.py`）：`WT_OCR_DET_MODEL`（默认 `PP-OCRv6_small_det`）、
`WT_OCR_REC_MODEL`（默认 `PP-OCRv6_small_rec`）、`WT_OCR_DET_LIMIT`（默认 960）、
`WT_OCR_LANG`（默认 `ch`）。**换模型必须重跑 `recheck_all.py` 对比**——
识别结果会变，而库里存的是当时的结果。

## 十五、真实单据的版面规则

真实照片的表格比合成样张难得多，以下规则都是为了修具体错例加的，别随手删：

| 规则 | 为什么 |
|---|---|
| 列边界按**标准模板的相对列宽拟合**，不是相邻锚点的中点 | 锚点是文字中心，格子宽窄悬殊（序号 7.7mm / 工序等级 65.3mm）时中点会落进宽格内部靠左——正是手写工序名的起笔处，结果工序整列为空。拟合 `x = b + s·rel`（12 个列头求 2 个参数），残差太大自动退回中点方案；版式定义在 `app/ocr/form_spec.py` |
| 纠偏必须精确到 0.1° | 0.5° 的残差就能让 1000px 高的竖线横移 8px，`detect_lines` 一条竖线都检不到。两段搜索：0.5° 粗扫 + 0.1° 细扫 |
| 列区间由表头标签的 x 坐标定义 | 手写值本身没有「列」信息，只能靠印刷表头定位 |
| 「数量」「序号」是**占位列**（`COLUMN_RESERVES`），不直接入库 | 漏掉它们会让相邻两列被并进同一格：实测「数量 2」+「单件 4:10:00」被拼成 `24:10:00`，「合格 2」+操作者签名被拼成 `22` |
| 「操作者」等同「工作者」 | 不同单据写法不同，缺这个锚点签名会跑到别的列 |
| 一个格子里挤多个子表头时按字符位置切分 | `合格返修` 被识别成一串时，按字宽插值出两列的中心 |
| 表头取值按「值左边最近的标签」全局配对，排序用 `dy×5 + dx` | 按「标签右边最近的文本」取会在标签密集时串行：`投产台数`/`产品名称` 抢同一个值。只按横向距离排序也不行——跨行标签的 dx 可能更小 |
| 第 2 个「件号」格归到件名 | 标准表把「件号」「类别」各印了两遍，第 2 格现场写的是件名 |
| 遇到「小计：」行就截断明细 | 小计行后面是「车间主任／计划调度／日期」表尾，不截断会把「计划调度」写进操作者列 |
| 「只有工序、没有数字」的行算残片，可与相邻行合并 | y 聚类会把一行的工序和数字切成两行 |
| 工时支持 `H:MM:SS` / `H:MM` | 手写常用时间格式，`4:10:00` = 4.1667 小时 |
| 空行、表尾合计行、杂字行不算明细 | 一张只有 1 行数据的单子曾被拆成 4 行（3 行是噪声） |
| 工序开头的序号要去掉 | 序号格与工序格粘连成 `1包板折弯` |
| 工序名只是原文一小段时不收敛 | `包板折弯` 曾被压成 `折弯`；复合工序保留原文并告警「工序未入典」 |
| 没有「日期」列就别报「日期缺失」 | 有的路线单只有单件/合计两列工时，日期由核算期决定，逐行报警纯属噪声 |
| 单件工时用「裁格复查」再读一次 | 整页尺度下格线穿过 5 的肚子会读成 8（`0:45:00`→`0:48:00`，置信度还更高）。但**必须多 padding 投票**——同一格 pad=0/2/4 得 45，pad=1/3/5 得 48，差 1px 就翻转 |
| 复查候选的标点形态必须与整页原文一致 | 去线会连带抹掉紧贴格线的冒号和点（`2.5`→`25`），这类残缺读数一律丢弃，否则会把 2.5 小时改成 25 小时 |
| 复查结果不按置信度取舍，只按勾稽仲裁 | 错值置信度反而更高（0.97 vs 0.93）。只有「整页值对不上手写合计、候选值对得上」才采用 |
| 姓名格、日期格不做复查 | 草书签名和手写 `9.10`（那个 1 只有 2px 高）在这个尺度下救不回来，只会引入噪声 |

### 切行的三条铁律

1. **切行不能靠 y 聚类**。手写行内 cy 抖动可达 80px，而行距只有 66px——行内差异比行间还大。
   必须用表格约束：同一行每列最多一个值，所以同行的两块文字不可能落在同一个 x 区间。
   见 `layout.group_rows_by_x()`。
2. **表头与数据必须分开切**。表头里「合格返修废品检查员」这种横跨多列的印刷标签会与数据同列文字 x 冲突。
   见 `layout.refine_data_rows()`。
3. **认不出来宁可不认**。短串模糊匹配会灾难性误判：单字符 `7` 曾被「包含关系加成」命成工序「发货」。
   宁可走 `UNKNOWN_PROCESS` 告警让人确认，也绝不猜成另一个工序/人/产品。

## 十六、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 上传后一直「待识别」 | OCR worker 没启动 | 跑 `scripts\start_ocr_worker.bat`；`/api/health` 会 ok=false 并提示 |
| 顶栏识别灯是红的但服务能用 | worker 进程挂了 / 库不可读 | 看 `health.worker.alive`；侧栏「导入与识别」有积压角标 |
| 上传的照片识别失败后不再重试 | `attempts >= 3`，毒图保护 | 确认图片本身是否可读，必要时重拍 |
| `No available model hosting platforms detected` | 默认模型源国内不可达 | 已内置 `PADDLE_PDX_MODEL_SOURCE=bos` |
| `ConvertPirAttribute2RuntimeAttribute` | oneDNN 指令路径 | 确认 `enable_mkldnn=False` 未被改动 |
| `Type of attribute: strides is not right` | Paddle 3.0.0 与模型算子不兼容 | 升级到 `paddlepaddle==3.3.1` |
| 装不上 paddlepaddle | Python 3.13 无 wheel | 用 3.11/3.12 建 venv |
| 识别结果为空 | 图片过暗/倾斜/分辨率过低 | 核对页点「重新识别」，或重拍补光 |
| 人员匹配不上 | 手写签名差异大 | 核对页下拉选择；改正即自动记别名 |
| 某列整列丢失 | 小字号子表头漏识 | 已内置母表头等分回溯；仍失败则手工补 |
| 导出被阻断 | 勾稽未通过 / 有待核对单据 / 有人未设单价 | 「导出与勾稽」页查看具体错误项 |
| 扫码提示「已报工」 | 同一张纸提交过两次 | 到扫码报工页「撤销」后再报，或改走撤销入口 |
| 扫码提示「码已失效」 | 单据被作废 | 重新打印（已报工的单会沿用原号） |
| 页面改了没生效 | 前端未重新构建 / 用了旧标签页 | `cd frontend && npx vite build`，浏览器 Ctrl+F5 |
| **后端改了没生效** | uvicorn 没开 `--reload` | **必须重启服务**。旧代码对着新表会静默降级（如结构全平铺） |
| `database is locked` | 并发写 + 长事务 | 已设 `timeout=30`；检查是否有未提交的长事务 |
| 结构树展开卡顿 | 一次性渲染 541 节点 | 已按子树分批 + MessageChannel 让出；别再往节点插槽塞 el- 组件 |

- 工时单价批量导入（当前逐人在系统管理里录）
- 加工路线单多联/多页、条码枪批量扫描
- 移动端拍照与扫码（当前已有响应式基础）

### 明确不建议（已评估，避免被重新提起）

| 方案 | 为什么不做 |
|---|---|
| 换 PostgreSQL / MySQL | 阈值是「日提交 > 5000 或并发写 > 50」，当前差两个数量级 |
| Redis / Celery | `image.status` 就是队列，多引入一个组件就多一处状态分叉 |
| OCR 多进程并行 | 实测吞吐 0.171 vs 0.175 张/s，Paddle 已吃满多核，加进程只抢核、多占 400MB |
| 全接口缓存 | 数据天天在改，缓存失效比不加更难解释 |
| 库文件覆盖式恢复 | 多进程占用 + WAL，Windows 上必然失败或丢数据 |

**岗位角色与名册的对应关系**（`kind` 字段）：

- `worker` → 明细「工作者」列
- `inspector` → 明细「检验员 / 检查员」列
- `receiver` → 明细「接交人 / 交接人」列
- `other` → 只做人员归类，不参与识别

内置 5 个岗位角色（工作者、检验员、接交人、计调员、材料员），内置角色的识别归类不可改，
避免历史单据匹配漂移；可自行新增。一人可兼多岗。没有任何岗位绑定的人会按 `is_inspector`
自动归类，不会漏出名册。

> **核对界面的「工作者」下拉按角色 `kind` 过滤，不看 `is_inspector` 布尔。**
> 之前按 `is_inspector` 过滤，兼任者（如马永刚既是工作者也是检验员）会被整个排除，
> `el-select` 找不到对应选项就把原始 value 当文本显示，界面上出现一个裸数字 `13`。
> 现在 `GET /api/dicts` 会返回每个人的 `kinds`（如 `["inspector","worker"]`），
> 下拉按 `kinds.includes('worker')` 过滤；若人员已停用/删除导致当前值不在名册里，
> 会补一个兜底选项显示原始手写名而不是数字 id。

**件名与工序是两件事**：工序是「怎么干」（车/铣/焊），件名是「干的是什么零件」（机架/刀轮）。
两者组合才定得出单件工时——同一产品同一道工序，不同零件的工时能差几倍，只按工序定标准必然误报。

### 三条口径约定

1. **精确命中保留原文，只有错字才纠偏**：单据写 `YUJ-18BZ`、字典里叫什么都按原写法存；
   只有识别成 `YUJ-l8BZ` 这类错字才会换成字典标准名。核对界面永远和原图对得上。
2. **名册为空 = 该字段未启用**：没维护检验员时不会因为「检验员未匹配」满屏告警。
3. **只有单据上写了值但不在字典里才提示**：`UNKNOWN_PRODUCT` / `UNKNOWN_MATERIAL` /
   `UNKNOWN_INSPECTOR` / `UNKNOWN_HANDOVER`，都是 warn 级，提示「去系统管理里补一条」。

### 批量导入（三种方式）

产品、工序、材料、件名、人员五项都支持：手动新增单条 / 粘贴文本 / 上传文件。

- **上传文件**：`.xlsx` / `.csv` / `.txt` 拖进去即可（旧版 `.xls` 需先另存为 `.xlsx`）。
  首行是表头 → 按列名对应，**列顺序不必和模板一致**；没有表头 → 按模板列顺序。
  可下载 CSV 模板（带 BOM，Excel 打开中文不乱码）。
- **粘贴文本**：列用 Tab / 逗号 / 中文逗号 / 竖线分隔均可。

```
产品：产品名称, 代号, 别名, 规格
工序：编码, 名称, 工种, 别名
材料：材料名称, 编码, 别名, 规格
人员：姓名, 工号, 班组, 工种, 别名, 角色（多个用 / 分隔）
```

- **别名分隔符随便写**：逗号、斜杠、顿号、分号、空格混排都会统一成逗号入库
  （`镗/镗床/镗工` → `镗,镗床,镗工`）。
- **名称列填单据上的写法**：产品/材料建议用单据上实际写的值，中文名放别名。
  若表里同时有「名称」和「代号」，名称列填中文名也能通过代号关联到已有记录，不会重复建。
- **工序编码可留空**：只填名称时按名称生成稳定编码，重复导入不会产生新记录。
- 支持「仅新增（跳过重复）」与「已存在则覆盖」；单条失败不影响其他行，回报新增/更新/跳过条数。

### 用最新字典回补历史单据

补完字典后点「用最新字典回补历史单据」，对指定核算期内**未确认**的单据重跑字段归一
（不重跑 OCR），把之前匹配不上的产品、材料、人员、检验员、接交人回填，并重算告警。
已确认的单据不动。接口：`POST /api/admin/rematch?ym=2026-09`。

### 从历史台账回填字典

车间手上有多年 Excel 台账（`doc/9月2车间工时核算.xlsx`）。用脚本把它里面出现过的
产品名称与工序提取进字典，识别兜底才有依据：

```bat
python scripts\import_ledger.py --dry-run   :: 只看归类报告，不写库
python scripts\import_ledger.py             :: 实际导入（幂等，可重复跑）
```

| 类别 | 处理 | 例子 |
|---|---|---|
| 工艺工序 | 归并为标准工序，原写法进别名 | 车1/车2 → 车；机架刨 → 刨；钳装 → 钳 |
| 件名类写法 | **不录工序字典** | 法兰、料仓、540内框、安装板1 |
| 噪声 | 丢弃 | 合计、工种：龙门刨 |
| 产品变体 | 合并到标准写法，原写法进别名 | YUJ-18Bz制丸机 → YUJ-18BZ制丸机 |
| 非产品杂项 | 剔除 | 零活、开车送货、外购拌料 |

**为什么件名类写法不录**：台账工序列是混合列，既有「车/铣/磨」这类工艺工序，也有「法兰/料仓」
这类**加工内容**。后者如果也进字典，月度汇总会碎成几十个只有一两条的"工序"，工时占比失去意义。
确需录入时加 `--include-unclassified`，会以工种「加工内容」建档。

存疑写法**不做自动合并**，按原文独立成条并打印清单，由人在弹窗里决定——猜错比多一条更难发现。
